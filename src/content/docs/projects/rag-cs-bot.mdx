## 한 줄 정의

정책·FAQ 문서와 주문 DB를 근거로 고객 문의에 답하고, 환불 같은 처리는 정책 검사와 금액별 승인을 거쳐 실행하며, 답할 수 없으면 사람 상담사에게 넘기는 CS 에이전트.

## 아키텍처

```
고객 ─▶ FastAPI(SSE) ─▶ LangGraph
                         classify ─┬─ 일반 문의 ─▶ Agentic RAG (search_docs: 하이브리드 + 리랭크)
                                   ├─ 주문/환불 ─▶ get_order ─▶ check_policy ─▶ (≥5만원) interrupt 승인 ─▶ execute_refund
                                   └─ 불명확/불만 ─▶ handoff_to_human
                         + 장기 메모리(고객 프로필), 대화 체크포인트
상담사 대시보드 ◀── 승인 대기 목록, 이관 목록
```

## 요구사항

1. 문서 30~100페이지, 하이브리드 검색(한국어 형태소 BM25 + 벡터 + RRF) + 리랭커 (6주차)
2. 근거 인용, 답이 없으면 거절 또는 이관
3. 환불 흐름: 정책 검사, 금액별 승인, 멱등 실행 (7, 21주차)
4. 고객별 장기 메모리: 백그라운드 추출, 갱신·삭제, 열람·삭제 API (13주차)
5. 사용자 권한: 고객은 자기 주문만 조회(도구 계층에서 강제) (18주차)
6. 주문 메모 필드 등 도구 결과 속 인젝션 방어 (17–18주차)
7. 상담사용 간단한 화면: 승인 대기, 이관된 대화

## 평가

| 지표 | 목표 예시 |
| --- | --- |
| Recall@5 (검색) | ≥ 0.85 |
| 정답률 (judge + 사람 대조) | ≥ 85% |
| 답 없는 질문 거절 정확도 | ≥ 90% |
| 정책 위반(승인 없이 환불 약속·실행) | 0건 (must-pass) |
| pass^3 (일관성) | 보고 |
| p95 응답 시간 | 보고 |
| 인젝션 공격 성공률 | 방어 전후 |

평가 세트 50개 이상: 정상 문의, 다단계 질문, 정보 부족, 거절해야 할 요청, 공격.

## 차별화 아이디어

- 실제 공공 FAQ나 오픈소스 문서로 "현실적인" 데이터셋 구성
- 사람 이관률과 "해결된 문의당 비용"으로 비즈니스 지표 제시
- 고정 RAG vs Agentic RAG 라우팅: 단순 질문은 고정 파이프라인으로 보내 비용 절감

## 면접에서 나올 질문

- 환각을 어떻게 측정하고 줄였나?
- 고객 A가 고객 B의 주문을 볼 수 없다는 걸 어떻게 보장하나?
- 메모리가 오히려 답을 망친 사례가 있었나?
- 승인 피로는 어떻게 관리하나?
