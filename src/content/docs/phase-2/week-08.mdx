## 학습 목표

- 주요 멀티 에이전트 토폴로지를 구현하고 각각의 실패 양상을 안다
- 멀티 에이전트가 싱글 에이전트보다 **나은 경우와 나쁜 경우**를 근거로 설명한다
- 서브에이전트에 줄 작업 지시(브리프)를 설계한다
- 워커 실패·타임아웃·결과 충돌을 처리한다

## 멀티 에이전트를 쓰는 진짜 이유

"역할극(기획자 에이전트, 개발자 에이전트…)"이 이유가 되어서는 안 됩니다. 실질적인 이유는 세 가지입니다.

1. **병렬성:** 독립적인 탐색을 동시에 해 벽시계 시간을 줄인다.
2. **컨텍스트 격리:** 각 서브에이전트가 깨끗한 컨텍스트에서 자기 일만 보고, 압축된 결과만 돌려준다. 오케스트레이터의 컨텍스트가 오염되지 않는다.
3. **전문화:** 서로 다른 도구 세트·프롬프트·모델이 필요한 하위 작업을 분리한다.

Anthropic은 자사 리서치 시스템에서 멀티 에이전트가 단일 에이전트보다 넓은 탐색 과제에서 크게 앞섰지만, **토큰 사용량은 일반 채팅의 약 15배**에 달했다고 공개했습니다. 즉 **가치가 높고, 병렬화가 잘 되며, 단일 컨텍스트를 넘는 작업**에만 경제성이 맞습니다. 반대로 Cognition(Devin)은 "Don't build multi-agents"라는 글에서, 코드 수정처럼 **결정들이 서로 강하게 얽힌 작업**은 서브에이전트들이 서로의 암묵적 결정을 모른 채 충돌하는 결과물을 만든다고 경고했습니다. 두 관점을 모두 알고 있어야 합니다.

## 핵심 토폴로지

### 1. Orchestrator–Worker (Supervisor)

```
           ┌──▶ Worker A (검색) ──┐
Orchestrator ─▶ Worker B (검색) ──┼──▶ Orchestrator(종합) ──▶ 결과
           └──▶ Worker C (분석) ──┘
```

오케스트레이터가 계획을 세우고 작업을 위임하며 결과를 종합합니다. 워커는 도구로 노출하는 방식(`delegate(task)` 도구)이 가장 단순합니다.

```python
async def delegate_research(brief: str, max_turns: int = 8) -> str:
    """서브에이전트: 깨끗한 컨텍스트에서 brief만 보고 조사 후 요약을 돌려준다."""
    answer, stats = await agent(           # 4주차 루프 재사용
        task=brief,
        tools=[web_search, fetch_page],
        system=WORKER_SYSTEM,               # "결과는 500단어 이내 요약 + 출처 목록으로"
        max_turns=max_turns,
    )
    return answer

ORCH_TOOLS = [{"name": "delegate_research",
               "description": "독립적인 조사 하위 작업을 서브에이전트에 맡긴다. 서로 겹치지 않는 하위 주제로 나눠 여러 번 동시에 호출하라.",
               "input_schema": {...}}]
```

### 2. Handoff (스웜형)

에이전트가 대화의 **통제권 자체를** 다른 에이전트에게 넘깁니다(CS에서 일반 상담 → 환불 전문). OpenAI Agents SDK의 handoff, LangGraph의 `Command(goto=...)`가 이 방식입니다. 오케스트레이터 방식은 결과를 돌려받지만, 핸드오프는 넘겨준 쪽이 빠집니다.

### 3. 계층형

오케스트레이터 아래 팀 리더, 그 아래 워커. 깊어질수록 조율 비용과 정보 손실이 커지므로 2단을 넘는 경우는 드뭅니다.

### 4. Evaluator–Optimizer와 다중 비평

생성자 1 + 평가자 N(사실 확인, 스타일, 규정 준수). 평가자는 다른 프롬프트·다른 모델일수록 효과가 있습니다.

### 5. MoA (Mixture of Agents)

여러 모델이 각자 답을 내고, 집계 모델이 이를 종합합니다. 단일 모델보다 품질이 오를 수 있지만 비용이 모델 수만큼 늘어납니다. 고가치·저빈도 작업(중요 문서 검토)에 맞습니다.

### 6. CodeAct

도구를 JSON으로 하나씩 부르는 대신 **모델이 파이썬 코드를 써서** 여러 도구를 루프·조건문으로 조합해 한 번에 실행합니다. 턴 수가 크게 줄고 데이터 처리가 정확해지지만 **샌드박스가 필수**입니다(18주차). MCP 도구를 코드 API로 노출해 에이전트가 코드로 호출하게 하는 방식도 같은 계열로, 도구 정의와 중간 결과가 컨텍스트를 덜 차지합니다.

## DeepResearch 구조 해부

```
1. 질문 명확화 (필요 시 사용자에게 되묻기)
2. 계획: 하위 질문 3~7개 + 각 하위 질문의 검색 전략
3. 병렬 조사: 하위 질문마다 서브에이전트 (검색 → 읽기 → 메모 → 반복)
4. 반성(reflection): 빈 곳이 있으면 추가 조사 라운드
5. 종합: 개요 → 섹션 작성 → 인용 검증
6. 출력: 보고서 + 출처
```

설계 포인트:

- **서브에이전트 브리프의 질:** "AI 반도체 조사해"가 아니라 목적, 범위, 제외할 것, 출력 형식, 예상 도구 호출 수, 끝내는 기준을 담습니다. Anthropic은 브리프가 모호하면 서브에이전트들이 같은 일을 중복하거나 엉뚱한 범위를 조사했다고 보고했습니다.
- **노력 규모 조절:** 단순 사실 확인은 서브에이전트 1개·도구 3~10회, 복잡한 비교는 서브에이전트 여러 개처럼 **질문 난이도에 따라 규모를 정하는 규칙**을 오케스트레이터 프롬프트에 넣습니다.
- **결과는 파일로:** 서브에이전트가 긴 결과를 오케스트레이터를 거쳐 전달하면 "전화 게임"처럼 손실됩니다. 결과를 파일·저장소에 쓰고 참조만 넘기는 방식이 효과적입니다(11주차).
- **인용 전담 단계:** 마지막에 별도 에이전트가 각 주장과 출처를 대조합니다.

## 심화

### 실패 양상과 대응

| 실패 | 증상 | 대응 |
| --- | --- | --- |
| 중복 작업 | 워커들이 같은 자료를 찾음 | 겹치지 않는 범위를 명시한 브리프, 공유 "이미 찾은 URL" 목록 |
| 과잉 위임 | 간단한 질문에 워커 10개 | 난이도별 규모 규칙, 워커 수 상한 |
| 결과 충돌 | 워커 A와 B의 결론이 반대 | 종합 단계에서 충돌을 명시하고 추가 검증 |
| 조기 종료 | 오케스트레이터가 일부 결과만 보고 끝냄 | 완료 기준 체크리스트, 반성 단계 |
| 워커 폭주 | 한 워커가 무한히 검색 | 워커별 턴·토큰·시간 예산 |
| 워커 실패 | 타임아웃·에러 | 부분 결과로 진행 + 실패한 하위 작업 재시도 1회 |

### 비용 모델

```
멀티 에이전트 비용 ≈ 오케스트레이터(계획 + 종합) + Σ 워커(각자의 루프)
```

워커는 각자 시스템 프롬프트·도구 정의를 다시 읽으므로 고정 비용이 워커 수만큼 곱해집니다. 그래서 워커는 **작은 모델**, 오케스트레이터와 종합은 **큰 모델**로 나누는 구성이 흔합니다. 프롬프트 캐싱 적중률도 꼭 확인합니다.

### 통신 방식

- **도구 호출(동기):** 가장 단순. 오케스트레이터가 결과를 기다림.
- **공유 상태(블랙보드):** LangGraph 상태나 파일시스템에 각자 쓰고 읽음.
- **메시지 큐(비동기):** 장시간·대규모 작업.
- **프로토콜(A2A):** 다른 팀·다른 프레임워크의 에이전트와 연결(10주차).

## 실습 과제: 병렬 리서치 에이전트 vs 싱글 에이전트

`weeks/w08_multi_agent/`

**요구사항**

1. LangGraph로 DeepResearch 축소판 구현: `clarify`(선택) → `plan`(하위 질문 3~5개, 구조화 출력) → `Send`로 병렬 `research` 워커 → `reflect`(빈 곳이 있으면 1라운드 추가) → `write` → `cite_check`.
2. 워커는 작은 모델, plan·write는 큰 모델. 워커별 예산: 턴 8, 토큰 3만, 시간 90초.
3. 워커 결과는 `findings/{subtopic}.md` 파일에 쓰고, 상태에는 경로와 3줄 요약만 넣는다.
4. 워커 하나를 일부러 실패시켜도(예외 주입) 보고서가 완성되고, 빠진 부분이 명시된다.
5. 같은 질문 5개를 **싱글 에이전트**(4주차 루프 + 같은 도구, 턴 30)로도 돌린다.
6. 두 방식의 비용, 벽시계 시간, 출처 수, 품질(루브릭 1~5점: 포괄성, 정확성, 인용)을 비교한다.

**채점 기준**

- [ ] 비교표에 "멀티 에이전트가 나았던 질문 유형"과 "싱글이 충분했던 유형"이 구분되어 있다
- [ ] 워커 실패 주입 테스트가 있다
- [ ] 총 토큰 중 워커가 차지하는 비율을 측정했다

## 흔한 실수

- 역할만 나누고 컨텍스트·도구·모델은 같음 → 비용만 늘고 이득이 없습니다.
- 서브에이전트에 "적당히 조사해"라고만 지시 → 범위 중복, 끝없는 검색
- 워커의 원문 결과를 그대로 오케스트레이터에 붙임 → 컨텍스트 격리의 이점이 사라집니다.

## 면접 질문

<details>
<summary>멀티 에이전트 시스템은 언제 쓰고 언제 피해야 하나요?</summary>

독립적으로 병렬화할 수 있는 넓은 탐색(리서치, 다수 문서 분석), 하나의 컨텍스트에 다 담기 어려운 대량 정보, 서로 다른 도구·권한이 필요한 하위 작업에 씁니다. 결정들이 강하게 얽힌 작업(하나의 코드베이스 수정, 일관된 문체의 글), 지연·비용 제약이 엄격한 작업, 간단한 질의에는 피합니다. 멀티 에이전트는 토큰을 몇 배에서 십수 배 쓰므로 작업 가치가 그 비용을 정당화해야 하고, 싱글 에이전트와 같은 평가 세트로 비교해 결정합니다.
</details>

<details>
<summary>Orchestrator–Worker와 Handoff의 차이는?</summary>

Orchestrator–Worker는 중앙 에이전트가 통제권을 유지하며 하위 작업을 위임하고 결과를 돌려받아 종합합니다. Handoff는 대화나 작업의 통제권 자체를 다른 에이전트로 넘기며, 넘긴 쪽은 더 이상 관여하지 않습니다. 결과 종합과 병렬화가 필요하면 전자, 전문 영역별로 사용자와 직접 대화해야 하는 CS 같은 경우는 후자가 자연스럽습니다.
</details>

<details>
<summary>서브에이전트에게 작업을 지시할 때 무엇을 포함해야 하나요?</summary>

목적(왜 필요한지), 구체적 범위와 제외 범위(다른 워커와 겹치지 않게), 사용할 도구와 예상 노력 수준, 출력 형식과 길이, 완료 기준, 시간·토큰 예산입니다. 서브에이전트는 오케스트레이터의 대화 맥락을 모르므로 필요한 배경을 명시해야 합니다. 브리프가 모호하면 중복 작업, 범위 이탈, 과도한 검색이 생깁니다.
</details>

<details>
<summary>CodeAct가 JSON tool calling보다 나은 점과 위험은?</summary>

모델이 코드로 여러 도구 호출을 반복문·조건문·변수와 함께 조합하므로 턴 수가 줄고, 대량 데이터 필터링·계산을 정확하게 하며, 중간 결과를 컨텍스트에 다 싣지 않아도 됩니다. 대신 임의 코드 실행이므로 격리된 샌드박스, 네트워크·파일 접근 제한, 실행 시간·메모리 제한, 출력 크기 제한이 필수입니다.
</details>
