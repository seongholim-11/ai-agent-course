## 학습 목표

- 주요 멀티 에이전트 토폴로지를 구현하고 각각의 실패 양상을 안다
- 멀티 에이전트가 싱글 에이전트보다 **나은 경우와 나쁜 경우**를 근거로 설명한다

## 멀티 에이전트를 쓰는 진짜 이유

**멀티 에이전트**는 에이전트 여러 개가 일을 나눠 하는 구조입니다. 흔히 "기획자 에이전트, 개발자 에이전트, 테스터 에이전트"처럼 회사 조직도를 흉내 내는 예시를 보게 되는데, **역할 이름을 나누는 것 자체는 아무 이득이 없습니다.** 같은 모델에 같은 정보를 주고 이름표만 바꾼 것이니까요. 실질적인 이유는 세 가지입니다.

1. **병렬성:** 서로 기다릴 필요 없는 조사를 동시에 해서 총 소요 시간(벽시계 시간)을 줄인다. 혼자 도서관 다섯 곳을 돌면 5시간, 다섯 명이 나눠 가면 1시간입니다.
2. **컨텍스트 격리:** 각 서브에이전트가 깨끗한 작업대(컨텍스트)에서 자기 일만 보고, 결과는 **압축된 요약만** 돌려줍니다. 서브에이전트가 웹페이지 30개를 읽었어도, 팀장(오케스트레이터)의 작업대에는 요약 한 장만 올라옵니다. 팀장의 작업대가 잡동사니로 덮이지 않습니다.
3. **전문화:** 서로 다른 도구 세트·프롬프트·모델이 필요한 일을 분리한다. 웹 검색 담당에게는 검색 도구만, DB 분석 담당에게는 SQL 도구만 주면 각자 헷갈릴 일이 줄어듭니다.

그런데 공짜가 아닙니다. Anthropic은 자사 리서치 시스템에서 멀티 에이전트가 넓은 범위를 탐색하는 과제에서 단일 에이전트보다 크게 앞섰지만, **토큰 사용량은 일반 채팅의 약 15배**에 달했다고 공개했습니다. 즉 **가치가 높고, 병렬화가 잘 되며, 한 작업대에 다 올릴 수 없을 만큼 큰 작업**에서만 수지가 맞습니다.

반대 의견도 알아야 합니다. Cognition(Devin을 만든 회사)은 "Don't build multi-agents"라는 글에서, 코드 수정처럼 **결정들이 서로 강하게 얽힌 작업**은 서브에이전트들이 서로가 암묵적으로 내린 결정(변수 이름, 설계 방향)을 모른 채 일해서, 합쳐 보면 서로 충돌하는 결과물이 나온다고 경고했습니다. 여러 사람이 소설을 한 챕터씩 따로 쓰면 등장인물 성격이 챕터마다 달라지는 것과 같습니다. 면접에서는 두 관점을 모두 말할 수 있어야 합니다.

## 핵심 토폴로지

**토폴로지**는 에이전트들이 어떻게 연결되어 있는지의 모양입니다.

### 1. Orchestrator–Worker (Supervisor)

```
           ┌──▶ Worker A (검색) ──┐
Orchestrator ─▶ Worker B (검색) ──┼──▶ Orchestrator(종합) ──▶ 결과
           └──▶ Worker C (분석) ──┘
```

팀장(오케스트레이터)이 계획을 세우고, 일을 팀원(워커)에게 나눠주고, 결과를 모아 종합합니다. 가장 흔하고 가장 먼저 시도해볼 구조입니다.

구현하는 가장 단순한 방법은 **워커를 도구로 만드는 것**입니다. 오케스트레이터 입장에서 "서브에이전트에게 맡기기"는 그냥 도구 호출 하나입니다.

```python
async def delegate_research(brief: str, max_turns: int = 8) -> str:
    """서브에이전트: 깨끗한 컨텍스트에서 brief만 보고 조사 후 요약을 돌려준다."""
    # 4주차 루프를 그대로 재사용한다. 단, 새 대화로 시작하므로 오케스트레이터의 대화 내용은 모른다
    answer, stats = await agent(
        task=brief,                         # 서브에이전트가 아는 것은 이 브리프뿐 → 브리프가 자세해야 한다
        tools=[web_search, fetch_page],     # 조사에 필요한 도구만 준다
        system=WORKER_SYSTEM,               # "결과는 500단어 이내 요약 + 출처 목록으로" (긴 원문을 돌려주지 않게)
        max_turns=max_turns,                # 워커 하나가 폭주하지 않게 예산을 건다
    )
    return answer                           # 오케스트레이터에게는 요약만 돌아간다

# 오케스트레이터에게 주는 도구. 설명에 "겹치지 않게 나눠서, 동시에 여러 번"을 명시한다
ORCH_TOOLS = [{"name": "delegate_research",
               "description": "독립적인 조사 하위 작업을 서브에이전트에 맡긴다. 서로 겹치지 않는 하위 주제로 나눠 여러 번 동시에 호출하라.",
               "input_schema": {...}}]
```

오케스트레이터가 한 턴에 `delegate_research`를 3번 호출하면, 4주차 루프의 병렬 실행(`gather`) 덕분에 서브에이전트 3개가 동시에 돕니다.

### 2. Handoff (스웜형)

에이전트가 대화의 **통제권 자체를** 다른 에이전트에게 넘깁니다. 고객센터에서 "환불 문의시군요, 환불 담당자에게 연결해드리겠습니다"라고 전화를 돌려주는 것과 같습니다. 일반 상담 에이전트 → 환불 전문 에이전트처럼 넘어가면, 그 뒤로는 환불 에이전트가 고객과 직접 대화합니다. OpenAI Agents SDK의 handoff, LangGraph의 `Command(goto=...)`가 이 방식입니다.

Orchestrator와의 차이: 오케스트레이터는 일을 맡기고 **결과를 돌려받아** 계속 책임지지만, 핸드오프는 넘겨준 쪽이 **빠집니다.**

### 3. 계층형

오케스트레이터 아래 팀 리더들, 그 아래 워커들. 회사 조직도처럼 층이 생깁니다. 하지만 층이 깊어질수록 지시가 전달되며 왜곡되고(전화 게임), 조율 비용이 커지므로 2단을 넘는 경우는 드뭅니다.

### 4. Evaluator–Optimizer와 다중 비평

생성자 1명 + 평가자 여러 명(사실 확인 담당, 문체 담당, 규정 준수 담당)이 함께 검토하는 구조입니다. 5주차 Evaluator–Optimizer를 확장한 것입니다. 평가자는 생성자와 **다른 프롬프트·다른 모델**일수록 효과가 있습니다. 같은 사람이 자기 글을 검토하면 실수가 잘 안 보이는 것과 같은 이유입니다.

### 5. MoA (Mixture of Agents)

여러 모델(예: Claude, GPT, Gemini)이 각자 답을 내고, 집계 모델이 그 답들을 읽고 종합해 최종 답을 씁니다. 여러 전문가 의견을 모아 보고서를 쓰는 것과 같습니다. 단일 모델보다 품질이 오를 수 있지만 비용이 모델 수만큼 늘어나므로, 중요하고 자주 하지 않는 작업(중요 계약서 검토)에 맞습니다.

### 6. CodeAct

보통 에이전트는 도구를 JSON으로 하나씩 부르고, 결과를 보고, 다음 도구를 부릅니다. **CodeAct**는 모델이 **파이썬 코드를 써서** 여러 도구를 반복문·조건문으로 엮어 한 번에 실행하게 합니다.

예를 들어 "주문 100건 중 환불 요청이 있는 것의 금액 합계"를 구할 때, JSON 방식이면 도구를 100번 부르며 100턴을 돌 수도 있지만, CodeAct면 모델이 `for` 문이 든 코드 한 덩어리를 써서 한 턴에 끝냅니다. 턴 수가 크게 줄고 계산도 정확해집니다. 대신 모델이 쓴 임의의 코드를 실행하는 것이니 **샌드박스(격리된 실행 환경)가 필수**입니다(18주차).

MCP 도구를 코드 API처럼 노출해서 에이전트가 코드로 호출하게 하는 방식도 같은 계열입니다. 도구 정의와 중간 결과를 컨텍스트에 다 싣지 않아도 되니 작업대를 덜 차지합니다.

## DeepResearch 구조 해부

"딥리서치"는 질문 하나를 받아 수십 개의 출처를 조사하고 보고서를 쓰는 기능입니다. 멀티 에이전트의 대표 사례이니 구조를 뜯어봅시다.

```
1. 질문 명확화     질문이 모호하면 사용자에게 되묻는다 ("어느 나라 기준인가요?")
2. 계획           하위 질문 3~7개 + 각 하위 질문을 어떻게 검색할지
3. 병렬 조사       하위 질문마다 서브에이전트 하나 (검색 → 읽기 → 메모 → 반복)
4. 반성           결과를 훑어보고 빈 곳이 있으면 추가 조사 라운드
5. 종합           개요 → 섹션별 작성 → 인용이 맞는지 검증
6. 출력           보고서 + 출처
```

잘 만들기 위한 설계 포인트:

- **서브에이전트 브리프의 질:** 서브에이전트는 팀장의 대화를 모릅니다. "AI 반도체 조사해"라고만 하면 무엇을 얼마나 조사할지 모릅니다. 새로 온 외주 직원에게 일을 맡기듯 **목적, 범위, 제외할 것, 출력 형식, 예상 도구 호출 수, 언제 끝내면 되는지**를 적어줍니다. Anthropic은 브리프가 모호하면 서브에이전트들이 같은 일을 중복하거나 엉뚱한 범위를 조사했다고 보고했습니다.
- **노력 규모 조절:** 모델은 일을 크게 벌이는 경향이 있습니다. "단순 사실 확인은 서브에이전트 1개·도구 3~10회, 복잡한 비교는 서브에이전트 여러 개"처럼 **질문 난이도에 따라 규모를 정하는 규칙**을 오케스트레이터 프롬프트에 적어둡니다.
- **결과는 파일로:** 서브에이전트의 긴 결과를 오케스트레이터를 거쳐 전달하면, 거칠 때마다 요약되며 정보가 빠지는 "전화 게임"이 생깁니다. 결과는 파일·저장소에 쓰고 **"findings/반도체_공급망.md에 저장했음 + 3줄 요약"처럼 참조만** 넘기는 방식이 효과적입니다(11주차).
- **인용 전담 단계:** 마지막에 별도 에이전트가 보고서의 각 주장이 실제로 그 출처에 있는 내용인지 대조합니다.

## 심화

### 실패 양상과 대응

멀티 에이전트는 사람 팀이 겪는 문제를 그대로 겪습니다.

| 실패 | 증상 | 대응 |
| --- | --- | --- |
| 중복 작업 | 워커들이 같은 자료를 찾음 | 겹치지 않는 범위를 명시한 브리프, 공유 "이미 찾은 URL" 목록 |
| 과잉 위임 | 간단한 질문에 워커 10개 | 난이도별 규모 규칙, 워커 수 상한 |
| 결과 충돌 | 워커 A와 B의 결론이 반대 | 종합 단계에서 충돌을 명시하고 추가 검증 |
| 조기 종료 | 오케스트레이터가 일부 결과만 보고 끝냄 | 완료 기준 체크리스트, 반성 단계 |
| 워커 폭주 | 한 워커가 무한히 검색 | 워커별 턴·토큰·시간 예산 |
| 워커 실패 | 타임아웃·에러 | 부분 결과로 진행 + 실패한 하위 작업 재시도 1회 |

### 비용 모델

```
멀티 에이전트 비용 ≈ 오케스트레이터(계획 + 종합) + Σ 워커(각자의 루프)
```

놓치기 쉬운 부분: 워커는 각자 새 대화로 시작하므로 **시스템 프롬프트와 도구 정의를 각자 다시 읽습니다.** 이 고정 비용이 워커 수만큼 곱해집니다. 그래서 흔히 **워커는 작은 모델**(단순 검색·요약), **오케스트레이터와 종합은 큰 모델**(계획·판단)로 나눕니다. 워커들이 같은 시스템 프롬프트를 쓰면 프롬프트 캐싱으로 고정 비용을 줄일 수 있으니, 캐시 적중률도 꼭 확인합니다.

### 통신 방식

에이전트끼리 정보를 주고받는 방법도 여러 가지입니다.

- **도구 호출(동기):** 가장 단순합니다. 오케스트레이터가 워커를 도구처럼 부르고 결과를 기다립니다.
- **공유 상태(블랙보드):** 회의실 화이트보드처럼, LangGraph 상태나 파일시스템에 각자 쓰고 읽습니다.
- **메시지 큐(비동기):** 몇 시간짜리, 대규모 작업에서 작업 쪽지를 큐에 넣고 워커들이 꺼내 처리합니다.
- **프로토콜(A2A):** 다른 팀·다른 프레임워크로 만든 에이전트와 표준 규격으로 연결합니다(10주차).

## 실습 과제: 병렬 리서치 에이전트 vs 싱글 에이전트

`weeks/w08_multi_agent/`

**요구사항**

1. LangGraph로 DeepResearch 축소판 구현: `clarify`(선택) → `plan`(하위 질문 3~5개, 구조화 출력) → `Send`로 병렬 `research` 워커 → `reflect`(빈 곳이 있으면 1라운드 추가) → `write` → `cite_check`.
2. 워커는 작은 모델, plan·write는 큰 모델. 워커별 예산: 턴 8, 토큰 3만, 시간 90초.
3. 워커 결과는 `findings/{subtopic}.md` 파일에 쓰고, 상태에는 경로와 3줄 요약만 넣는다.
4. 워커 하나를 일부러 실패시켜도(예외 주입) 보고서가 완성되고, 빠진 부분이 명시된다.
5. 같은 질문 5개를 **싱글 에이전트**(4주차 루프 + 같은 도구, 턴 30)로도 돌린다.
6. 두 방식의 비용, 벽시계 시간, 출처 수, 품질(루브릭 1~5점: 포괄성, 정확성, 인용)을 비교한다.

**채점 기준**

- [ ] 비교표에 "멀티 에이전트가 나았던 질문 유형"과 "싱글이 충분했던 유형"이 구분되어 있다
- [ ] 워커 실패 주입 테스트가 있다
- [ ] 총 토큰 중 워커가 차지하는 비율을 측정했다

## 흔한 실수

- **역할 이름만 나누고 컨텍스트·도구·모델은 같음:** 위에서 말한 세 가지 이점이 하나도 없으니 비용만 늘어납니다.
- **서브에이전트에 "적당히 조사해"라고만 지시:** 범위가 겹치고, 언제 끝낼지 몰라 끝없이 검색합니다.
- **워커의 원문 결과를 그대로 오케스트레이터에 붙임:** 컨텍스트 격리라는 가장 큰 이점이 사라집니다. 요약과 참조만 넘기세요.

## 면접 질문

<details>
<summary>멀티 에이전트 시스템은 언제 쓰고 언제 피해야 하나요?</summary>

독립적으로 병렬화할 수 있는 넓은 탐색(리서치, 다수 문서 분석), 하나의 컨텍스트에 다 담기 어려운 대량 정보, 서로 다른 도구·권한이 필요한 하위 작업에 씁니다. 결정들이 강하게 얽힌 작업(하나의 코드베이스 수정, 일관된 문체의 글), 지연·비용 제약이 엄격한 작업, 간단한 질의에는 피합니다. 멀티 에이전트는 토큰을 몇 배에서 십수 배 쓰므로 작업 가치가 그 비용을 정당화해야 하고, 싱글 에이전트와 같은 평가 세트로 비교해 결정합니다.
</details>

<details>
<summary>Orchestrator–Worker와 Handoff의 차이는?</summary>

Orchestrator–Worker는 중앙 에이전트가 통제권을 유지하며 하위 작업을 위임하고 결과를 돌려받아 종합합니다. Handoff는 대화나 작업의 통제권 자체를 다른 에이전트로 넘기며, 넘긴 쪽은 더 이상 관여하지 않습니다. 결과 종합과 병렬화가 필요하면 전자, 전문 영역별로 사용자와 직접 대화해야 하는 CS 같은 경우는 후자가 자연스럽습니다.
</details>

<details>
<summary>서브에이전트에게 작업을 지시할 때 무엇을 포함해야 하나요?</summary>

목적(왜 필요한지), 구체적 범위와 제외 범위(다른 워커와 겹치지 않게), 사용할 도구와 예상 노력 수준, 출력 형식과 길이, 완료 기준, 시간·토큰 예산입니다. 서브에이전트는 오케스트레이터의 대화 맥락을 모르므로 필요한 배경을 명시해야 합니다. 브리프가 모호하면 중복 작업, 범위 이탈, 과도한 검색이 생깁니다.
</details>

<details>
<summary>CodeAct가 JSON tool calling보다 나은 점과 위험은?</summary>

모델이 코드로 여러 도구 호출을 반복문·조건문·변수와 함께 조합하므로 턴 수가 줄고, 대량 데이터 필터링·계산을 정확하게 하며, 중간 결과를 컨텍스트에 다 싣지 않아도 됩니다. 대신 임의 코드 실행이므로 격리된 샌드박스, 네트워크·파일 접근 제한, 실행 시간·메모리 제한, 출력 크기 제한이 필수입니다.
</details>
