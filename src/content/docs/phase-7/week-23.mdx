## 학습 목표

- 24주 동안의 회고 메모를 재료로 기술 글 2편을 쓴다
- 에이전트 생태계 오픈소스에 의미 있는 기여를 1건 이상 한다

## 기술 블로그

### 무엇을 쓸까

가장 가치 있는 글은 **"해봤더니 이랬다"**입니다. 개념 정리 글은 이미 많습니다. 회고 메모(각 주차 하단)에서 수치가 있는 실패·개선 경험을 고르세요.

주제 예시:

- "한국어 RAG에서 BM25 하이브리드가 Recall@5를 0.6에서 0.8로 올린 과정"
- "LLM-as-judge를 사람 평가와 맞추기까지: kappa 0.41 → 0.78"
- "멀티 에이전트 리서치, 싱글 에이전트보다 정말 나은가? 비용 2배의 값어치 분석"
- "프롬프트 캐싱 적중률 31%의 원인은 시스템 프롬프트 첫 줄의 날짜였다"
- "내 에이전트를 직접 공격해봤다: 간접 인젝션 20개 시나리오와 방어 결과"

### 글의 구조

1. **문제와 맥락** (무엇을 만들다가 무슨 문제를 만났나, 숫자로)
2. **가설과 시도** (실패한 시도 포함, 왜 실패했나)
3. **해결과 결과** (전후 비교표, 그래프)
4. **일반화** (다른 사람이 가져갈 수 있는 교훈)
5. **한계** (이 결과가 적용되지 않는 경우)

분량은 1,500~3,000자, 코드와 표, 그래프 1개 이상. 사내 기술 블로그 수준의 글 2편이면 면접에서 반드시 질문이 나옵니다.

## 오픈소스 기여

### 어디에

LangGraph, MCP SDK·서버, Langfuse, LiteLLM, vLLM, 평가 도구(Ragas 등), 한국어 NLP 도구(Kiwi 등).

### 어떻게

1. 쓰다가 막힌 지점을 기록해둔다(이번 24주 동안 반드시 있었을 것)
2. 이슈 트래커에서 같은 문제를 찾거나, 재현 가능한 최소 예제로 이슈를 연다
3. `good first issue`, 문서 개선, 예제 추가, 한국어 관련 버그부터
4. 기여 가이드(CONTRIBUTING.md)를 읽고, 작은 PR로, 테스트와 함께

작은 문서 수정 PR이라도 **실제로 쓰다가 발견한 문제**를 고친 것이면 면접에서 좋은 이야깃거리가 됩니다. 직접 만든 MCP 서버를 공식 목록이나 커뮤니티 레지스트리에 등록하는 것도 방법입니다.

## GitHub 프로필

- 프로필 README: 한 줄 소개, 대표 프로젝트 3개(한 줄 설명 + 핵심 수치 + 링크), 블로그 글, 기술 스택
- 대표 저장소 고정(pin)
- 각 저장소에 설명, 토픽 태그, 데모 링크
- 커밋 메시지가 의미 있게(면접관이 이력을 볼 수 있음)

## 실습 과제

- [ ] 기술 블로그 2편 발행 (각각 수치 비교표 포함)

- [ ] 블로그 ↔ README ↔ 프로필 상호 링크

## 면접 질문

<details>
<summary>최근에 읽은 에이전트 관련 글이나 논문 중 인상 깊었던 것은?</summary>

준비 방법: 이 코스의 "더 읽기"에서 두세 개를 골라 **요지 한 문장, 내 프로젝트에 적용한 것 또는 적용하지 않은 이유, 동의하지 않는 부분**을 정리해둡니다. 예: Anthropic의 멀티 에이전트 리서치 글과 Cognition의 "Don't build multi-agents"를 함께 읽고, 내 리서치 에이전트는 하위 작업이 독립적이라 전자가 맞았지만 코드 수정 에이전트였다면 후자의 지적처럼 단일 에이전트가 나았을 것이라고 말하면 좋습니다.
</details>

<details>
<summary>빠르게 변하는 AI 생태계를 어떻게 따라가나요?</summary>

공식 엔지니어링 블로그(공급자, 주요 프레임워크), 스펙 저장소의 변경 사항(MCP 등), 컨퍼런스 영상, 소수의 신뢰하는 실무자 글을 정기적으로 봅니다. 새 도구는 이름이 아니라 "어떤 문제를 어떤 트레이드오프로 푸는가"로 이해하고, 내 평가 세트로 직접 확인해 채택 여부를 정합니다. 패턴(컨텍스트 관리, 평가, 권한 설계)은 도구보다 오래가므로 거기에 시간을 더 씁니다.
</details>
