## 기술 블로그

이번 주의 목표는 **공개된 증거**를 만드는 것입니다. 이력서에 "평가 체계를 구축했다"고 적는 것보다, 그 과정을 자세히 쓴 글 링크 하나가 훨씬 설득력 있습니다. 면접관은 글을 읽고 "이 사람은 이 문제를 정말 깊이 고민했구나"를 확인하고, 거기서 질문을 시작합니다.

### 무엇을 쓸까

가장 가치 있는 글은 **"해봤더니 이랬다"**입니다. "RAG란 무엇인가" 같은 개념 정리 글은 이미 수천 개가 있습니다. 하지만 "내가 이걸 해봤더니 이런 문제가 있었고, 이렇게 고쳤더니 숫자가 이렇게 바뀌었다"는 글은 그 경험을 한 사람만 쓸 수 있습니다.

재료는 이미 있습니다. 각 주차 하단의 **회고 메모**에서 수치가 있는 실패·개선 경험을 고르세요.

주제 예시:

- "한국어 RAG에서 BM25 하이브리드가 Recall@5를 0.6에서 0.8로 올린 과정"
- "LLM-as-judge를 사람 평가와 맞추기까지: kappa 0.41 → 0.78"
- "멀티 에이전트 리서치, 싱글 에이전트보다 정말 나은가? 비용 2배의 값어치 분석"
- "프롬프트 캐싱 적중률 31%의 원인은 시스템 프롬프트 첫 줄의 날짜였다"
- "내 에이전트를 직접 공격해봤다: 간접 인젝션 20개 시나리오와 방어 결과"

좋은 제목은 **구체적인 숫자나 의외의 결론**을 담고 있습니다. "RAG 성능 개선기"보다 "캐시 적중률 31%의 범인은 날짜 한 줄이었다"가 읽고 싶어집니다.

### 글의 구조

1. **문제와 맥락:** 무엇을 만들다가 무슨 문제를 만났나. 숫자로. ("리서치 에이전트의 보고서당 비용이 $0.91이었다")
2. **가설과 시도:** 무엇을 의심했고 무엇을 해봤나. **실패한 시도도 포함**하고, 왜 실패했는지 쓴다. 독자는 실패담에서 가장 많이 배운다.
3. **해결과 결과:** 무엇이 효과가 있었나. 전후 비교표, 그래프.
4. **일반화:** 다른 사람이 자기 프로젝트에 가져갈 수 있는 교훈.
5. **한계:** 이 결과가 적용되지 않는 경우. ("문서가 1,000건 이하일 때만 확인했다")

분량은 1,500~3,000자, 코드와 표, 그래프 1개 이상. 회사 기술 블로그 수준의 글 2편이면 면접에서 반드시 질문이 나옵니다.

## 오픈소스 기여

### 어디에

LangGraph, MCP SDK·서버, Langfuse, LiteLLM, vLLM, 평가 도구(Ragas 등), 한국어 NLP 도구(Kiwi 등). 이 코스에서 직접 써본 도구들입니다. 써본 도구일수록 기여할 거리가 보입니다.

### 어떻게

오픈소스 기여라고 하면 거창한 기능을 만들어야 할 것 같지만, 그렇지 않습니다.

1. **쓰다가 막힌 지점을 기록해둔다.** 24주 동안 "문서에 이게 없네", "이 에러 메시지가 무슨 뜻인지 모르겠네", "한국어에서 이상하게 동작하네" 같은 순간이 반드시 있었을 것입니다.
2. **이슈 트래커에서 같은 문제를 찾거나**, 없으면 다른 사람이 그대로 따라 해서 문제를 볼 수 있는 **최소 재현 예제**로 이슈를 연다. 좋은 버그 리포트도 그 자체로 기여입니다.
3. `good first issue` 라벨이 붙은 이슈, 문서 개선, 예제 추가, 한국어 관련 버그부터 시작한다.
4. **기여 가이드(CONTRIBUTING.md)를 먼저 읽고**, 작은 PR로, 테스트와 함께 보낸다. 큰 변경은 PR을 만들기 전에 이슈로 먼저 의견을 묻는다.

작은 문서 수정 PR이라도 **실제로 쓰다가 발견한 문제**를 고친 것이라면 면접에서 좋은 이야깃거리가 됩니다. "이 라이브러리를 쓰다가 이런 문제를 겪었고, 원인을 찾아 고쳐서 기여했다"는 문제 해결 과정 전체를 보여주기 때문입니다. 직접 만든 MCP 서버를 공식 목록이나 커뮤니티 레지스트리에 등록하는 것도 방법입니다.

## GitHub 프로필

GitHub 프로필은 포트폴리오의 **입구**입니다. 이력서의 GitHub 링크를 누른 사람이 처음 보는 화면입니다.

- **프로필 README:** 한 줄 소개, 대표 프로젝트 3개(한 줄 설명 + 핵심 수치 + 링크), 블로그 글, 기술 스택.
- **대표 저장소 고정(pin):** 수십 개 저장소 중 보여주고 싶은 것을 맨 위에.
- **각 저장소 정리:** 설명 한 줄, 토픽 태그, 데모 링크.
- **의미 있는 커밋 메시지:** 면접관이 커밋 이력을 볼 수 있습니다. "수정", "asdf"만 가득하면 인상이 나빠집니다. "Add hybrid search with RRF (Recall@5 0.62 → 0.81)"처럼 무엇을 왜 바꿨는지 쓰세요.

준비 방법: 이 코스의 "더 읽기"에서 두세 개를 골라 **요지 한 문장, 내 프로젝트에 적용한 것 또는 적용하지 않은 이유, 동의하지 않는 부분**을 정리해둡니다. 예: Anthropic의 멀티 에이전트 리서치 글과 Cognition의 "Don't build multi-agents"를 함께 읽고, 내 리서치 에이전트는 하위 작업이 독립적이라 전자가 맞았지만 코드 수정 에이전트였다면 후자의 지적처럼 단일 에이전트가 나았을 것이라고 말하면 좋습니다.
</details>

<details>
<summary>빠르게 변하는 AI 생태계를 어떻게 따라가나요?</summary>

공식 엔지니어링 블로그(공급자, 주요 프레임워크), 스펙 저장소의 변경 사항(MCP 등), 컨퍼런스 영상, 소수의 신뢰하는 실무자 글을 정기적으로 봅니다. 새 도구는 이름이 아니라 "어떤 문제를 어떤 트레이드오프로 푸는가"로 이해하고, 내 평가 세트로 직접 확인해 채택 여부를 정합니다. 패턴(컨텍스트 관리, 평가, 권한 설계)은 도구보다 오래가므로 거기에 시간을 더 씁니다.
</details>
