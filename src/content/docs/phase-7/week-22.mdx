## 채용 담당자는 무엇을 보는가

신입 대상 AI 엔지니어 공고는 6% 남짓입니다. 대부분의 공고가 경력자를 찾으니, 경력자와 경쟁하려면 포트폴리오가 **"이 사람은 실제 서비스를 운영할 수 있다"**는 증거가 되어야 합니다.

채용 담당자와 면접관은 바쁩니다. 포트폴리오 하나에 몇 분 쓰지 않습니다. 그 몇 분 안에 눈에 들어와야 할 것을 중요한 순서대로 나열하면 이렇습니다.

1. **측정된 결과:** "정답률 87%(50문항, 95% 신뢰구간 75~94%), 요청당 $0.011, p95 6.2초". 숫자, 그리고 그 숫자를 어떻게 쟀는지(14주차)가 함께 있으면 "이 사람은 측정할 줄 안다"는 신호가 됩니다.
2. **실패와 개선의 기록:** "하이브리드 검색으로 Recall@5 0.62 → 0.81, 제품 코드 질문에서 효과가 컸다". 처음부터 잘 된 프로젝트보다, 문제를 발견하고 고친 과정이 실력을 더 잘 보여줍니다.
3. **설계 근거:** "멀티 에이전트를 쓴 이유와, 일부러 쓰지 않은 부분". 기술을 아는 것보다 **언제 쓰고 언제 안 쓰는지** 아는 게 시니어의 표시입니다.
4. **운영 요소:** 평가 CI, 트레이싱, 보안 테스트, 비용 통제, 중단 후 재개. 데모와 서비스를 가르는 부분입니다(14~21주차).
5. **동작하는 데모:** 공개 URL 또는 영상.

"LangGraph로 멀티 에이전트 챗봇을 만들었습니다"만 있는 포트폴리오는 수백 개입니다. 같은 기술을 썼어도 위 1~4가 있으면 완전히 다르게 보입니다.

## 핵심 작업

### 1. 대표 프로젝트 고르기

[포트폴리오 프로젝트](../../projects/overview/) 5개 중 **1번(Report Generation Agent)과 5번(평가·관측 파이프라인)은 필수**입니다. 1번은 에이전트 설계·멀티 에이전트·신뢰성을, 5번은 이 코스에서 가장 중요한 평가 역량을 보여줍니다. 나머지 하나는 지원할 회사의 도메인에 맞춰 고릅니다.

- 커머스·고객센터 → 2번 (RAG CS 챗봇)
- B2B SaaS·사내 자동화 → 3번 (MCP 업무 자동화)
- 데이터 조직 → 4번 (Text2SQL / GraphRAG)

### 2. 아키텍처 다이어그램

화려할 필요 없이 박스와 화살표 수준이면 충분합니다. 중요한 것은 그림에서 다음 네 가지가 보이는 것입니다.

- **데이터 흐름:** 요청이 어디로 들어와서 어디를 거쳐 나가는지
- **상태 저장 위치:** 체크포인트, 대화, 벡터 DB가 어디 있는지
- **신뢰 경계:** 외부 콘텐츠(웹, 업로드)가 들어오는 곳 (17주차)
- **사람 승인 지점:** 어디서 사람이 개입하는지 (18주차)

Mermaid로 저장소에 텍스트로 넣어두면 수정하기 쉽고, GitHub이 그림으로 그려줍니다.

### 3. 데모 영상 (2~3분)

라이브 데모는 서버가 꺼지거나 API 키가 만료되면 안 열립니다. 영상은 항상 볼 수 있습니다. 구성은 이렇게 잡습니다.

1. 문제와 사용자 (15초): "누가 어떤 불편을 겪는가"
2. 실제 사용 장면 (60초): 입력 → 진행 이벤트가 흘러나오는 화면 → 결과
3. 내부 동작 (30초): 트레이스 화면에서 에이전트가 무슨 도구를 어떤 순서로 썼는지
4. 평가 결과 (30초): 리포트와 핵심 수치
5. 가장 어려웠던 설계 결정 하나 (15초)

### 4. 코드 정리

- **비밀이 커밋 이력에 없는지 확인:** 지금 파일에서 지웠어도 예전 커밋에 API 키가 남아 있으면 누구나 볼 수 있습니다. `git log -p | grep -i "sk-"`나 gitleaks 같은 도구로 이력 전체를 검사합니다. 발견되면 그 키는 즉시 폐기하고 새로 발급합니다.
- `docker compose up` 한 줄로 실행되게, `.env.example`(키 이름만 있고 값은 빈 예시 파일) 제공.
- 테스트와 평가가 CI에서 초록색.
- 실습 주차 폴더(`weeks/`)는 별도 저장소로 분리하거나 정리해서, 대표 프로젝트가 연습 코드 사이에 묻히지 않게 합니다.
