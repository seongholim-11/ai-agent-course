## 학습 목표

- 에이전트 관측이 일반 서비스 모니터링과 다른 점을 설명한다
- trace, span, generation, session 개념으로 에이전트 실행을 기록한다
- Langfuse(또는 LangSmith)를 붙이고 OpenTelemetry GenAI 규칙을 이해한다
- 트레이스로 가장 느린 단계, 가장 비싼 단계, 가장 자주 실패하는 단계를 찾는다

## 왜 에이전트에는 특별한 관측이 필요한가

**관측(observability)**은 "시스템 안에서 무슨 일이 일어났는지를 밖에서 알아볼 수 있게 기록하는 것"입니다. 14주차 평가가 "미리 만든 시험지로 실력 측정"이라면, 관측은 "실제 근무 중의 업무 일지와 CCTV"입니다.

일반 웹 서비스는 "요청이 왔고, 200으로 응답했고, 0.1초 걸렸다" 정도로 충분합니다. 같은 요청은 같은 코드 경로를 지나기 때문입니다. 에이전트는 다릅니다.

- **같은 요청도 매번 다른 경로**로 실행됩니다. 어떤 때는 도구 2번, 어떤 때는 7번.
- **HTTP 200이어도 답이 틀릴 수 있습니다.** 서버 입장에서는 성공인데 고객 입장에서는 실패입니다.

그래서 "왜 이 답이 나왔나"를 알려면 각 LLM 호출의 입력과 출력, 도구 호출과 그 결과, 의사결정 순서가 모두 기록되어 있어야 합니다. 블랙박스 없는 비행기 사고 조사가 불가능한 것과 같습니다. LangChain 조사에서 프로덕션 에이전트를 운영하는 팀의 94%가 관측 도구를 쓰고 71.5%가 상세 트레이싱을 한다고 답했습니다. 사실상 필수입니다.

## 핵심 개념

### 1. 데이터 모델

에이전트 실행 기록은 나무(트리) 구조로 저장합니다.

```
Session (사용자 대화 전체, session_id)                     ← 대화 한 통
└─ Trace (요청 하나: "환불해줘")                        8.2s  $0.012     ← 질문 하나에 대한 처리 전체
   ├─ Span: classify                                   0.6s                ← 그 안의 한 단계
   │   └─ Generation: claude-haiku (in 820 / out 12)    0.6s  $0.0009     ← LLM 호출 한 번
   ├─ Span: agent_loop
   │   ├─ Generation: turn 1 (tool_use: get_order)     1.1s
   │   ├─ Span: tool get_order                         0.3s
   │   ├─ Generation: turn 2 (tool_use: check_policy)  1.4s
   │   ├─ Span: tool check_policy                      2.9s  ← 병목 (가장 오래 걸림)
   │   └─ Generation: turn 3 (final)                   1.9s
   └─ Score: judge.accuracy = PASS, user_feedback = 👍  ← 이 처리에 대한 평가
```

- **Trace:** 요청 하나에 대한 처리 전체. 택배 하나의 전체 배송 기록입니다.
- **Span:** 그 안의 시간이 걸리는 작업 단위(노드, 도구 실행). 배송 기록의 "물류센터 도착", "배송 출발" 같은 구간입니다.
- **Generation:** LLM 호출을 기록하는 특별한 span. 모델명, 입력·출력, 토큰, 비용, TTFT를 담습니다.
- **Session:** 같은 대화에 속한 여러 trace를 묶습니다.
- **Score:** trace에 붙는 평가 결과(자동 judge 점수, 사용자의 👍/👎, 사람 라벨).
- **메타데이터:** user_id, 버전(프롬프트·모델·코드), 환경, 실험 ID를 **꼭** 붙입니다. 나중에 "프롬프트 v3부터 비용이 늘었다"를 찾아내려면 각 기록이 어느 버전에서 나왔는지 알아야 하기 때문입니다.

### 2. Langfuse 붙이기

**Langfuse**는 LLM 앱 전용 관측 도구(오픈소스)입니다. 코드에 데코레이터를 붙이면 위 트리 구조로 기록이 쌓입니다.

```python
from langfuse import observe, get_client

langfuse = get_client()         # 환경 변수의 LANGFUSE_* 키로 서버에 연결

@observe()                      # 이 함수가 호출될 때마다 span 하나로 기록된다 (입력·출력·시간 자동)
async def get_order(order_id: str): ...

@observe(as_type="generation")  # LLM 호출임을 표시 → 토큰·비용 칸이 생긴다
async def call_llm(messages, model):
    resp = await client.messages.create(model=model, messages=messages, max_tokens=1024)
    # 지금 기록 중인 generation에 모델·입출력·사용량을 채워 넣는다 → 비용이 자동 계산된다
    langfuse.update_current_generation(
        model=model, input=messages, output=resp.content,
        usage_details={"input": resp.usage.input_tokens, "output": resp.usage.output_tokens},
    )
    return resp

@observe()                      # 가장 바깥 함수 = trace 하나. 안에서 부른 @observe 함수들이 자식 span이 된다
async def handle(user_id: str, session_id: str, msg: str):
    # trace에 "누가, 어느 대화에서, 어느 버전으로" 실행했는지 붙인다 → 나중에 필터·비교의 기준
    langfuse.update_current_trace(user_id=user_id, session_id=session_id,
                                  tags=["refund"], metadata={"prompt_version": "v3", "git_sha": GIT_SHA})
    ...
```

LangGraph·LangChain은 콜백 핸들러 하나만 넘기면, OpenAI·Anthropic SDK는 계측 래퍼로 감싸면 자동으로 기록됩니다. 자체 호스팅은 docker compose로 띄웁니다.

### 3. OpenTelemetry GenAI 규칙

**OpenTelemetry(OTel)**는 서비스의 실행 기록(트레이스, 지표, 로그)을 남기는 업계 표준입니다. 여기에 생성형 AI용 **시맨틱 규칙**(semantic conventions, 속성 이름 표준)이 있어서 `gen_ai.request.model`(요청 모델), `gen_ai.usage.input_tokens`(입력 토큰), `gen_ai.operation.name`(chat, execute_tool, invoke_agent) 같은 이름을 정해두었습니다.

이게 왜 중요할까요? 모두가 같은 이름표를 쓰면 기록을 Langfuse, Datadog, Grafana 등 **어느 도구로 보내도 똑같이 읽힙니다.** 나중에 관측 도구를 바꿔도 계측 코드를 다시 짤 필요가 없습니다(벤더 종속 회피). 회사에 이미 OTel 기반 모니터링이 있다면, 에이전트 기록도 같은 파이프라인에 태우는 것이 운영상 유리합니다. 에이전트 호출이 뒤쪽 마이크로서비스·DB 호출까지 하나의 trace로 이어지기 때문입니다.

### 4. 대시보드에 둘 것

| 범주 | 지표 |
| --- | --- |
| 비용 | 요청당 비용 p50/p95, 일 총비용, 모델별·기능별 비용, 캐시 적중률 |
| 지연 | 엔드투엔드 p50/p95/p99, TTFT, 턴 수 분포, 도구별 지연 |
| 신뢰성 | 에러율(LLM API, 도구), 재시도율, 타임아웃, 최대 턴 도달 비율 |
| 품질 | 온라인 judge 점수 추이, 사용자 피드백, 거절률, 사람 이관률 |
| 행동 | 도구 호출 빈도, 반복 루프 감지 수, 평균 컨텍스트 길이 |

**p50, p95**는 백분위수입니다. p50은 100개 요청을 빠른 순으로 세웠을 때 50번째(중간값), p95는 95번째 값입니다. "대부분은 이 정도"(p50)와 "느린 쪽은 이 정도"(p95)를 함께 봅니다.

평균이나 p50만 보면 안 됩니다. 에이전트는 **긴 꼬리**가 심해서, 대부분은 5초에 끝나는데 일부는 50초 걸리는 식으로 p95가 p50의 5~10배인 경우가 흔합니다. 비용 폭주도 이 꼬리에서 일어납니다(루프에 빠진 요청 하나가 수백 턴을 도는 식).

## 심화

### 트레이스로 병목 찾기

1. 지연 상위 5% 트레이스(가장 느린 것들)를 모은다.
2. 각 트레이스에서 시간을 가장 많이 쓴 span을 집계한다. "느린 요청의 70%에서 check_policy가 가장 오래 걸렸다" 같은 결론이 나온다.
3. 흔한 원인과 처방:
   - 서로 독립인 도구를 순서대로 부름 → 병렬화 (1주차, 4주차)
   - 느린 외부 API → 캐시, 타임아웃
   - 불필요한 턴 → 프롬프트·도구 설계 개선
   - 컨텍스트가 길어져 TTFT 증가 → 11주차 컨텍스트 전략
   - 큰 모델이 필요 없는 단계에 큰 모델 사용 → 19주차 라우팅

### 개인정보와 로그

트레이스에는 사용자가 입력한 내용과 도구 결과(고객 주소, 주문 내역)가 그대로 담깁니다. 디버깅에는 좋지만 개인정보 덩어리이기도 합니다. 그래서 다음을 정해야 합니다.

- **마스킹:** 이메일, 전화번호, 주민번호 패턴을 기록 전에 `<EMAIL>`처럼 가린다
- **보존 기간:** 30일 뒤 자동 삭제 등
- **접근 권한:** 누가 원본 기록을 볼 수 있는지
- **샘플링:** 전부가 아니라 일부만 기록

외부 관측 서비스에 데이터를 보내는 것 자체가 법적으로 **개인정보 처리 위탁**에 해당할 수 있다는 점도 기억하세요.

### 샘플링 전략

트래픽이 많으면 모든 트레이스를 저장하기 비쌉니다. 그렇다고 무작위로 1%만 남기면 정작 중요한 실패 기록을 놓칩니다. 그래서 **에러·느린 요청·낮은 점수·부정 피드백은 100% 저장**하고, 정상 요청은 일정 비율로만 샘플링합니다. 요청이 끝난 뒤 결과를 보고 저장 여부를 정하므로 tail-based sampling이라고 합니다. 블랙박스가 사고 직전 영상은 반드시 보존하는 것과 같습니다.

### 관측에서 평가로

관측 데이터는 16주차 개선 루프의 원료입니다. 👎가 붙었거나 judge 점수가 낮은 트레이스를 모아 사람이 검토하고, 대표 사례를 14주차 평가 세트에 추가합니다. 실제 사용자가 겪은 실패가 시험지에 들어가니 평가 세트가 점점 현실을 닮아갑니다. 관측 도구 대부분이 이 "트레이스 → 데이터셋" 기능을 제공합니다.

## 실습 과제

`weeks/w15_observability/`

**요구사항**

1. Langfuse를 docker compose로 자체 호스팅(또는 클라우드 무료 플랜)한다.
2. 7주차 환불 에이전트 또는 8주차 리서치 에이전트 전체를 계측한다: 모든 LLM 호출, 도구 호출, 노드에 span. user_id, session_id, 버전 메타데이터.
3. 이메일·전화번호 마스킹을 트레이스 전송 전에 적용한다.
4. 14주차 평가 세트 50개를 돌려 트레이스를 쌓고, 비용·지연·도구 사용 대시보드를 만든다.
5. 트레이스 분석으로 가장 느린 단계를 찾아 개선하고(병렬화, 타임아웃, 캐시 등) 전후 p95를 비교한다.
6. 평가 세트 judge 점수를 트레이스에 Score로 붙인다.

**채점 기준**

- [ ] 트레이스 하나를 열면 모든 도구 호출의 입력·출력·지연이 보인다
- [ ] 마스킹이 적용되어 원본 이메일이 트레이스에 없다
- [ ] 개선 전후 p95 지연 비교가 있다

## 면접 질문

<details>
<summary>프로덕션 에이전트에서 무엇을 모니터링하나요?</summary>

비용(요청당 p50·p95, 모델·기능별, 캐시 적중률), 지연(엔드투엔드 p50·p95·p99, TTFT, 턴 수, 도구별), 신뢰성(LLM·도구 에러율, 재시도, 타임아웃, 최대 턴 도달), 품질(온라인 judge 점수, 사용자 피드백, 거절률, 사람 이관률), 행동(도구 호출 패턴, 반복 루프, 컨텍스트 길이)입니다. 이를 트레이스 단위로 기록해 개별 실패를 추적할 수 있어야 하고, 프롬프트·모델·코드 버전을 메타데이터로 붙여 변경의 영향을 볼 수 있어야 합니다.
</details>

<details>
<summary>에이전트가 이상한 답을 했다는 신고가 오면 어떻게 조사하나요?</summary>

해당 요청의 트레이스를 찾아 각 단계의 입력과 출력을 따라갑니다. 검색이나 도구가 잘못된 정보를 줬는지, 모델이 올바른 정보를 받고도 잘못 해석했는지, 도구를 잘못된 인자로 불렀는지, 컨텍스트가 너무 길어 지시를 놓쳤는지를 구분합니다. 원인을 분류한 뒤 같은 유형의 다른 트레이스가 있는지 검색해 빈도를 확인하고, 사례를 평가 세트에 추가한 뒤 수정하고 회귀 테스트를 돌립니다.
</details>

<details>
<summary>OpenTelemetry를 에이전트 관측에 쓰는 이점은?</summary>

GenAI 시맨틱 규칙으로 모델, 토큰, 도구 실행, 에이전트 호출 같은 속성 이름이 표준화되어 있어, 특정 관측 벤더에 종속되지 않고 여러 백엔드로 같은 데이터를 보낼 수 있습니다. 또한 기존 서비스의 분산 트레이싱과 같은 트레이스 ID로 연결되어, 에이전트 호출이 하위 마이크로서비스·DB까지 어떻게 이어지는지 한 화면에서 볼 수 있습니다.
</details>
