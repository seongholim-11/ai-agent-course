## 학습 목표

- 프롬프트·모델·도구 변경을 코드 변경처럼 CI에서 평가한다
- 회귀(regression) 기준을 정하고 자동으로 막는다
- 프로덕션 데이터 → 오류 분석 → 평가 세트 → 수정 → 배포의 개선 루프를 운영한다
- 온라인 A/B 테스트를 설계하고 결과를 해석한다

## 개선 루프

```
   ┌──────────── 프로덕션 트레이스 + 피드백 ◀───────────┐
   ▼                                                  │
 샘플링·필터 (부정 피드백, 낮은 점수, 에러)              │
   ▼                                                  │
 오류 분석 (읽고 분류, 상위 실패 유형 선정)             │
   ▼                                                  │
 평가 세트에 대표 사례 추가                            │
   ▼                                                  │
 수정 (프롬프트, 도구, 검색, 모델, 코드)               │
   ▼                                                  │
 CI 오프라인 평가 (회귀 없음 확인) ──▶ 점진 배포·A/B ───┘
```

이 루프를 **주 단위로** 돌리는 팀이 품질을 꾸준히 올립니다. 모델을 바꾸거나 프롬프트를 고칠 때 "느낌상 나아졌다"가 아니라 숫자로 판단하게 됩니다.

## 핵심 개념

### 1. 무엇이 바뀌면 평가를 돌리나

프롬프트, 모델(버전 포함), 도구 설명·스키마, 검색 설정(청킹, 리랭커), 그래프 구조, 의존 라이브러리. 즉 **에이전트 동작에 영향을 주는 모든 것**입니다. 프롬프트를 코드 저장소에서 버전 관리하는 이유입니다.

### 2. CI에 평가 넣기

```yaml
# .github/workflows/eval.yml
name: agent-eval
on:
  pull_request:
    paths: ["agents/**", "prompts/**", "tools/**", "evals/**"]
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv run evals/run.py --suite smoke --repeats 2 --out report.json
        env: { ANTHROPIC_API_KEY: "${{ secrets.ANTHROPIC_API_KEY }}" }
      - run: uv run evals/compare.py --base main --head report.json --fail-on-regression
      - uses: marocchino/sticky-pull-request-comment@v2
        with: { path: report.md }
```

- **스위트 계층화:** PR마다 빠른 smoke(20~30개, 수 분), 머지 전·야간에 full(전체, 반복 실행).
- **비용 통제:** 작은 모델로 judge, 캐싱, 변경된 영역 관련 항목만 실행.
- **PR 코멘트:** 기준 대비 점수·비용·지연 변화와 새로 실패한 항목 목록을 보여줍니다.

### 3. 회귀 판정 규칙

비결정성 때문에 "1%p라도 떨어지면 실패"는 노이즈로 계속 깨집니다.

- **핵심 항목(must-pass):** 안전·정책 관련 항목은 하나라도 실패하면 막습니다.
- **전체 점수:** 신뢰구간이 겹치지 않을 정도로 떨어지면 막거나, 임계값(예: -5%p)을 둡니다.
- **비용·지연 예산:** 요청당 비용 +20% 이상, p95 +30% 이상이면 경고.
- **새로 실패한 항목 목록:** 점수가 같아도 다른 항목이 깨졌을 수 있습니다. 항목 단위 비교가 중요합니다.

### 4. 온라인 평가

- **자동 judge 샘플링:** 프로덕션 응답의 일부(예: 5%)에 judge를 돌려 점수 추이를 봅니다.
- **암묵적 신호:** 재질문, 같은 질문 반복, 사람 상담 요청, 대화 이탈, 복사 버튼 클릭.
- **명시적 신호:** 👍/👎, 별점. 응답률이 낮고 편향되어(불만족한 사람이 더 누름) 단독으로 쓰기 어렵습니다.

### 5. A/B 테스트

1. **가설과 1차 지표**를 미리 정한다(예: "새 프롬프트는 해결률을 올린다", 1차 지표: 사람 이관 없이 끝난 대화 비율).
2. **가드레일 지표:** 비용, 지연, 안전 위반은 나빠지면 안 됨.
3. 사용자 단위로 무작위 배정(같은 사용자가 두 버전을 오가지 않게).
4. 필요한 표본 크기를 사전에 계산하고, 중간에 몰래 보고 멈추지 않는다(peeking).
5. 그림자 모드(shadow): 새 버전을 사용자에게 보여주지 않고 병렬로 돌려 오프라인 비교만 하는 방법도 있습니다. 부수효과 있는 도구는 가짜로 바꿔야 합니다.

## 심화

### 오류 분석을 루틴으로

매주 30~50개 실패 트레이스를 직접 읽고 분류합니다. 처음엔 자유롭게 메모하고(open coding), 비슷한 것을 묶어 범주를 만들고(axial coding), 범주별 빈도를 셉니다. **가장 흔한 실패 유형 하나를 고치는 것**이 막연한 프롬프트 수정보다 훨씬 효과적입니다. 이 과정은 위임하기 어렵습니다. 제품을 이해하는 사람이 직접 읽어야 합니다.

### 모델 교체 절차

새 모델이 나오면:

1. full 스위트를 반복 실행해 점수·비용·지연을 비교한다.
2. 항목 단위로 새로 실패한 것과 새로 성공한 것을 읽는다. 모델마다 프롬프트 민감도가 달라서 **프롬프트를 조금 고쳐야** 제 성능이 나오는 경우가 많다.
3. 비용이 더 싼 모델이 품질을 유지한다면 라우팅(19주차)에 넣는다.
4. 그림자 모드 → 소량 트래픽 → 전체 순서로 바꾼다.

### 데이터 플라이휠

좋은 평가 세트와 라벨링된 트레이스는 시간이 지날수록 쌓이는 **경쟁력**입니다. 나중에 파인튜닝, 라우터 학습, few-shot 예시 선택에 그대로 쓰입니다. 그래서 라벨에 기준·작성자·날짜를 남겨 품질을 관리합니다.

## 실습 과제: 자동 회귀 평가 파이프라인 (Phase 4 완료 과제)

`.github/workflows/eval.yml` + `evals/`

**요구사항**

1. 14주차 평가 하네스를 CI에 넣는다. PR마다 smoke(20개×2회), main 머지 시 full(50개×3회).
2. `compare.py`: 기준(main 최신 결과) 대비 점수·비용·지연 변화, 새로 실패한 항목, must-pass 위반을 계산하고 마크다운 리포트를 생성한다.
3. must-pass 위반이나 임계값 초과 시 CI 실패.
4. PR에 리포트를 코멘트로 남긴다.
5. 실험: 의도적으로 나쁜 프롬프트 변경(예: 정책 문장 삭제)을 PR로 올려 CI가 막는지 확인한다.
6. 실험: 모델을 다른 것으로 바꾼 PR을 올려 점수·비용 비교 리포트를 받는다.
7. 15주차 트레이스에서 낮은 점수 10개를 골라 오류 분석 후 평가 세트에 추가하는 스크립트를 만든다.

**채점 기준**

- [ ] 나쁜 프롬프트 PR이 CI에서 실패한다
- [ ] 모델 교체 PR 리포트에 점수·비용·지연 변화와 신뢰구간이 있다
- [ ] 평가 세트에 프로덕션(또는 시뮬레이션) 유래 항목이 추가되었다

## 면접 질문

<details>
<summary>프롬프트를 바꿀 때 품질이 떨어지지 않았는지 어떻게 확인하나요?</summary>

프롬프트를 코드처럼 버전 관리하고, 변경 PR마다 평가 세트로 CI에서 자동 평가합니다. 각 항목을 여러 번 실행해 기준 버전과 점수·비용·지연을 비교하고, 안전·정책 관련 필수 항목이 하나라도 깨지면 막습니다. 전체 점수는 신뢰구간이나 임계값으로 판단하고, 항목 단위로 새로 실패한 사례를 읽어 확인합니다. 머지 후에는 점진 배포와 온라인 지표로 다시 확인합니다.
</details>

<details>
<summary>새 모델이 나왔을 때 교체 여부를 어떻게 결정하나요?</summary>

전체 평가 세트를 반복 실행해 품질, 비용, 지연, 일관성(pass^k)을 기존 모델과 비교하고, 항목 단위로 새로 실패·성공한 사례를 읽습니다. 모델마다 프롬프트 반응이 달라 약간의 프롬프트 조정 후 다시 비교합니다. 품질이 같고 싸면 일부 경로부터 라우팅하고, 그림자 모드나 소량 트래픽 A/B로 온라인 지표를 확인한 뒤 전환합니다. 벤치마크 점수만 보고 바꾸지 않습니다.
</details>

<details>
<summary>에이전트 A/B 테스트에서 주의할 점은?</summary>

1차 지표와 가드레일 지표(비용, 지연, 안전)를 사전에 정하고, 사용자 단위로 무작위 배정하며, 필요한 표본 크기를 미리 계산해 중간에 결과를 보고 멈추지 않습니다. 에이전트는 결과 분산이 커서 표본이 더 필요할 수 있고, 명시적 피드백은 응답 편향이 있어 해결률·이관률 같은 행동 지표를 함께 봅니다. 부수효과 있는 기능은 그림자 모드로 먼저 검증합니다.
</details>
