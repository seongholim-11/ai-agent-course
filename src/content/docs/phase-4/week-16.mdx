원본 강의 범위 밖입니다. 14~15주차 결과물을 이어서 씁니다.
</Aside>

## 학습 목표

- 프롬프트·모델·도구 변경을 코드 변경처럼 CI에서 평가한다
- 회귀(regression) 기준을 정하고 자동으로 막는다
- 프로덕션 데이터 → 오류 분석 → 평가 세트 → 수정 → 배포의 개선 루프를 운영한다
- 온라인 A/B 테스트를 설계하고 결과를 해석한다

## 개선 루프

14주차에서 시험지(평가 세트)를, 15주차에서 업무 일지(트레이스)를 만들었습니다. 이번 주는 둘을 이어서 **품질이 계속 좋아지는 순환 구조**를 만듭니다. 운동선수가 경기 영상을 보고(관측) → 약점을 찾고(오류 분석) → 그 약점을 훈련 메뉴에 넣고(평가 세트 추가) → 훈련하고(수정) → 연습 경기로 확인하고(CI 평가) → 실전에 나가는(배포) 것과 같습니다.

```
   ┌──────────── 프로덕션 트레이스 + 피드백 ◀───────────┐
   ▼                                                  │
 샘플링·필터 (부정 피드백, 낮은 점수, 에러)              │
   ▼                                                  │
 오류 분석 (읽고 분류, 상위 실패 유형 선정)             │
   ▼                                                  │
 평가 세트에 대표 사례 추가                            │
   ▼                                                  │
 수정 (프롬프트, 도구, 검색, 모델, 코드)               │
   ▼                                                  │
 CI 오프라인 평가 (회귀 없음 확인) ──▶ 점진 배포·A/B ───┘
```

이 루프를 **주 단위로** 돌리는 팀이 품질을 꾸준히 올립니다. 모델을 바꾸거나 프롬프트를 고칠 때 "느낌상 나아졌다"가 아니라 숫자로 판단하게 됩니다.

## 핵심 개념

### 1. 무엇이 바뀌면 평가를 돌리나

**회귀(regression)**는 "고치다가 원래 잘 되던 것이 망가지는 것"입니다. 환불 질문을 개선하려고 프롬프트를 고쳤더니 배송 질문 답이 이상해지는 식입니다.

에이전트에서는 회귀가 생각보다 다양한 곳에서 생깁니다. 프롬프트, 모델(같은 이름이라도 버전 포함), 도구 설명·스키마, 검색 설정(청킹, 리랭커), 그래프 구조, 의존 라이브러리… 즉 **에이전트 동작에 영향을 주는 모든 것**이 바뀔 때마다 평가를 돌려야 합니다. 프롬프트를 코드 저장소에 넣고 코드처럼 버전 관리하는 이유가 이것입니다. 그래야 "프롬프트 변경"도 PR이 되고, PR마다 자동 평가를 붙일 수 있습니다.

### 2. CI에 평가 넣기

**CI(Continuous Integration)**는 코드를 올릴 때마다 자동으로 테스트를 돌려주는 시스템입니다. 여기에 일반 테스트뿐 아니라 **에이전트 평가**를 넣습니다.

```yaml
# .github/workflows/eval.yml
name: agent-eval
on:
  pull_request:
    # 에이전트 동작에 영향을 주는 파일이 바뀐 PR에서만 실행한다 (README 수정에 돈을 쓰지 않게)
    paths: ["agents/**", "prompts/**", "tools/**", "evals/**"]
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      # 빠른 smoke 세트를 2번씩 돌려 결과를 report.json에 저장 (API 키는 저장소 비밀값에서)
      - run: uv run evals/run.py --suite smoke --repeats 2 --out report.json
        env: { ANTHROPIC_API_KEY: "${{ secrets.ANTHROPIC_API_KEY }}" }
      # main 브랜치의 최신 결과와 비교해서, 회귀가 있으면 이 단계가 실패 → PR 머지가 막힌다
      - run: uv run evals/compare.py --base main --head report.json --fail-on-regression
      # 비교 리포트를 PR에 코멘트로 남긴다 (다시 돌리면 같은 코멘트를 갱신)
      - uses: marocchino/sticky-pull-request-comment@v2
        with: { path: report.md }
```

- **스위트 계층화:** PR마다는 빠른 smoke 세트(20~30개, 수 분)만, 머지 전·야간에는 full 세트(전체, 반복 실행)를 돌립니다. 매 PR에 전체를 돌리면 너무 느리고 비쌉니다.
- **비용 통제:** judge는 작은 모델로, 캐싱 활용, 바뀐 영역과 관련된 항목만 실행.
- **PR 코멘트:** 기준 대비 점수·비용·지연 변화와 새로 실패한 항목 목록을 보여줘서, 리뷰어가 숫자를 보고 판단하게 합니다.

### 3. 회귀 판정 규칙

"점수가 1%p라도 떨어지면 실패"로 하면, 14주차에서 본 비결정성 때문에 아무것도 안 바꿔도 CI가 계속 빨간불이 됩니다. 자꾸 울리는 화재경보기는 결국 아무도 신경 쓰지 않게 됩니다. 그래서 규칙을 나눕니다.

- **핵심 항목(must-pass):** 안전·정책 관련 항목(승인 없는 환불 금지, 개인정보 노출 금지)은 **하나라도 실패하면** 막습니다. 여기엔 관용이 없습니다.
- **전체 점수:** 신뢰구간이 겹치지 않을 정도로 확실히 떨어졌을 때만 막거나, 임계값(예: -5%p)을 둡니다. 노이즈로 생긴 작은 흔들림은 통과시킵니다.
- **비용·지연 예산:** 요청당 비용이 20% 이상, p95 지연이 30% 이상 늘면 경고합니다. 품질은 같은데 비용이 두 배가 된 변경도 문제입니다.
- **새로 실패한 항목 목록:** 전체 점수가 같아도 내용이 바뀌었을 수 있습니다. A 문제 3개가 새로 맞고 B 문제 3개가 새로 틀리면 점수는 같지만, B가 중요한 문제라면 큰일입니다. **항목 단위 비교**가 중요합니다.

### 4. 온라인 평가

배포 후 실제 사용 중에 품질을 재는 방법입니다.

- **자동 judge 샘플링:** 실제 응답의 일부(예: 5%)에 judge를 돌려 점수 추이를 봅니다. 점수가 떨어지기 시작하면 알람.
- **암묵적 신호:** 사용자가 말하지 않아도 행동으로 드러나는 불만. 같은 질문 다시 하기, 표현을 바꿔 재질문, "상담원 연결해주세요", 대화 중간 이탈. 반대로 답변 복사 버튼 클릭은 만족 신호.
- **명시적 신호:** 👍/👎, 별점. 누르는 사람이 적고, 불만족한 사람이 더 많이 누르는 경향(편향)이 있어서 이것만 보면 왜곡됩니다. 암묵적 신호와 함께 봅니다.

### 5. A/B 테스트

**A/B 테스트**는 사용자를 무작위로 두 그룹으로 나눠, A 그룹에는 기존 버전을, B 그룹에는 새 버전을 보여주고 결과를 비교하는 실험입니다. 신약 임상시험에서 약을 받는 그룹과 가짜 약을 받는 그룹을 나누는 것과 같습니다.

1. **가설과 1차 지표를 미리 정한다.** 예: "새 프롬프트는 해결률을 올린다", 1차 지표: 사람 이관 없이 끝난 대화 비율. 실험 후에 좋아 보이는 지표를 골라 보고하면 안 됩니다.
2. **가드레일 지표**를 정한다. 비용, 지연, 안전 위반처럼 "1차 지표가 좋아져도 이건 나빠지면 안 되는" 지표.
3. **사용자 단위로 무작위 배정**한다. 같은 사용자가 대화마다 A와 B를 오가면 경험이 섞여 결과를 해석할 수 없습니다.
4. **필요한 표본 크기를 미리 계산**하고, 중간에 결과를 몰래 보다가 좋아 보일 때 멈추지 않는다(peeking 금지). 동전을 던지다가 앞면이 많이 나온 순간에 멈추고 "이 동전은 앞면이 잘 나온다"고 하는 것과 같은 오류입니다.
5. **그림자 모드(shadow):** 새 버전을 사용자에게 보여주지 않고 뒤에서 같은 요청으로 함께 돌려 결과만 비교하는 방법도 있습니다. 위험 없이 실제 트래픽으로 시험할 수 있습니다. 단, 메일 발송 같은 부수효과 있는 도구는 가짜로 바꿔야 합니다.

## 심화

### 오류 분석을 루틴으로

매주 실패 트레이스 30~50개를 직접 읽고 분류합니다(14주차 방법). 처음엔 사례마다 자유롭게 메모하고(open coding), 비슷한 것끼리 묶어 범주를 만들고(axial coding), 범주별 개수를 셉니다.

**가장 흔한 실패 유형 하나를 고치는 것**이 막연히 프롬프트를 다듬는 것보다 훨씬 효과적입니다. "전체 실패의 40%가 날짜 계산 오류"라는 걸 알면, 날짜 계산 도구 하나를 추가하는 것만으로 큰 개선이 됩니다.

이 과정은 남에게 맡기기 어렵습니다. 제품과 사용자를 이해하는 사람이 직접 읽어야 "이게 왜 실패인지"를 판단할 수 있기 때문입니다.

### 모델 교체 절차

새 모델이 나오면 벤치마크 점수만 보고 바꾸고 싶어집니다. 안전한 절차는 이렇습니다.

1. full 세트를 반복 실행해 점수·비용·지연을 비교한다.
2. 항목 단위로 새로 틀린 것과 새로 맞은 것을 직접 읽는다. 모델마다 같은 프롬프트에 대한 반응이 달라서, **프롬프트를 조금 고쳐야** 새 모델이 제 성능을 내는 경우가 많다.
3. 더 싼 모델이 품질을 유지한다면 전체 교체가 아니라 일부 경로에 라우팅한다(19주차).
4. 그림자 모드 → 소량 트래픽 → 전체 순서로 바꾼다. 문제가 생기면 바로 되돌릴 수 있게.

### 데이터 플라이휠

**플라이휠**은 한 번 돌기 시작하면 관성으로 점점 빨라지는 바퀴입니다. 좋은 평가 세트와 라벨이 붙은 트레이스는 시간이 지날수록 쌓이고, 쌓일수록 개선이 빨라지는 **경쟁력**이 됩니다. 나중에 파인튜닝, 라우터 학습, few-shot 예시 선택에 그대로 쓰입니다. 경쟁사가 같은 모델을 써도 이 데이터는 따라 할 수 없습니다. 그래서 라벨에는 기준·작성자·날짜를 남겨 품질을 관리합니다.

## 실습 과제: 자동 회귀 평가 파이프라인 (Phase 4 완료 과제)

`.github/workflows/eval.yml` + `evals/`

**요구사항**

1. 14주차 평가 하네스를 CI에 넣는다. PR마다 smoke(20개×2회), main 머지 시 full(50개×3회).
2. `compare.py`: 기준(main 최신 결과) 대비 점수·비용·지연 변화, 새로 실패한 항목, must-pass 위반을 계산하고 마크다운 리포트를 생성한다.
3. must-pass 위반이나 임계값 초과 시 CI 실패.
4. PR에 리포트를 코멘트로 남긴다.
5. 실험: 의도적으로 나쁜 프롬프트 변경(예: 정책 문장 삭제)을 PR로 올려 CI가 막는지 확인한다.
6. 실험: 모델을 다른 것으로 바꾼 PR을 올려 점수·비용 비교 리포트를 받는다.
7. 15주차 트레이스에서 낮은 점수 10개를 골라 오류 분석 후 평가 세트에 추가하는 스크립트를 만든다.

**채점 기준**

- [ ] 나쁜 프롬프트 PR이 CI에서 실패한다
- [ ] 모델 교체 PR 리포트에 점수·비용·지연 변화와 신뢰구간이 있다
- [ ] 평가 세트에 프로덕션(또는 시뮬레이션) 유래 항목이 추가되었다

## 면접 질문

<details>
<summary>프롬프트를 바꿀 때 품질이 떨어지지 않았는지 어떻게 확인하나요?</summary>

프롬프트를 코드처럼 버전 관리하고, 변경 PR마다 평가 세트로 CI에서 자동 평가합니다. 각 항목을 여러 번 실행해 기준 버전과 점수·비용·지연을 비교하고, 안전·정책 관련 필수 항목이 하나라도 깨지면 막습니다. 전체 점수는 신뢰구간이나 임계값으로 판단하고, 항목 단위로 새로 실패한 사례를 읽어 확인합니다. 머지 후에는 점진 배포와 온라인 지표로 다시 확인합니다.
</details>

<details>
<summary>새 모델이 나왔을 때 교체 여부를 어떻게 결정하나요?</summary>

전체 평가 세트를 반복 실행해 품질, 비용, 지연, 일관성(pass^k)을 기존 모델과 비교하고, 항목 단위로 새로 실패·성공한 사례를 읽습니다. 모델마다 프롬프트 반응이 달라 약간의 프롬프트 조정 후 다시 비교합니다. 품질이 같고 싸면 일부 경로부터 라우팅하고, 그림자 모드나 소량 트래픽 A/B로 온라인 지표를 확인한 뒤 전환합니다. 벤치마크 점수만 보고 바꾸지 않습니다.
</details>

<details>
<summary>에이전트 A/B 테스트에서 주의할 점은?</summary>

1차 지표와 가드레일 지표(비용, 지연, 안전)를 사전에 정하고, 사용자 단위로 무작위 배정하며, 필요한 표본 크기를 미리 계산해 중간에 결과를 보고 멈추지 않습니다. 에이전트는 결과 분산이 커서 표본이 더 필요할 수 있고, 명시적 피드백은 응답 편향이 있어 해결률·이관률 같은 행동 지표를 함께 봅니다. 부수효과 있는 기능은 그림자 모드로 먼저 검증합니다.
</details>
