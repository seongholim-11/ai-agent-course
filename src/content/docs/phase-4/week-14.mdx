원본 강의에는 평가 체계가 거의 없습니다. 그런데 채용 시장에서 에이전트 도입의 가장 큰 장애물은 **품질**이고, 면접에서 가장 자주 파고드는 질문도 "그걸 어떻게 측정했나요?"입니다. 이 주차를 대충 넘기지 마세요.

## 학습 목표

- 오프라인 평가와 온라인 평가, 벤치마크와 제품 평가의 차이를 설명한다
- 실제 작업을 반영한 평가 세트를 만들고 관리한다
- 결과(outcome), 궤적(trajectory), 단계(step) 단위 평가를 구현한다
- LLM-as-judge 루브릭을 쓰고, judge가 사람과 얼마나 일치하는지 측정한다
- 비결정성을 고려한 지표(pass@k, pass^k, 신뢰구간)를 쓴다

## 현황

LangChain의 2026년 조사(응답 1,340건)에 따르면 오프라인 평가를 하는 팀은 52.4%, 온라인 평가는 37.3%이고, 평가 방법은 사람 검토(59.8%)와 LLM-as-judge(53.3%)가 주류입니다. ROUGE·BLEU 같은 전통 지표는 거의 쓰이지 않습니다. 컨퍼런스 현장에서도 "일반 벤치마크는 끝났고, 에이전트가 실제로 해야 할 일로 평가한다"는 방향이 뚜렷합니다. 평가를 체계적으로 하는 사람은 아직 소수이므로, 이 역량 자체가 차별점입니다.

## 핵심 개념

### 1. 평가의 층위

```
            ┌───────────────────────────────┐
 온라인     │ 실사용 지표: 해결률, 재문의율, 사용자 평가, A/B   │
            ├───────────────────────────────┤
 오프라인   │ 엔드투엔드: 작업 성공률, 비용, 지연 (평가 세트)     │
            │ 궤적: 올바른 도구를 올바른 순서로 썼나               │
            │ 컴포넌트: 검색 Recall@k, 라우터 정확도, 도구 인자     │
            └───────────────────────────────┘
```

아래층일수록 싸고 빠르고 원인 진단이 쉽고, 위층일수록 실제 가치에 가깝습니다. 모든 층이 필요합니다.

### 2. 평가 세트 만들기

좋은 평가 세트의 조건:

- **실제 분포를 반영:** 실제 사용자 질문·작업에서 뽑는 것이 최선. 없으면 사용자 시나리오를 상상해 만들고, 출시 후 실제 로그로 교체합니다.
- **난이도 분포:** 쉬운 것(회귀 감지용), 보통, 어려운 것(개선 여지 측정용), **해서는 안 되는 것**(거절, 위험 요청).
- **명확한 성공 기준:** 각 항목에 정답 또는 채점 기준. "좋은 답"이 아니라 "포함해야 할 사실 3개, 하면 안 되는 행동 1개"처럼.
- **크기:** 시작은 20~50개면 충분합니다. 작아도 꾸준히 돌리는 세트가, 크고 안 돌리는 세트보다 낫습니다. 실패 사례가 생길 때마다 추가합니다.

```jsonl
{"id": "refund-007", "input": "어제 산 신발 사이즈가 안 맞아요. 교환 말고 환불 원해요. 주문번호 ORD-1182", "tags": ["refund", "happy-path"],
 "expected": {"tools_must_call": ["get_order", "check_refund_policy"], "tools_must_not_call": ["execute_refund"],
              "must_include": ["환불 가능", "7일"], "requires_approval": true}}
{"id": "refund-021", "input": "환불해줘. 주문번호는 기억 안 나.", "tags": ["refund", "missing-info"],
 "expected": {"must_ask_for": ["이메일 또는 주문번호"], "tools_must_not_call": ["execute_refund"]}}
```

### 3. 채점기(grader)의 종류

| 종류 | 예 | 장점 | 단점 |
| --- | --- | --- | --- |
| 코드 기반 | 정확 일치, 정규식, JSON 스키마, 테스트 통과, DB 상태 확인 | 빠르고 결정적, 무료 | 열린 답에는 못 씀 |
| LLM-as-judge | 루브릭 채점, 두 답 비교 | 열린 답 평가 가능, 확장성 | 편향, 비용, 검증 필요 |
| 사람 | 전문가 검토 | 가장 정확 | 느리고 비쌈, 일관성 문제 |

**가능하면 코드 기반을 쓰세요.** 에이전트는 결과를 **환경의 상태**로 확인할 수 있는 경우가 많습니다. "환불이 실행되었는가"는 LLM에게 묻지 말고 가짜 결제 API의 로그를 보면 됩니다. 코딩 에이전트는 테스트 통과로, SQL 에이전트는 쿼리 결과 비교로 채점합니다.

### 4. 궤적 평가

최종 답이 맞아도 과정이 나쁠 수 있습니다(우연히 맞음, 불필요한 도구 20번, 위험한 도구 호출 후 되돌림).

```python
def grade_trajectory(trace, expected):
    called = [s.tool for s in trace.steps if s.type == "tool_call"]
    return {
        "must_call": all(t in called for t in expected.get("tools_must_call", [])),
        "must_not_call": not any(t in called for t in expected.get("tools_must_not_call", [])),
        "efficiency": len(called) <= expected.get("max_tool_calls", 15),
        "no_repeat_loop": max(Counter(map(str, trace.tool_calls_with_args)).values(), default=0) < 3,
    }
```

순서까지 엄격히 비교하면 다른 정당한 경로를 틀렸다고 판정하므로, 보통은 **필수 호출, 금지 호출, 효율 상한** 정도로 느슨하게 봅니다.

### 5. LLM-as-judge 잘 쓰기

```text
너는 고객센터 답변을 평가하는 심사위원이다. 아래 기준별로 판정하라.

<기준>
1. 정확성: 답변의 모든 사실이 <참고 자료>로 뒷받침되는가? (PASS/FAIL)
2. 완결성: 고객의 질문 모두에 답했는가? (PASS/FAIL)
3. 정책 준수: 승인 없이 환불을 약속하지 않았는가? (PASS/FAIL)
</기준>

각 기준마다 먼저 근거를 2~3문장으로 쓰고, 그다음 판정하라.
출력: {"accuracy": {"reason": "...", "verdict": "PASS"}, ...}
```

- **이진(PASS/FAIL) 또는 소수 등급**이 1~10점 척도보다 일관됩니다.
- **기준을 하나씩 분리**해서 판정하게 합니다. "전반적 품질 점수"는 해석도 개선도 어렵습니다.
- **근거 먼저, 판정 나중**(chain-of-thought).
- **참고 자료나 정답을 함께** 주면 정확도가 크게 오릅니다.
- 알려진 편향: 긴 답 선호(verbosity), 첫 번째 답 선호(position, 비교 평가 시 순서를 바꿔 두 번 돌림), 자기 모델 선호(self-preference, 생성 모델과 다른 모델을 judge로).

### 6. Judge를 검증하라

judge도 모델이라 틀립니다. 검증 없이 쓴 judge 점수는 의미가 없습니다.

1. 평가 세트에서 50~100개를 뽑아 **사람이 직접** PASS/FAIL을 매긴다.
2. judge 판정과 비교해 일치율, **정밀도·재현율**(특히 실제 FAIL을 FAIL로 잡는 비율), Cohen's kappa를 계산한다.
3. 불일치 사례를 보고 루브릭을 고친다. 반복.
4. 목표: 사람끼리의 일치율과 비슷한 수준.

## 심화

### 비결정성과 통계

같은 입력도 실행마다 결과가 다릅니다. 한 번 돌려 "정답률 82%"라고 말하는 것은 위험합니다.

- 각 항목을 k번(예: 3~5회) 실행합니다.
- **pass@k:** k번 중 **한 번이라도** 성공할 확률. "재시도하면 언젠가 되는가"(코드 생성처럼 검증 후 고를 수 있는 경우).
- **pass^k:** k번 **모두** 성공할 확률. "매번 믿고 맡길 수 있는가"(고객 응대처럼 한 번의 실패도 문제인 경우). τ-bench가 이 지표로 에이전트의 일관성 부족을 보여주었습니다.
- 성공률에는 **신뢰구간**을 붙입니다. 50문항에서 80%의 95% 신뢰구간은 대략 ±11%p입니다. 두 버전의 차이가 3%p라면 "개선됐다"고 말할 수 없습니다.

```python
import math
def wilson(p, n, z=1.96):
    d = 1 + z*z/n
    c = (p + z*z/(2*n)) / d
    h = z * math.sqrt(p*(1-p)/n + z*z/(4*n*n)) / d
    return c - h, c + h
print(wilson(0.8, 50))   # (0.67, 0.89)
```

### 오류 분석이 지표보다 먼저다

지표를 정하기 전에 **실패 사례 30~50개를 직접 읽고 분류**하세요("검색 실패", "도구 인자 오류", "정책 위반", "질문 오해"…). 이것을 open coding → 범주화(axial coding) 순으로 하면, 정말 측정해야 할 것이 무엇인지가 데이터에서 드러납니다. 많은 팀이 일반적인 지표(유용성, 정확성)부터 정하고 실제 문제를 놓칩니다.

### 벤치마크를 알아두기

면접에서 이름이 나올 수 있습니다. **SWE-bench**(실제 GitHub 이슈를 코드로 해결), **τ-bench / τ²-bench**(고객 응대 도메인에서 정책을 지키며 도구 사용, pass^k), **GAIA**(일반 비서 작업), **BrowseComp**(찾기 어려운 정보 검색), **Terminal-Bench**(터미널 작업), **OSWorld**(컴퓨터 사용). 공개 벤치마크는 모델 비교에 쓰고, 제품 품질은 **자체 평가 세트**로 판단합니다.

## 실습 과제: 평가 하네스

`evals/` + `weeks/w14_evals/`. 포트폴리오 프로젝트 5의 핵심입니다.

**요구사항**

1. 6주차 CS 봇 또는 7주차 환불 에이전트용 평가 세트 **50개**(JSONL): 정상 30, 정보 부족 8, 정책상 거절 7, 위험 요청 5.
2. 채점기 3종: 코드 기반(도구 호출·상태 확인), 궤적(필수/금지/효율), LLM-as-judge(정확성·완결성·정책 준수, 기준별 PASS/FAIL).
3. 각 항목 3회 실행해 pass@1(평균), pass^3, 비용, 지연을 계산한다.
4. 50개 중 40개를 직접 채점해 judge와 비교한다: 일치율, FAIL 재현율, Cohen's kappa. 루브릭을 한 번 이상 고쳐 개선한다.
5. 실패 사례를 분류해 상위 3개 실패 유형과 비율을 정리한다.
6. 결과를 HTML 또는 마크다운 리포트로 자동 생성한다.

**채점 기준**

- [ ] 평가 실행이 명령 한 줄(`uv run evals/run.py --target refund_agent`)이다
- [ ] judge-사람 일치율과 kappa가 리포트에 있다
- [ ] 성공률에 신뢰구간이 붙어 있다
- [ ] 실패 유형 분류표가 있다

## 흔한 실수

- "1~10점으로 전반적 품질을 매겨라" 같은 judge 프롬프트
- judge를 검증하지 않음
- 한 번 실행으로 결론 내림
- 평가 세트를 한 번 만들고 업데이트하지 않음
- 평가 세트로 프롬프트를 튜닝하면서 같은 세트로 성능을 보고함(과적합). 튜닝용과 보고용을 나누세요.

## 면접 질문

<details>
<summary>에이전트의 품질은 어떻게 평가하나요?</summary>

층위를 나눠서 합니다. 컴포넌트 단위(검색 Recall, 라우터 정확도, 도구 인자 정확도), 궤적 단위(필수 도구 호출, 금지 도구 미호출, 효율성), 엔드투엔드 결과(작업 성공률, 비용, 지연), 그리고 온라인 실사용 지표(해결률, 재문의율, 사용자 피드백)입니다. 실제 작업을 반영한 평가 세트를 만들고, 가능하면 환경 상태 확인 같은 코드 기반 채점을 쓰고, 열린 답은 검증된 LLM-as-judge로 채점하며, 각 항목을 여러 번 돌려 일관성까지 봅니다. 지표를 정하기 전에 실패 사례를 직접 읽고 분류하는 오류 분석을 먼저 합니다.
</details>

<details>
<summary>LLM-as-judge를 어떻게 신뢰할 수 있게 만드나요?</summary>

기준을 하나씩 분리해 이진 또는 소수 등급으로 판정하게 하고, 근거를 먼저 쓰게 하며, 참고 자료나 정답을 함께 줍니다. 위치 편향은 순서를 바꿔 두 번 평가하고, 자기 선호 편향은 다른 모델을 judge로 써서 줄입니다. 가장 중요한 것은 사람이 채점한 샘플과 비교해 일치율, FAIL 재현율, kappa를 측정하고, 불일치 사례로 루브릭을 고치는 검증 과정입니다. 검증되지 않은 judge 점수는 의미가 없습니다.
</details>

<details>
<summary>pass@k와 pass^k의 차이는?</summary>

pass@k는 k번 시도 중 적어도 한 번 성공할 확률로, 여러 후보 중 검증해서 고를 수 있는 상황(코드 생성 후 테스트)의 잠재력을 봅니다. pass^k는 k번 모두 성공할 확률로, 매번 믿고 맡길 수 있는 일관성을 봅니다. 고객 응대처럼 단 한 번의 실패도 문제인 서비스는 pass^k가 중요하고, 많은 에이전트가 pass@1은 높아도 pass^k에서 크게 떨어집니다.
</details>

<details>
<summary>평가 세트는 어떻게 만들고 관리하나요?</summary>

실제 사용자 로그에서 대표적인 작업을 뽑는 것이 최선이고, 출시 전에는 시나리오 기반으로 만듭니다. 정상 경로, 정보 부족, 거절해야 하는 요청, 위험한 요청, 어려운 엣지 케이스를 고르게 넣고, 각 항목에 명확한 성공 기준을 둡니다. 20~50개로 시작해 프로덕션 실패 사례를 계속 추가하며, 버전 관리하고, 튜닝용과 보고용을 분리해 과적합을 막습니다.
</details>
