## 학습 목표

- 프롬프트 엔지니어링과 컨텍스트 엔지니어링의 차이를 설명한다
- 컨텍스트가 길어질 때 품질이 떨어지는 이유와 증상을 안다
- 쓰기(write), 고르기(select), 압축(compress), 격리(isolate) 네 가지 전략을 구현한다
- 긴 작업의 토큰 사용량을 줄이면서 품질을 유지하고, 이를 수치로 보여준다

## 프롬프트에서 컨텍스트로

프롬프트 엔지니어링은 "지시문을 어떻게 쓰나"의 문제였습니다. 에이전트에서는 매 턴 모델이 보는 것이 **시스템 프롬프트 + 도구 정의 + 대화 기록 + 도구 결과 + 검색 문서 + 메모리**의 조합입니다. 컨텍스트 엔지니어링은 **매 턴 이 유한한 공간에 무엇을, 어떤 순서와 형태로 넣을지 결정하는 일**입니다. 2026년 AI Engineer 컨퍼런스 보고서는 이를 그해의 가장 중요한 엔지니어링 과제로 꼽았습니다.

Anthropic은 컨텍스트를 **유한하고 체감 수익이 줄어드는 자원**으로 보고, "원하는 결과를 낼 가능성을 최대화하는 가장 작은 고신호(high-signal) 토큰 집합"을 찾으라고 정리합니다.

## 왜 길면 나빠지는가

- **주의력 희석:** 트랜스포머는 모든 토큰 쌍의 관계를 봅니다. 토큰이 늘수록 중요한 정보에 쏠리는 주의가 줄어듭니다.
- **Context rot:** 여러 연구에서 입력이 길어질수록 같은 과제의 정확도가 떨어지는 현상이 관찰됩니다. 윈도우 한도 훨씬 전부터 시작됩니다.
- **오염과 혼란:** 잘못된 도구 결과, 폐기된 계획, 서로 모순되는 정보가 남아 있으면 모델이 거기에 끌려갑니다. 초반의 환각이 계속 참조되는 것을 "context poisoning"이라 부르기도 합니다.
- **비용:** 3주차에서 본 것처럼 입력 토큰은 턴 수에 대해 제곱으로 늘어납니다.

## 핵심 전략 4가지

### 1. 쓰기(Write): 컨텍스트 밖에 저장

중요한 것을 컨텍스트에만 두지 말고 외부에 씁니다.

- **스크래치패드·노트 파일:** 에이전트가 `notes.md`에 진행 상황, 결정, 남은 일을 기록하고 필요할 때 다시 읽습니다.
- **todo 리스트:** 계획을 파일이나 상태로 유지(12주차).
- **아티팩트:** 긴 중간 결과(검색 원문, 코드, 표)는 파일로 쓰고 경로만 컨텍스트에 둡니다.

```python
WRITE_NOTE = {"name": "write_note", "description": "중요한 발견, 결정, 남은 할 일을 notes.md에 덧붙인다. 긴 작업에서는 5~10턴마다 정리하라.", ...}
READ_NOTE = {"name": "read_note", "description": "지금까지의 노트를 읽는다. 무엇을 했는지 헷갈리면 먼저 읽어라.", ...}
```

### 2. 고르기(Select): 필요한 것만 불러오기

- **Just-in-time 로딩:** 파일 전체를 미리 넣지 말고 경로·목록만 주고 필요할 때 `read_file`, `grep`으로 읽게 합니다. 코딩 에이전트가 코드베이스 전체를 넣지 않고 탐색하는 방식입니다.
- **도구 선택:** 상황에 필요한 도구만 노출(도구 검색).
- **메모리 검색:** 관련 있는 기억만 검색해 넣기(13주차).
- **RAG:** 6주차의 검색 품질이 곧 컨텍스트 품질입니다.

### 3. 압축(Compress): 줄여서 남기기

- **도구 결과 절단·요약:** 웹페이지 전문 대신 관련 단락만, 거대한 JSON 대신 필요한 필드만.
- **오래된 도구 결과 지우기(tool result clearing):** 몇 턴 전의 도구 결과는 "[결과 생략: 필요하면 다시 호출]"로 바꿉니다. 가장 안전하고 효과가 큰 압축입니다.
- **Compaction:** 대화가 한도에 가까워지면 지금까지의 내용을 요약해 새 컨텍스트로 시작합니다.

```python
COMPACT_PROMPT = """지금까지의 작업을 이어받을 사람을 위해 요약하라. 반드시 포함:
1. 원래 목표와 사용자의 제약 조건 (원문 그대로)
2. 지금까지 확정된 사실과 그 출처
3. 내린 결정과 이유
4. 실패한 시도와 원인 (다시 시도하지 않도록)
5. 남은 할 일과 다음 단계
6. 작업 중인 파일 경로
버릴 것: 중복된 도구 결과 원문, 이미 해결된 오류의 세부 로그."""

async def maybe_compact(messages, used_tokens, limit=120_000):
    if used_tokens < limit * 0.7:
        return messages
    summary = await llm(COMPACT_PROMPT, messages)
    # 시스템 프롬프트와 최근 몇 턴은 원문 유지
    return [messages[0], {"role": "user", "content": f"[이전 작업 요약]\n{summary}"}] + messages[-4:]
```

Compaction의 위험은 **무엇을 잃는지 모른다**는 것입니다. 원래 지시문의 세부 제약, 사용자가 한 번 말한 선호, 미묘한 실패 원인이 요약에서 빠지기 쉽습니다. 그래서 요약 프롬프트를 체크리스트로 쓰고, 압축 전후 품질을 평가합니다.

### 4. 격리(Isolate): 컨텍스트를 나누기

- **서브에이전트:** 탐색처럼 토큰을 많이 먹는 일을 깨끗한 컨텍스트의 서브에이전트에 맡기고, **1~2천 토큰의 압축된 결과만** 받습니다. 8주차 멀티 에이전트의 주된 이점입니다.
- **상태 분리:** LangGraph 상태에 모델에게 보여줄 필드와 숨길 필드를 나눕니다.
- **샌드박스·코드 실행:** 대량 데이터 처리를 코드로 하게 하고 결과 요약만 컨텍스트로 가져옵니다.

## 심화

### 컨텍스트 구성 순서와 캐싱

```
[시스템 프롬프트]  ← 고정, 캐시
[도구 정의]        ← 고정, 캐시
[고정 지식/규칙]   ← 고정, 캐시
[요약된 이전 맥락] ← compaction 시에만 바뀜
[최근 대화 + 도구 결과]
[현재 지시]        ← 가장 마지막 (최근 위치에 있을수록 잘 따름)
```

컨텍스트 엔지니어링은 품질만이 아니라 **캐시 적중률**과 함께 설계해야 합니다. 오래된 도구 결과를 지우면 그 지점 뒤의 캐시가 깨지므로, 지우는 시점을 묶어서(예: 20턴마다 한 번) 처리하는 등의 절충이 필요합니다.

### 시스템 프롬프트의 "적절한 고도"

너무 구체적이면(if-else 규칙 나열) 취약하고, 너무 추상적이면("잘 해라") 모델이 방향을 못 잡습니다. 원칙과 우선순위, 대표 예시 몇 개, 경계 조건을 섹션(XML 태그나 마크다운 헤더)으로 나눠 씁니다. 예시는 엣지 케이스를 모두 나열하기보다 **다양하고 대표적인 몇 개**가 낫습니다.

### 도구 결과 설계가 곧 컨텍스트 설계

- 페이지네이션과 `max_results` 인자를 기본으로
- `response_format: "concise" | "detailed"` 같은 옵션을 주고 기본값은 간결하게
- 사람이 읽을 수 있는 이름을 UUID보다 우선(모델의 정확도가 오름)
- 결과가 잘렸으면 잘렸다고 명시("결과 250건 중 20건 표시, 필터를 좁혀라")

### 측정 없이는 최적화도 없다

턴마다 컨텍스트 구성(시스템/도구/대화/도구 결과 토큰 수)을 기록하면 어디서 부풀어 오르는지 바로 보입니다. 대부분 **도구 결과**가 범인입니다.

## 실습 과제: 긴 작업 다이어트

`weeks/w11_context/`

**과제:** "오픈소스 저장소 하나(예: 중간 크기 파이썬 라이브러리)를 클론해, 주요 모듈의 구조와 확장 포인트를 설명하는 문서 작성"처럼 **도구 호출 40회 이상**이 필요한 작업을 고릅니다.

**요구사항**

1. 기준선: 4주차 루프 + `list_dir`, `read_file`, `grep` 도구, 아무 컨텍스트 관리 없이 실행. 턴별 토큰 구성을 기록한다.
2. 개선 1: 도구 결과 절단(파일은 기본 200줄, 필요 시 범위 지정) + 오래된 도구 결과 지우기.
3. 개선 2: `notes.md` 쓰기·읽기 도구.
4. 개선 3: 탐색을 서브에이전트로 격리("이 디렉터리를 조사해 500단어 요약").
5. 개선 4: 컨텍스트 70% 도달 시 compaction.
6. 각 단계의 총 토큰, 비용, 완료 여부, 결과 품질(루브릭)을 표로 비교한다.
7. 턴별 토큰 구성을 누적 막대 차트로 그린다(matplotlib).

**채점 기준**

- [ ] 기준선 대비 총 토큰 50% 이상 감소
- [ ] 품질 점수가 기준선보다 떨어지지 않았다(떨어졌다면 원인 분석)
- [ ] compaction 요약에서 빠진 정보가 있었는지 확인하고 프롬프트를 한 번 개선했다

## 흔한 실수

- 큰 윈도우를 믿고 모든 것을 넣음 → 비용과 품질 모두 나빠집니다.
- compaction 요약에 원래 목표와 제약을 빠뜨림 → 압축 후 에이전트가 목표를 잊습니다.
- 서브에이전트 결과를 원문 그대로 받음 → 격리 효과 없음
- 노트 파일을 쓰게만 하고 읽으라는 지시가 없음

## 면접 질문

<details>
<summary>컨텍스트 엔지니어링이란 무엇이고 프롬프트 엔지니어링과 어떻게 다른가요?</summary>

프롬프트 엔지니어링은 주로 지시문 작성에 관한 것이고, 컨텍스트 엔지니어링은 에이전트가 매 턴 보는 전체 입력(시스템 프롬프트, 도구 정의, 대화 기록, 도구 결과, 검색 문서, 메모리)을 동적으로 구성하고 관리하는 일입니다. 컨텍스트는 길수록 비싸고 품질이 떨어지는 유한 자원이므로, 쓰기(외부 저장), 고르기(필요할 때만 로딩), 압축(요약·절단·삭제), 격리(서브에이전트) 전략으로 고신호 정보만 남기는 것이 목표입니다.
</details>

<details>
<summary>에이전트 대화가 컨텍스트 한도에 가까워지면 어떻게 하나요?</summary>

먼저 가장 안전한 것부터: 오래된 도구 결과를 지우고 큰 결과를 절단합니다. 그다음 중요한 상태를 노트 파일이나 상태 저장소로 옮기고, 그래도 부족하면 compaction으로 목표·제약·확정 사실·결정·실패·남은 일을 요약해 새 컨텍스트로 이어갑니다. 탐색이 많은 작업은 처음부터 서브에이전트로 격리합니다. 압축 전후 품질을 평가 세트로 확인하는 것이 중요합니다.
</details>

<details>
<summary>긴 컨텍스트 모델을 쓰면 컨텍스트 관리가 필요 없지 않나요?</summary>

아닙니다. 입력이 길어질수록 정확도가 떨어지는 현상(context rot, lost in the middle)이 한도 훨씬 전부터 나타나고, 비용과 지연은 입력에 비례해 증가하며, 잘못된 정보가 남아 계속 영향을 미칩니다. 긴 컨텍스트는 여유를 줄 뿐이고, 고신호 정보를 선별하는 일은 여전히 필요합니다.
</details>

<details>
<summary>서브에이전트가 컨텍스트 관리에 어떻게 도움이 되나요?</summary>

서브에이전트는 자기만의 깨끗한 컨텍스트에서 탐색(수십 번의 검색, 파일 읽기)을 하고, 그 과정의 원문은 버린 채 압축된 결과만 부모에게 돌려줍니다. 부모의 컨텍스트에는 결과 요약만 쌓이므로 긴 작업에서도 부모가 목표와 계획에 집중할 수 있습니다. 대신 서브에이전트는 부모의 맥락을 모르므로 브리프를 잘 써야 하고, 토큰 총량은 늘어날 수 있습니다.
</details>
