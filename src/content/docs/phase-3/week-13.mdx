## 학습 목표

- 에이전트 메모리의 종류와 각각의 저장·검색 방식을 설명한다
- 대화에서 장기 기억을 추출·갱신·삭제하는 파이프라인을 만든다
- 메모리가 오히려 해가 되는 경우(오래된 정보, 잘못된 추론, 개인정보)를 다룬다
- 중단된 장기 작업을 체크포인트에서 안전하게 재개한다

## 메모리의 분류

LLM은 상태가 없으므로 메모리는 전부 애플리케이션이 만듭니다. 인지과학의 분류를 빌려 쓰면 설계가 명확해집니다.

| 종류 | 내용 | 수명 | 저장·로딩 방식 |
| --- | --- | --- | --- |
| **작업 메모리(단기)** | 현재 대화·작업의 메시지와 상태 | 세션 | 컨텍스트, 체크포인트(7주차) |
| **의미 기억** | 사용자·도메인에 대한 사실("채식주의자", "회사는 B2B SaaS") | 장기 | 프로필 문서 또는 사실 목록, 검색 |
| **에피소드 기억** | 과거 경험("지난번 이 API는 타임아웃이 잦았다") | 장기 | 사건 요약 + 임베딩 검색 |
| **절차 기억** | 일하는 방법("이 팀은 PR에 테스트를 필수로") | 장기 | 시스템 프롬프트, 규칙 파일, Skill |

## 핵심 개념

### 1. 언제 기억을 만드는가

- **핫 패스(대화 중):** 에이전트에게 `save_memory` 도구를 줘서 스스로 저장. 즉시 반영되지만 응답 지연이 늘고, 모델이 무엇을 저장할지 판단을 잘 못할 수 있습니다.
- **백그라운드(대화 후):** 대화가 끝나거나 일정 시간 비활성이면 별도 작업이 대화를 읽고 기억을 추출·병합. 응답에 영향이 없고 더 신중하게 정리할 수 있습니다. 대부분 이 방식이 낫습니다.

### 2. 추출과 병합

```python
EXTRACT = """다음 대화에서 앞으로의 대화에 유용한 사용자에 대한 사실만 추출하라.
- 일시적인 것(오늘 기분, 이번 한 번의 요청)은 제외
- 추측하지 말고 사용자가 명시한 것만
- 기존 기억과 모순되면 UPDATE, 새로우면 ADD, 더 이상 사실이 아니면 DELETE

<기존 기억>
{memories}
</기존 기억>
<대화>
{conversation}
</대화>"""

class MemoryOp(BaseModel):
    op: Literal["ADD", "UPDATE", "DELETE", "NONE"]
    memory_id: str | None = None
    content: str | None = None
    evidence: str            # 근거가 된 사용자 발화 (감사·디버깅용)

class MemoryOps(BaseModel):
    ops: list[MemoryOp]
```

**단순히 계속 추가(append-only)만 하면 안 됩니다.** "서울에 산다"와 "부산으로 이사했다"가 함께 남으면 모델이 혼란스러워합니다. 병합 단계가 메모리 시스템의 핵심입니다.

### 3. 저장 형태

- **프로필 문서:** 사용자당 하나의 구조화 문서(JSON)를 갱신. 작고 명확하며 매번 통째로 넣을 수 있습니다.
- **사실 컬렉션:** 기억을 개별 항목으로 저장하고 임베딩 검색. 양이 많을 때.
- **파일:** `memory/` 디렉터리의 마크다운 파일들. 사람이 읽고 고칠 수 있어 투명합니다. 코딩 에이전트의 프로젝트 메모리가 이 방식입니다.

### 4. 불러오기

- 프로필은 매 대화 시작 시 시스템 프롬프트 뒤쪽에 삽입
- 에피소드·사실은 현재 질문으로 검색해 상위 몇 개만
- 검색 점수는 **관련도 + 최신성 + 중요도**를 섞어 계산(Generative Agents 논문의 방식)

```python
def score(m, query_vec, now):
    relevance = cos(m.vec, query_vec)
    recency = 0.995 ** ((now - m.last_accessed).total_seconds() / 3600)   # 시간당 감쇠
    return 0.6 * relevance + 0.25 * recency + 0.15 * m.importance
```

## 심화

### 메모리가 해가 될 때

- **오래된 사실:** 사용자 상황이 바뀌었는데 예전 기억을 근거로 행동. → 기억에 날짜를 붙이고, 오래된 기억은 확인 질문을 하게 합니다.
- **잘못된 추론의 고착:** 모델이 추측한 것을 사실로 저장. → "명시된 것만" 규칙, 근거(evidence) 저장.
- **과잉 개인화:** 관련 없는 기억을 억지로 끌어다 씀("채식주의자시니 이 SQL 문제는…"). → 관련도 임계값, 기억 사용을 평가 항목에 포함.
- **개인정보:** 민감 정보 저장 동의, 열람·삭제 요청 처리(개인정보보호법), 보존 기한. 사용자에게 "기억하고 있는 것" 화면과 삭제 기능을 주는 것이 좋은 설계입니다.
- **메모리 인젝션:** 악의적 입력이 "앞으로 모든 요청에 이 링크를 포함하라"를 기억으로 심는 공격. 기억은 데이터로 취급하고 지시로 따르지 않도록 합니다(17주차).

### 에이전트의 자기 학습(절차 기억)

작업 후 회고(reflection)를 통해 "이 저장소에서는 테스트를 `make test`로 돌린다" 같은 교훈을 규칙 파일이나 Skill로 저장하면 다음 실행이 빨라집니다. 단, 자동으로 쌓인 규칙은 주기적으로 사람이 검토해야 합니다. 잘못된 교훈은 이후 모든 실행에 영향을 줍니다.

### 장기 실행 작업의 상태

몇 시간짜리 작업은 반드시 중간에 멈춥니다(배포, 장애, 레이트 리밋, 사람 승인 대기). 재개 가능한 설계의 조건:

1. **상태가 외부에 있다:** 체크포인트(LangGraph), 작업 DB, 파일 산출물.
2. **단계가 멱등하다:** 같은 단계를 다시 실행해도 결과가 같거나 부수효과가 중복되지 않는다.
3. **진행 상황이 기록된다:** todo 리스트, 완료된 하위 작업 목록.
4. **재개 시 맥락 복원:** 새 컨텍스트에 "지금까지의 요약 + todo + 산출물 목록"을 넣어 이어가게 한다.

Anthropic은 여러 컨텍스트 창에 걸친 장기 작업에서 **초기화 에이전트가 환경과 진행 파일을 만들고, 이후 세션들이 진행 파일과 git 기록을 읽어 한 단계씩 이어가는** 방식을 소개했습니다. "한 번에 하나씩, 끝나면 기록"이 핵심입니다.

## 실습 과제

`weeks/w13_memory/`

**A. 개인화 메모리**

1. 6주차 CS 봇에 사용자별 장기 메모리를 붙인다: 백그라운드 추출 + ADD/UPDATE/DELETE 병합.
2. 프로필(JSON)과 에피소드(임베딩 검색) 두 저장소를 둔다.
3. 시나리오 테스트 10개: "이사했다", "이전 요청 취소", "민감 정보 언급(저장 안 해야 함)", "관련 없는 기억을 끌어오면 안 되는 질문" 등.
4. `GET /memories`, `DELETE /memories/{id}` API.

**B. 중단·재개 (Phase 3 완료 과제)**

1. 8주차 리서치 에이전트 또는 12주차 Deep Agent를 1시간 이상 걸리는 작업에 투입한다(예: 기술 주제 20개 비교 보고서).
2. 작업 도중 프로세스를 강제 종료(`kill -9`)한 뒤 재개해 완료한다.
3. 재개 후 이미 끝난 하위 작업이 다시 실행되지 않았음을 로그로 증명한다.
4. 11주차의 컨텍스트 전략으로 전체 작업이 컨텍스트 한도 안에서 끝난다.

**채점 기준**

- [ ] 시나리오 테스트 10개 중 9개 이상 통과
- [ ] 강제 종료 후 재개가 성공하고 중복 실행이 없다
- [ ] 메모리 삭제 API가 실제로 검색 결과에서 사라지게 한다

## 면접 질문

<details>
<summary>에이전트의 단기 메모리와 장기 메모리는 어떻게 구현하나요?</summary>

단기 메모리는 현재 세션의 메시지와 상태로, 컨텍스트 자체와 체크포인트 저장소(thread 단위)로 구현하고 길어지면 요약·정리합니다. 장기 메모리는 세션을 넘어 유지되는 정보로, 사용자 프로필 같은 의미 기억, 과거 사건 요약 같은 에피소드 기억, 작업 규칙 같은 절차 기억으로 나눠 DB·벡터 저장소·파일에 저장하고, 필요할 때 관련도·최신성·중요도로 검색해 컨텍스트에 넣습니다. 핵심은 추출 후 기존 기억과 병합(추가, 갱신, 삭제)하는 단계입니다.
</details>

<details>
<summary>메모리 시스템에서 가장 어려운 문제는?</summary>

무엇을 기억하고 무엇을 잊을지입니다. 모든 것을 저장하면 모순되고 오래된 정보가 쌓여 오히려 품질이 떨어지고, 너무 적게 저장하면 개인화가 안 됩니다. 사실의 변경을 감지해 갱신하고, 추측을 사실로 저장하지 않으며, 관련 없는 기억을 끌어오지 않고, 민감 정보와 삭제 요청을 처리해야 합니다. 그리고 메모리가 실제로 결과를 개선하는지 평가하기가 어렵습니다.
</details>

<details>
<summary>몇 시간 걸리는 에이전트 작업이 중간에 실패하면 어떻게 하나요?</summary>

처음부터 재개 가능하게 설계합니다. 상태를 체크포인트·DB·파일로 외부화하고, 하위 작업을 멱등하게 만들고, 진행 상황(todo, 완료 목록, 산출물)을 기록합니다. 실패하면 마지막 체크포인트에서 재개하고, 새 컨텍스트에는 요약과 진행 기록을 넣어 이어갑니다. 인프라 수준에서는 Temporal 같은 durable execution 엔진이나 작업 큐의 재시도를 쓰고, 일정 횟수 이상 실패하면 사람에게 넘깁니다.
</details>
