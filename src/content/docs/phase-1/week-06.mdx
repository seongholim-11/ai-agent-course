## 학습 목표

- RAG 파이프라인의 각 단계(수집, 청킹, 임베딩, 색인, 검색, 리랭킹, 생성)의 설계 선택지를 안다
- 하이브리드 검색과 리랭킹으로 검색 품질을 올리고 **수치로 증명**한다
- 고정 파이프라인 RAG와 Agentic RAG의 차이를 구현으로 체감한다
- 검색 품질(Recall@k, MRR)과 생성 품질(충실도, 정답률)을 따로 평가한다

## RAG 파이프라인

```
[색인 시점]  문서 → 파싱 → 청킹 → 임베딩 → 벡터 DB + 키워드 색인 (+ 메타데이터)
[질의 시점]  질문 → (질의 재작성) → 하이브리드 검색 top-50 → 리랭킹 top-5 → 프롬프트 → 답변 + 출처
```

RAG 품질 문제의 대부분은 **생성이 아니라 검색**에서 생깁니다. 정답 청크가 컨텍스트에 없으면 어떤 모델도 맞출 수 없습니다. 그래서 검색과 생성을 **분리해서 평가**합니다.

## 핵심 개념

### 1. 파싱과 청킹

- **파싱:** PDF·HTML·표·이미지에서 텍스트를 뽑는 단계가 의외로 품질을 좌우합니다. 표가 깨지거나 머리글·바닥글이 섞이면 검색이 망가집니다.
- **청킹 전략:**

| 전략 | 방식 | 장단점 |
| --- | --- | --- |
| 고정 길이 | 500토큰 + 50토큰 겹침 | 단순, 문맥이 잘릴 수 있음 |
| 구조 기반 | 마크다운 헤더·조항·함수 단위 | 의미 단위 보존, 길이 불균일 |
| 의미 기반 | 임베딩 유사도가 떨어지는 지점에서 분할 | 비용 높음, 효과는 데이터에 따라 다름 |
| 부모-자식 | 작은 청크로 검색하고 큰 부모 청크를 넣음 | 정밀 검색 + 넉넉한 문맥 |

- **문맥 추가(Contextual Retrieval):** 각 청크 앞에 "이 청크는 ○○ 문서의 △△ 절이며 …에 관한 내용"이라는 짧은 설명을 LLM으로 생성해 붙인 뒤 임베딩합니다. 청크 단독으로는 모호한 문장("위 조건에 해당하면…")의 검색률이 크게 오릅니다. 생성 비용은 프롬프트 캐싱으로 줄입니다.

### 2. 하이브리드 검색

- **벡터 검색:** 의미가 비슷한 것을 찾습니다. 동의어·의역에 강하고 **고유명사, 코드, 에러 메시지, 제품 번호에 약합니다.**
- **키워드 검색(BM25):** 정확한 단어 일치에 강합니다. 한국어는 형태소 분석기(예: Kiwi, Mecab)로 토큰화해야 성능이 납니다.
- **결합:** 두 결과를 **RRF(Reciprocal Rank Fusion)**로 합칩니다. 점수 스케일이 달라도 순위만 쓰므로 간단하고 강합니다.

```python
def rrf(result_lists: list[list[str]], k: int = 60) -> list[str]:
    score: dict[str, float] = {}
    for results in result_lists:
        for rank, doc_id in enumerate(results):
            score[doc_id] = score.get(doc_id, 0) + 1 / (k + rank + 1)
    return sorted(score, key=score.get, reverse=True)

ids = rrf([vector_search(q, 50), bm25_search(q, 50)])[:30]
```

### 3. 리랭킹

1차 검색(bi-encoder)은 질문과 문서를 따로 임베딩해 빠르지만 거칩니다. **리랭커(cross-encoder)**는 질문과 문서를 함께 읽어 관련도를 매겨 정확하지만 느립니다. 그래서 1차로 30~50개를 뽑고 리랭커로 5~10개를 고릅니다. Cohere Rerank, bge-reranker, Voyage rerank 등이 있습니다.

### 4. 생성 프롬프트

```text
아래 <documents>만 근거로 답하라.
- 각 주장 뒤에 [문서번호]로 출처를 단다.
- 문서에 답이 없으면 "제공된 자료에서 찾을 수 없습니다"라고 답한다. 추측하지 않는다.
- 문서 간 내용이 충돌하면 충돌 사실과 각 출처를 함께 밝힌다.

<documents>
<doc id="1" title="환불 정책" updated="2026-09-01">...</doc>
...
</documents>
```

### 5. Agentic RAG

고정 파이프라인은 질문마다 **한 번** 검색합니다. Agentic RAG는 검색을 **도구로** 주고 모델이 판단하게 합니다.

- 검색이 필요한지 판단(인사말에는 검색 안 함)
- 질문을 여러 하위 질의로 분해해 각각 검색(multi-hop)
- 결과가 부족하면 쿼리를 바꿔 재검색
- 소스를 골라 검색(사내 위키 vs 주문 DB vs 웹)

```python
TOOLS = [
  {"name": "search_docs", "description": "사내 정책·FAQ 문서를 검색한다. 정책, 규정, 절차 질문에 사용. 결과가 부족하면 다른 표현으로 다시 검색하라.",
   "input_schema": {"type": "object", "properties": {
       "query": {"type": "string"}, "doc_type": {"type": "string", "enum": ["policy", "faq", "manual", "any"]}},
       "required": ["query"]}},
  {"name": "search_orders", "description": "고객 주문 조회. ...", "input_schema": {...}},
]
```

| | 고정 RAG | Agentic RAG |
| --- | --- | --- |
| 지연·비용 | 낮고 일정 | 높고 들쭉날쭉 |
| 단순 질문 | 충분 | 과함 |
| 다단계·비교 질문 | 약함 | 강함 |
| 디버깅 | 쉬움 | 트레이스 필요 |

## 심화

### 검색 평가 지표

- **Recall@k:** 정답 청크가 상위 k개 안에 있는 비율. RAG에서 가장 중요합니다.
- **MRR:** 첫 정답의 순위 역수 평균. 정답이 얼마나 위에 있는지.
- **nDCG:** 관련도 등급이 여러 단계일 때.
- **생성 평가:** 충실도(faithfulness, 답이 근거 문서로 뒷받침되는가), 답변 관련성, 정답 일치. Ragas 같은 라이브러리가 LLM-as-judge로 계산해주지만, judge 자체를 검증해야 합니다(14주차).

**평가 세트 만드는 법:** 문서에서 청크를 무작위로 뽑아 LLM으로 "이 청크로 답할 수 있는 질문"을 생성하고, 사람이 걸러 30~100개를 만듭니다. 각 질문에 정답 청크 ID를 붙여두면 Recall@k를 자동으로 잴 수 있습니다. 실제 사용자 질문 로그가 있으면 그것이 최고의 평가 세트입니다.

### 질의 변환 기법

- **질의 재작성:** 대화 맥락이 있는 질문("그거 언제까지야?")을 독립 질문으로 바꿉니다. 멀티턴 RAG의 필수 단계입니다.
- **HyDE:** 가상의 답변을 먼저 생성해 그것으로 검색합니다. 질문과 문서의 표현 차이가 클 때 유효합니다.
- **분해:** "A와 B의 환불 조건 차이"를 A, B 각각의 질의로 나눕니다.

### 메타데이터 필터와 권한

실서비스에서는 "이 사용자가 볼 수 있는 문서만" 검색해야 합니다. 권한 필터는 **검색 단계에서** 적용해야 합니다. 생성 단계에서 프롬프트로 "권한 없는 내용은 말하지 마"라고 하는 것은 보안이 아닙니다. 날짜·부서·문서 종류 필터도 같은 방식으로 둡니다.

### 벡터 DB 선택

pgvector(이미 Postgres를 쓰면 가장 단순, 수백만 건까지 충분), Qdrant·Weaviate·Milvus(대규모, 필터·하이브리드 내장), 관리형(Pinecone 등)이 있습니다. 대부분의 서비스 규모에서는 **DB 선택보다 청킹·하이브리드·리랭킹이 품질에 훨씬 큰 영향**을 줍니다.

## 실습 과제: 문서 기반 CS 챗봇 (Phase 1 완료 과제)

`weeks/w06_rag_bot/`. 포트폴리오 프로젝트 2의 출발점이 됩니다.

**데이터:** 공개된 한국어 이용약관·FAQ·도움말 문서를 30~100페이지 분량으로 모읍니다(예: 공공기관 민원 FAQ, 오픈소스 프로젝트 문서).

**요구사항**

1. 청킹 전략 2가지(고정 길이 vs 헤더 기반)를 구현하고 Recall@5를 비교한다.
2. pgvector 또는 Qdrant로 벡터 검색 + BM25(한국어 형태소 토큰화) + RRF 하이브리드.
3. 리랭커를 붙여 전후 Recall@5, MRR을 비교한다.
4. 출처 인용이 있는 답변 생성. 답이 없으면 거절.
5. Agentic RAG 버전: `search_docs`를 도구로 주고 재검색을 허용한다.
6. **평가 세트 30문항**(답이 없는 질문 5개 포함)으로 고정 RAG vs Agentic RAG의 정답률, 거절 정확도, 평균 비용·지연을 비교한다.
7. 2주차 API 서버에 붙여 SSE로 답변과 "검색 중…" 이벤트를 스트리밍한다.

**결과표 예시**

| 벡터만 | | | | | | |
| 하이브리드 | | | | | | |

**채점 기준**

- [ ] 답이 없는 질문 5개 중 4개 이상을 올바르게 거절한다

## 흔한 실수

- 검색 품질을 측정하지 않고 프롬프트만 계속 고침
- 표·목록을 청킹하면서 머리글을 잃음 → 청크에 상위 헤더 경로를 붙이세요("환불 정책 > 해외 결제 > 수수료").
- 너무 많은 청크(20개 이상)를 넣음 → 오히려 정확도가 떨어지고 비쌉니다.
- 문서가 업데이트되어도 색인을 갱신하지 않음 → 증분 색인과 문서 버전(updated_at) 관리가 필요합니다.

## 면접 질문

<details>
<summary>RAG 답변 품질이 낮을 때 어떻게 디버깅하나요?</summary>

먼저 검색과 생성을 분리합니다. 실패 사례마다 "정답 근거가 검색 결과에 있었는가"를 확인해 Recall@k를 봅니다. 없었다면 검색 문제(파싱, 청킹, 임베딩 모델, 하이브리드 부재, 질의 재작성 부재, 메타데이터 필터)이고, 있었는데 틀렸다면 생성 문제(너무 많은 청크, 프롬프트 지시, 충돌하는 문서, 모델 성능)입니다. 실패 유형을 분류해 가장 많은 유형부터 고치고, 고칠 때마다 같은 평가 세트로 재측정합니다.
</details>

<details>
<summary>하이브리드 검색이 왜 필요한가요?</summary>

벡터 검색은 의미적 유사성에 강하지만 고유명사, 제품 코드, 에러 메시지, 숫자처럼 정확한 일치가 중요한 질의에 약하고, BM25는 그 반대입니다. 두 결과를 RRF 같은 방식으로 결합하면 서로의 약점을 보완해 대부분의 데이터셋에서 Recall이 오릅니다. 한국어는 형태소 분석 기반 토큰화를 해야 BM25가 제대로 동작합니다.
</details>

<details>
<summary>Agentic RAG와 일반 RAG의 차이와 트레이드오프는?</summary>

일반 RAG는 질문마다 고정된 한 번의 검색 후 생성합니다. Agentic RAG는 검색을 도구로 제공해 모델이 검색 필요 여부, 질의 분해, 재검색, 소스 선택을 스스로 결정합니다. 다단계·비교·모호한 질문에서 정확도가 오르지만 지연과 비용이 늘고 변동이 커지며 디버깅에 트레이스가 필요합니다. 그래서 단순 질문은 고정 RAG로, 복잡한 질문만 에이전트로 보내는 라우팅을 함께 쓰기도 합니다.
</details>

<details>
<summary>RAG에서 접근 권한은 어떻게 처리하나요?</summary>

색인 시 각 청크에 권한 메타데이터(부서, 문서 ACL, 테넌트 ID)를 붙이고, 검색 쿼리에 사용자 권한 필터를 **검색 엔진 수준에서** 적용합니다. 프롬프트로 "보지 말라"고 지시하는 것은 우회될 수 있어 보안 통제가 아닙니다. 멀티테넌트라면 테넌트별 컬렉션 분리도 고려하고, 원본 문서의 권한 변경이 색인에 반영되는 동기화 경로를 둡니다.
</details>

<details>
<summary>청크 크기는 어떻게 정하나요?</summary>

정답은 없고 데이터와 질문 유형에 따라 실험으로 정합니다. 작은 청크는 검색이 정밀하지만 문맥이 부족하고, 큰 청크는 문맥이 넉넉하지만 관련 없는 내용이 섞여 임베딩이 흐려집니다. 문서 구조(헤더, 조항) 단위로 자르고, 300~800토큰 범위에서 평가 세트로 Recall@k를 비교하며, 부모-자식 청킹이나 문맥 추가로 두 장점을 함께 얻는 방법을 씁니다.
</details>
