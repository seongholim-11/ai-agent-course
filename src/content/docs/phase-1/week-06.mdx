## RAG 파이프라인

**RAG(Retrieval-Augmented Generation, 검색 증강 생성)**는 "모델이 기억에 의존해 답하지 말고, 먼저 관련 문서를 찾아서 그걸 보고 답하게 하자"는 방법입니다. 오픈북 시험과 같습니다. 모델이 회사의 환불 정책을 외우고 있을 리 없으니, 정책 문서에서 관련 부분을 찾아 질문과 함께 넣어줍니다.

RAG는 두 시점으로 나뉩니다. 책에 미리 색인(찾아보기)을 만들어두는 일과, 질문이 왔을 때 색인으로 해당 페이지를 찾는 일입니다.

```
[색인 시점: 미리 한 번]  문서 → 파싱 → 청킹 → 임베딩 → 벡터 DB + 키워드 색인 (+ 메타데이터)
[질의 시점: 질문마다]    질문 → (질의 재작성) → 하이브리드 검색 top-50 → 리랭킹 top-5 → 프롬프트 → 답변 + 출처
```

여기서 꼭 기억할 사실: **RAG 품질 문제의 대부분은 생성이 아니라 검색에서 생깁니다.** 오픈북 시험에서 엉뚱한 페이지를 펼쳤다면 아무리 똑똑한 학생도 답을 맞힐 수 없습니다. 정답이 담긴 조각이 모델에게 전달되지 않으면 어떤 모델도 못 맞춥니다. 그래서 "검색이 정답을 찾아왔는가"와 "찾아온 걸로 답을 잘 썼는가"를 **따로 평가**합니다.

## 핵심 개념

### 1. 파싱과 청킹

- **파싱:** PDF·HTML·표·이미지에서 텍스트를 뽑아내는 단계입니다. 지루해 보이지만 의외로 품질을 좌우합니다. 표가 깨져서 숫자들이 한 줄로 뭉개지거나, 모든 페이지의 머리글·바닥글("○○회사 내부 문서 3/40쪽")이 본문에 섞이면 검색이 망가집니다.
- **청킹:** 긴 문서를 검색 단위가 될 작은 조각(청크)으로 자르는 일입니다. 문서 통째로는 너무 길어서 관련 부분만 집어 넣을 수 없기 때문입니다. 자르는 방법에 따라 결과가 크게 달라집니다.

| 전략 | 방식 | 장단점 |
| --- | --- | --- |
| 고정 길이 | 500토큰마다 자르고 50토큰씩 겹치게 | 단순하지만 문장·문맥이 중간에 잘릴 수 있음 |
| 구조 기반 | 마크다운 헤더·조항·함수 단위로 | 의미 단위가 보존되지만 길이가 들쭉날쭉 |
| 의미 기반 | 앞뒤 문장의 임베딩 유사도가 뚝 떨어지는 지점에서 | 비용이 높고, 효과는 데이터에 따라 다름 |
| 부모-자식 | 작은 청크로 검색하고, 넣을 때는 그 청크가 속한 큰 부모 청크를 | 정밀한 검색 + 넉넉한 문맥 |

겹침(overlap)을 두는 이유는, 중요한 문장이 경계에서 반으로 잘려도 어느 한쪽 청크에는 온전히 남게 하기 위해서입니다.

- **문맥 추가(Contextual Retrieval):** 청크를 잘라놓으면 "위 조건에 해당하면 수수료는 면제된다" 같은 문장만 덩그러니 남아서, 무엇에 관한 내용인지 알 수 없습니다. 그래서 각 청크 앞에 "이 청크는 ○○ 문서의 △△ 절이며 해외 결제 수수료에 관한 내용이다" 같은 짧은 설명을 LLM으로 만들어 붙인 뒤 임베딩합니다. 모호한 청크의 검색률이 크게 오릅니다. 청크마다 LLM을 부르니 비용이 드는데, 같은 문서 전체를 앞에 두고 청크만 바꿔가며 부르면 프롬프트 캐싱(3주차)으로 크게 줄일 수 있습니다.

### 2. 하이브리드 검색

검색 방식은 크게 두 가지이고, 서로 잘하는 것이 다릅니다.

- **벡터 검색:** 임베딩(3주차)으로 **뜻이 비슷한** 것을 찾습니다. "반품하고 싶어요"로 "환불 절차" 문서를 찾는 데 강합니다. 반대로 **고유명사, 코드, 에러 메시지, 제품 번호에 약합니다.** "E1042"와 "E1043"은 뜻이 비슷해 보여서 구분을 잘 못 합니다.
- **키워드 검색(BM25):** 질문의 **단어가 그대로 들어 있는** 문서를 찾습니다. 정확한 일치에 강해서 "E1042"는 확실히 찾지만, 같은 뜻을 다른 말로 쓰면 못 찾습니다. 한국어는 "환불은", "환불이", "환불을"이 다른 단어로 취급되지 않도록 **형태소 분석기**(예: Kiwi, Mecab)로 "환불 + 은"처럼 쪼개서 색인해야 제대로 동작합니다.
- **결합:** 두 검색 결과를 **RRF(Reciprocal Rank Fusion)**로 합칩니다. 두 방식의 점수는 단위가 달라서 그냥 더할 수 없는데, RRF는 점수 대신 **순위**만 씁니다. "양쪽 목록에서 모두 상위권인 문서"가 1등이 되는 방식이라 간단하면서도 강합니다.

```python
def rrf(result_lists: list[list[str]], k: int = 60) -> list[str]:
    """여러 검색 결과(문서 ID 목록)를 순위 기반으로 합친다."""
    score: dict[str, float] = {}
    for results in result_lists:                     # 벡터 결과, BM25 결과 각각에 대해
        for rank, doc_id in enumerate(results):      # rank: 0이 1등
            # 순위가 높을수록(rank가 작을수록) 큰 점수. k=60은 상위 몇 개에 점수가 쏠리지 않게 완화하는 값
            score[doc_id] = score.get(doc_id, 0) + 1 / (k + rank + 1)
    # 두 목록에 모두 나온 문서는 점수가 두 번 더해져 위로 올라온다
    return sorted(score, key=score.get, reverse=True)

# 각각 50개씩 넉넉히 뽑아 합친 뒤 상위 30개를 리랭커에 넘긴다
ids = rrf([vector_search(q, 50), bm25_search(q, 50)])[:30]
```

### 3. 리랭킹

1차 검색에 쓰는 임베딩 방식(bi-encoder)은 질문과 문서를 **따로따로** 숫자로 바꿔 비교합니다. 문서 임베딩을 미리 계산해둘 수 있어서 수백만 건도 순식간에 검색하지만, 질문과 문서를 함께 놓고 읽는 게 아니라서 판단이 거칩니다.

**리랭커(cross-encoder)**는 질문과 문서를 **한 쌍으로 함께 읽고** "이 문서가 이 질문에 얼마나 답이 되는가"를 점수 매깁니다. 훨씬 정확하지만, 문서마다 모델을 한 번씩 돌려야 해서 느립니다.

그래서 두 단계로 씁니다. 서류 전형(1차 검색)으로 후보 30~50명을 빠르게 추리고, 면접(리랭킹)으로 최종 5~10명을 고르는 것과 같습니다. Cohere Rerank, bge-reranker, Voyage rerank 등이 있습니다.

### 4. 생성 프롬프트

찾아온 문서를 모델에게 넘길 때는 "이것만 근거로 답하라"는 규칙을 분명히 줍니다.

```text
아래 <documents>만 근거로 답하라.
- 각 주장 뒤에 [문서번호]로 출처를 단다.                  ← 사용자가 확인할 수 있게, 그리고 환각을 줄이기 위해
- 문서에 답이 없으면 "제공된 자료에서 찾을 수 없습니다"라고 답한다. 추측하지 않는다.   ← 모르면 모른다고
- 문서 간 내용이 충돌하면 충돌 사실과 각 출처를 함께 밝힌다.  ← 오래된 정책과 새 정책이 섞여 있을 때

<documents>
<doc id="1" title="환불 정책" updated="2026-09-01">...</doc>   ← 제목·수정일 같은 메타데이터도 함께 주면 판단에 도움이 된다
...
</documents>
```

문서를 `<doc>` 태그로 감싸는 이유는, 어디까지가 자료이고 어디부터가 지시인지 모델이 구분하기 쉽게 하기 위해서입니다. (문서 안에 악의적인 지시가 숨어 있는 공격은 17주차에서 다룹니다.)

### 5. Agentic RAG

고정 파이프라인 RAG는 질문이 오면 무조건 **한 번** 검색하고 답합니다. **Agentic RAG**는 검색을 **도구로** 주고, 언제 어떻게 검색할지를 모델이 판단하게 합니다(4주차 루프 + 검색 도구). 그러면 이런 일을 할 수 있습니다.

- 검색이 필요한지 판단한다 ("안녕하세요"에는 검색하지 않음)
- 질문을 여러 하위 질의로 나눠 각각 검색한다 ("A와 B 비교" → A 검색, B 검색. 이런 여러 단계 검색을 multi-hop이라고 함)
- 결과가 부족하면 다른 표현으로 다시 검색한다
- 어디서 찾을지 고른다 (사내 위키 vs 주문 DB vs 웹)

```python
TOOLS = [
  {"name": "search_docs",
   # 설명에 "결과가 부족하면 다시 검색하라"를 넣어 재검색 행동을 유도한다
   "description": "사내 정책·FAQ 문서를 검색한다. 정책, 규정, 절차 질문에 사용. 결과가 부족하면 다른 표현으로 다시 검색하라.",
   "input_schema": {"type": "object", "properties": {
       "query": {"type": "string"},
       # enum으로 문서 종류를 고르게 하면 메타데이터 필터로 검색 범위를 좁힐 수 있다
       "doc_type": {"type": "string", "enum": ["policy", "faq", "manual", "any"]}},
       "required": ["query"]}},
  {"name": "search_orders", "description": "고객 주문 조회. ...", "input_schema": {...}},
]
```

| | 고정 RAG | Agentic RAG |
| --- | --- | --- |
| 지연·비용 | 낮고 일정 | 높고 들쭉날쭉 |
| 단순 질문 | 충분 | 과함 |
| 다단계·비교 질문 | 약함 | 강함 |
| 디버깅 | 쉬움 | 트레이스 필요 |

5주차의 교훈 그대로, 무조건 Agentic이 좋은 게 아닙니다. 단순 FAQ는 고정 RAG로, 복잡한 질문만 Agentic으로 보내는 라우팅이 흔한 답입니다.

## 심화

### 검색 평가 지표

"검색이 좋아졌다"를 느낌이 아니라 숫자로 말하려면 지표가 필요합니다.

- **Recall@k:** 정답 청크가 상위 k개 안에 들어 있는 비율. "모델에게 건넨 5개 안에 정답이 있었나?"이므로 RAG에서 가장 중요합니다.
- **MRR(Mean Reciprocal Rank):** 첫 번째 정답이 몇 등에 있었는지의 역수 평균. 1등이면 1, 3등이면 1/3. 정답이 얼마나 위에 있는지를 봅니다.
- **nDCG:** 관련도가 "딱 맞음 / 조금 관련 / 무관"처럼 여러 단계일 때 쓰는 지표.
- **생성 평가:** 충실도(faithfulness, 답이 근거 문서로 뒷받침되는가), 답변 관련성, 정답 일치. Ragas 같은 라이브러리가 LLM-as-judge(LLM이 채점하는 방식)로 계산해주지만, 그 채점기 자체가 믿을 만한지 따로 검증해야 합니다(14주차).

**평가 세트 만드는 법:** 문서에서 청크를 무작위로 뽑아 LLM에게 "이 청크로 답할 수 있는 질문"을 만들게 하고, 사람이 이상한 것을 걸러 30~100개를 만듭니다. 각 질문에 "정답은 이 청크"라는 ID를 붙여두면 Recall@k를 자동으로 잴 수 있습니다. 실제 사용자 질문 로그가 있다면 그게 최고의 평가 세트입니다.

### 질의 변환 기법

사용자의 질문을 그대로 검색에 쓰면 잘 안 찾아질 때가 있습니다. 검색하기 좋게 질문을 바꾸는 방법들입니다.

- **질의 재작성:** 대화 중의 질문은 앞 맥락이 있어야 뜻이 통합니다. "그거 언제까지야?"로는 아무것도 못 찾으니 "해외 결제 환불 신청 기한은 언제까지인가?"처럼 혼자서도 뜻이 통하는 질문으로 바꿉니다. 여러 턴 대화형 RAG에는 필수입니다.
- **HyDE:** 질문 대신 **가상의 답변을 먼저 만들어 그걸로 검색**합니다. 질문("환불 돼요?")과 문서("구매일로부터 7일 이내 청약철회가 가능하다")의 말투가 크게 다를 때, 답변처럼 생긴 문장이 문서와 더 비슷하기 때문입니다.
- **분해:** "A 상품과 B 상품의 환불 조건 차이"를 A 질의, B 질의로 나눠 각각 검색합니다.

### 메타데이터 필터와 권한

실서비스에서는 "이 사용자가 볼 수 있는 문서만" 검색되어야 합니다. 인사팀 문서가 일반 직원 답변에 섞여 나오면 안 됩니다. 이 권한 필터는 반드시 **검색 단계에서** 걸어야 합니다. 생성 단계에서 프롬프트로 "권한 없는 내용은 말하지 마"라고 하는 것은 보안이 아닙니다. 모델은 지시를 어길 수 있고, 일단 컨텍스트에 들어간 내용은 새어 나갈 수 있습니다. 날짜·부서·문서 종류 필터도 같은 방식으로 둡니다.

### 벡터 DB 선택

pgvector(이미 Postgres를 쓴다면 가장 단순하고 수백만 건까지 충분), Qdrant·Weaviate·Milvus(대규모, 필터·하이브리드 기능 내장), 관리형 서비스(Pinecone 등)가 있습니다. 어떤 DB를 쓸지 오래 고민하기 쉬운데, 대부분의 서비스 규모에서는 **DB 선택보다 청킹·하이브리드·리랭킹이 품질에 훨씬 큰 영향**을 줍니다.

**요구사항**

1. 청킹 전략 2가지(고정 길이 vs 헤더 기반)를 구현하고 Recall@5를 비교한다.
2. pgvector 또는 Qdrant로 벡터 검색 + BM25(한국어 형태소 토큰화) + RRF 하이브리드.
3. 리랭커를 붙여 전후 Recall@5, MRR을 비교한다.
4. 출처 인용이 있는 답변 생성. 답이 없으면 거절.
5. Agentic RAG 버전: `search_docs`를 도구로 주고 재검색을 허용한다.
6. **평가 세트 30문항**(답이 없는 질문 5개 포함)으로 고정 RAG vs Agentic RAG의 정답률, 거절 정확도, 평균 비용·지연을 비교한다.
7. 2주차 API 서버에 붙여 SSE로 답변과 "검색 중…" 이벤트를 스트리밍한다.

## 흔한 실수

- **검색 품질은 측정하지 않고 프롬프트만 계속 고침:** 문제가 검색에 있다면 프롬프트를 아무리 고쳐도 안 나아집니다. Recall@k부터 재세요.
- **표·목록을 청킹하면서 머리글을 잃음:** "수수료: 2%"만 남은 청크는 무슨 수수료인지 알 수 없습니다. 청크 앞에 상위 헤더 경로를 붙이세요("환불 정책 > 해외 결제 > 수수료").
- **너무 많은 청크(20개 이상)를 넣음:** 많이 넣으면 안전할 것 같지만, 오히려 관련 없는 내용에 주의가 흩어져 정확도가 떨어지고 비용만 늘어납니다.
- **문서가 바뀌어도 색인을 갱신하지 않음:** 정책이 바뀌었는데 옛 정책으로 답하게 됩니다. 바뀐 문서만 다시 색인하는 증분 색인과 문서 버전(updated_at) 관리가 필요합니다.

## 면접 질문

<details>
<summary>RAG 답변 품질이 낮을 때 어떻게 디버깅하나요?</summary>

먼저 검색과 생성을 분리합니다. 실패 사례마다 "정답 근거가 검색 결과에 있었는가"를 확인해 Recall@k를 봅니다. 없었다면 검색 문제(파싱, 청킹, 임베딩 모델, 하이브리드 부재, 질의 재작성 부재, 메타데이터 필터)이고, 있었는데 틀렸다면 생성 문제(너무 많은 청크, 프롬프트 지시, 충돌하는 문서, 모델 성능)입니다. 실패 유형을 분류해 가장 많은 유형부터 고치고, 고칠 때마다 같은 평가 세트로 재측정합니다.
</details>

<details>
<summary>하이브리드 검색이 왜 필요한가요?</summary>

벡터 검색은 의미적 유사성에 강하지만 고유명사, 제품 코드, 에러 메시지, 숫자처럼 정확한 일치가 중요한 질의에 약하고, BM25는 그 반대입니다. 두 결과를 RRF 같은 방식으로 결합하면 서로의 약점을 보완해 대부분의 데이터셋에서 Recall이 오릅니다. 한국어는 형태소 분석 기반 토큰화를 해야 BM25가 제대로 동작합니다.
</details>

<details>
<summary>Agentic RAG와 일반 RAG의 차이와 트레이드오프는?</summary>

일반 RAG는 질문마다 고정된 한 번의 검색 후 생성합니다. Agentic RAG는 검색을 도구로 제공해 모델이 검색 필요 여부, 질의 분해, 재검색, 소스 선택을 스스로 결정합니다. 다단계·비교·모호한 질문에서 정확도가 오르지만 지연과 비용이 늘고 변동이 커지며 디버깅에 트레이스가 필요합니다. 그래서 단순 질문은 고정 RAG로, 복잡한 질문만 에이전트로 보내는 라우팅을 함께 쓰기도 합니다.
</details>

<details>
<summary>RAG에서 접근 권한은 어떻게 처리하나요?</summary>

색인 시 각 청크에 권한 메타데이터(부서, 문서 ACL, 테넌트 ID)를 붙이고, 검색 쿼리에 사용자 권한 필터를 **검색 엔진 수준에서** 적용합니다. 프롬프트로 "보지 말라"고 지시하는 것은 우회될 수 있어 보안 통제가 아닙니다. 멀티테넌트라면 테넌트별 컬렉션 분리도 고려하고, 원본 문서의 권한 변경이 색인에 반영되는 동기화 경로를 둡니다.
</details>

<details>
<summary>청크 크기는 어떻게 정하나요?</summary>

정답은 없고 데이터와 질문 유형에 따라 실험으로 정합니다. 작은 청크는 검색이 정밀하지만 문맥이 부족하고, 큰 청크는 문맥이 넉넉하지만 관련 없는 내용이 섞여 임베딩이 흐려집니다. 문서 구조(헤더, 조항) 단위로 자르고, 300~800토큰 범위에서 평가 세트로 Recall@k를 비교하며, 부모-자식 청킹이나 문맥 추가로 두 장점을 함께 얻는 방법을 씁니다.
</details>
