- 에이전트를 "LLM이 루프 안에서 도구를 골라 쓰며 스스로 다음 행동을 정하는 시스템"으로 정의하고 설명한다

## 에이전트의 최소 정의

"에이전트"라는 말이 거창하게 들리지만, 뼈대는 몇 줄짜리 반복문입니다.

```
while not done:                                  # 끝날 때까지 반복
    response = LLM(system, tools, messages)      # 모델에게 "지금까지 상황 + 쓸 수 있는 도구"를 보여주고 묻는다
    if response에 도구 호출이 있으면:              # 모델이 "이 도구를 써야겠다"고 답했다면
        결과 = 도구 실행(response.tool_calls)      # 우리 코드가 그 도구를 실제로 실행하고
        messages += [response, 결과]              # 모델의 요청과 실행 결과를 대화에 덧붙인다
    else:
        done = True                              # 도구 없이 답했다 = 최종 답을 냈다
```

사람이 일하는 방식과 같습니다. "무엇을 해야 하지?" 생각하고 → 계산기를 두드리거나 검색해보고 → 결과를 보고 다시 생각하고 → 충분하면 답을 정리합니다. 다른 점은 **"생각"을 LLM이 하고, "행동"(도구 실행)은 우리 코드가 한다**는 것뿐입니다.

이게 전부입니다. LangGraph, OpenAI Agents SDK, Claude Agent SDK 같은 프레임워크는 모두 이 루프 위에 상태 저장, 스트리밍, 재시도, 관측, 사람 승인 같은 편의 기능을 얹은 것입니다. 이 루프를 한 번 직접 짜보면, 나중에 프레임워크로 만든 에이전트가 이상하게 동작할 때 "어디를 봐야 하는지"가 보입니다.

## 핵심 개념

### 1. Tool calling의 메시지 흐름

**Tool calling**(또는 function calling)은 모델이 "이 도구를 이 인자로 불러줘"라고 요청할 수 있게 해주는 API 기능입니다. 가장 많이 오해하는 지점부터 짚으면: **모델은 도구를 직접 실행하지 않습니다.** 식당에서 손님(모델)이 주문서를 쓰면, 주방(우리 코드)이 요리해서 가져다주는 구조입니다.

단계별로 보면 다음과 같습니다.

1. 개발자가 도구 목록(이름, 설명, 입력 형식을 정한 JSON Schema)을 요청에 함께 보낸다. "이런 도구들이 있어"라고 메뉴판을 주는 것.
2. 모델이 도구를 쓰기로 하면, 텍스트 답변 대신 **`tool_use` 블록**(도구 이름, 인자, 호출 ID)을 내고 `stop_reason="tool_use"`로 멈춘다. 주문서를 내민 것.
3. 개발자 코드가 그 도구를 실제로 실행한다. 요리하는 것.
4. 실행 결과를 `tool_result` 블록(같은 호출 ID를 붙여서)으로 대화에 붙여 다시 요청한다. 요리를 가져다주는 것.
5. 모델이 결과를 보고 다른 도구를 또 부르거나, 충분하면 최종 답을 낸다.

호출 ID가 필요한 이유는, 모델이 한 번에 도구를 여러 개 부를 수 있어서 "어느 결과가 어느 요청에 대한 것인지" 짝을 맞춰야 하기 때문입니다.

```json
// 2단계에서 모델이 내는 블록 (Anthropic 형식)
// id: 이 호출의 고유 번호 / name: 부르고 싶은 도구 / input: 넘길 인자
{"type": "tool_use", "id": "toolu_01A", "name": "get_weather", "input": {"city": "서울"}}

// 4단계에서 우리가 붙이는 결과
// role이 "user"인 점에 주의: 도구 결과는 "바깥 세상에서 온 정보"라 user 쪽 메시지로 넣는다
// tool_use_id: 위 호출의 id와 똑같아야 짝이 맞는다
{"role": "user", "content": [
  {"type": "tool_result", "tool_use_id": "toolu_01A", "content": "{\"temp_c\": 3, \"sky\": \"맑음\"}"}
]}
```

### 2. 도구 정의는 프롬프트다

모델은 도구의 코드를 볼 수 없습니다. 오직 **이름과 설명, 입력 형식만 보고** 언제 어떤 도구를 쓸지 정합니다. 그러니 도구 설명은 사람이 읽는 API 문서가 아니라 **모델에게 주는 업무 지시서**입니다. 신입 직원에게 "이 시스템은 이럴 때 쓰고, 이건 꼭 확인하고, 이럴 땐 쓰지 마"라고 알려주듯 써야 합니다.

```python
TOOLS = [{
    "name": "search_orders",
    "description": (
        "고객의 주문을 조회한다. "
        "고객이 주문 상태, 배송, 환불을 물을 때 사용한다. "          # ← 언제 쓰는지
        "이메일 또는 주문번호 중 하나는 반드시 필요하다. "            # ← 필요한 인자
        "결과는 최근 주문 최대 10건이다. "                          # ← 결과가 어떻게 생겼는지
        "주문번호를 모르면 먼저 고객에게 이메일을 물어라."            # ← 막혔을 때 어떻게 할지
    ),
    "input_schema": {                       # 인자의 모양 (JSON Schema)
        "type": "object",
        "properties": {
            "email": {"type": "string", "description": "고객 이메일"},
            # 형식 힌트를 설명에 넣어두면 모델이 엉뚱한 값을 넣는 일이 줄어든다
            "order_id": {"type": "string", "description": "'ORD-' 로 시작하는 주문번호"},
        },
    },
}]
```

좋은 도구 설명에 들어가는 것: **언제 쓰는지, 언제 쓰지 말아야 하는지, 필요한 인자, 결과 형태, 제약**. Anthropic은 이 작업을 사람용 화면을 설계하는 HCI(Human-Computer Interface)에 빗대 **ACI(Agent-Computer Interface) 설계**라고 부르며, 사람용 UI만큼 공을 들이라고 권합니다. 실제로 도구 설명 몇 줄을 고치는 것만으로 성공률이 크게 오르는 경우가 많습니다.

### 3. 맨손 루프 전체 코드

이제 위 개념을 모두 담은 실제 코드입니다. 길어 보이지만 ① 도구 정의, ② 도구 실행기, ③ 루프, 세 부분으로 나뉩니다.

```python
# weeks/w04_agent_loop/agent.py
import json, asyncio
import anthropic
from pydantic import BaseModel, ValidationError

client = anthropic.AsyncAnthropic()     # 비동기 클라이언트 (도구를 병렬로 돌리기 위해)

# ── ① 도구 정의 ──────────────────────────────────────────────
class CalcArgs(BaseModel):              # 계산기 도구의 입력 형식
    expression: str

def calculator(expression: str) -> str:
    """수식 문자열을 안전하게 계산한다."""
    import ast, operator as op
    # 허용할 연산만 미리 정해둔다: + - * / ** 음수부호
    ops = {ast.Add: op.add, ast.Sub: op.sub, ast.Mult: op.mul, ast.Div: op.truediv, ast.Pow: op.pow, ast.USub: op.neg}
    def ev(n):                          # 수식을 나무 구조(AST)로 바꾼 뒤 한 마디씩 직접 계산
        if isinstance(n, ast.Constant): return n.value                                   # 숫자
        if isinstance(n, ast.BinOp): return ops[type(n.op)](ev(n.left), ev(n.right))     # a 연산 b
        if isinstance(n, ast.UnaryOp): return ops[type(n.op)](ev(n.operand))             # -a
        raise ValueError("허용되지 않는 식")     # 함수 호출, 변수 등은 거부
    # eval()은 절대 쓰지 않는다: 모델이 "__import__('os').system(...)"을 보내면 그대로 실행되기 때문
    return str(ev(ast.parse(expression, mode="eval").body))

# 도구 이름 → (입력 검증용 모델, 실제 함수)
REGISTRY = {"calculator": (CalcArgs, calculator)}
# 모델에게 보여줄 메뉴판. input_schema는 Pydantic이 자동으로 만들어준다
TOOL_DEFS = [{"name": "calculator", "description": "사칙연산과 거듭제곱 식을 계산한다. 숫자 계산이 필요하면 반드시 사용한다.",
              "input_schema": CalcArgs.model_json_schema()}]

# ── ② 도구 실행기 ────────────────────────────────────────────
async def run_tool(name: str, args: dict) -> tuple[str, bool]:
    """(결과 문자열, 에러 여부)를 돌려준다. 절대 예외를 밖으로 던지지 않는다."""
    if name not in REGISTRY:                       # 모델이 없는 도구 이름을 지어낼 때가 있다
        return f"알 수 없는 도구: {name}. 사용 가능: {list(REGISTRY)}", True
    model, fn = REGISTRY[name]
    try:
        parsed = model.model_validate(args)        # 인자 형식 검증
    except ValidationError as e:
        # 무엇이 틀렸는지 알려주면 모델이 다음 턴에 고쳐서 다시 부른다
        return f"인자 오류: {e.errors(include_url=False)}. 스키마에 맞게 다시 호출하라.", True
    try:
        # to_thread: 동기 함수를 별도 스레드에서 실행 (이벤트 루프를 막지 않게)
        # wait_for: 20초 넘게 걸리면 포기 (멈춘 도구 하나가 전체를 붙잡지 않게)
        out = await asyncio.wait_for(asyncio.to_thread(fn, **parsed.model_dump()), timeout=20)
        return out[:8000], False                   # 결과가 너무 길면 잘라서 컨텍스트를 보호
    except Exception as e:
        return f"도구 실행 실패: {e!r}", True       # 실패도 "결과"로 돌려준다

# ── ③ 에이전트 루프 ──────────────────────────────────────────
async def agent(task: str, *, max_turns=10, token_budget=50_000, model="claude-haiku-4-5"):
    messages = [{"role": "user", "content": task}]   # 대화는 사용자의 과제로 시작
    used = 0                                          # 지금까지 쓴 토큰 (예산 감시용)
    for turn in range(max_turns):                     # 최대 턴 수 = 무한 루프 방지 장치
        resp = await client.messages.create(model=model, max_tokens=2048, tools=TOOL_DEFS,
                                            system="필요하면 도구를 써서 정확히 답하라.", messages=messages)
        used += resp.usage.input_tokens + resp.usage.output_tokens
        # 모델의 응답 블록(텍스트 + tool_use)을 "그대로" 대화에 추가해야 다음 요청에서 짝이 맞는다
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason != "tool_use":            # 도구를 안 불렀다 = 최종 답
            return "".join(b.text for b in resp.content if b.type == "text"), {"turns": turn + 1, "tokens": used}
        if used > token_budget:                       # 돈을 너무 많이 썼으면 중단
            return "토큰 예산 초과로 중단했습니다.", {"turns": turn + 1, "tokens": used}

        calls = [b for b in resp.content if b.type == "tool_use"]   # 이번 턴에 요청된 도구 호출들
        # 여러 도구를 동시에 실행한다 (1주차의 gather). 결과 순서는 calls 순서와 같다
        results = await asyncio.gather(*(run_tool(c.name, c.input) for c in calls))
        # 모든 결과를 "하나의" user 메시지에 담는다. 각 결과에는 짝이 되는 호출 id를 붙인다
        messages.append({"role": "user", "content": [
            {"type": "tool_result", "tool_use_id": c.id, "content": out, "is_error": err}
            for c, (out, err) in zip(calls, results)]})
    return "최대 턴 수에 도달했습니다.", {"turns": max_turns, "tokens": used}

if __name__ == "__main__":
    print(asyncio.run(agent("(1234*5678) + 2**20 을 계산하고 결과가 짝수인지 알려줘")))
```

### 4. 이 코드가 담고 있는 설계 결정

짧은 코드지만 줄마다 이유가 있습니다. 면접에서 "왜 이렇게 짰나요?"라고 물으면 이 표의 오른쪽 칸을 말할 수 있어야 합니다.

| 결정 | 이유 |
| --- | --- |
| 도구 오류를 예외로 올리지 않고 `is_error` 결과로 돌려줌 | 예외를 던지면 루프가 죽지만, 결과로 돌려주면 모델이 에러를 읽고 인자를 고치거나 다른 방법을 시도할 수 있다 |
| Pydantic으로 인자 검증 | 모델이 스키마를 어기는 일(필수 인자 누락, 숫자 자리에 문자열)은 생각보다 흔하다 |
| `max_turns`, `token_budget` | 모델이 끝내지 못하고 같은 일을 반복할 때 무한 루프와 비용 폭주를 막는 안전장치 |
| 결과 8,000자 절단 | 웹페이지 전문 같은 큰 결과가 컨텍스트(작업대)를 차지하는 것을 막는다 (11주차에서 정교하게) |
| 병렬 `gather` | 모델이 한 턴에 검색 3개를 부르면 하나씩이 아니라 동시에 실행해 시간을 줄인다 |
| `eval()` 대신 AST 파서 | 모델 출력은 신뢰할 수 없는 입력이다. 악의적인 문서를 읽은 모델이 위험한 코드를 보낼 수 있다 (17주차) |

## 심화

### 종료 조건은 생각보다 어렵다

"모델이 도구를 안 부르면 끝"은 가장 단순한 종료 조건이지만, 실무에서는 부족합니다. 모델이 대충 텍스트로 답하고 끝내버리거나, 반대로 끝없이 검색만 하기도 합니다. 그래서 다음 장치를 함께 씁니다.

- **명시적 종료 도구:** `submit_answer(answer, sources)` 같은 도구를 주고 "끝낼 때는 반드시 이걸 불러라"라고 합니다. 최종 답이 항상 정해진 형식(답 + 출처 목록)으로 나오니 후처리와 평가가 쉬워집니다.
- **진전 없음 감지:** 같은 도구를 같은 인자로 3번 이상 부르면 막다른 길에 빠진 것입니다. 루프를 멈추거나 "다른 방법을 시도하라"는 메시지를 끼워 넣습니다.
- **사람에게 질문:** `ask_user(question)` 도구를 주면, 정보가 부족할 때 추측하는 대신 루프를 멈추고 사람에게 묻습니다(7주차 interrupt).

### tool_choice로 행동 강제하기

`tool_choice` 옵션으로 모델의 도구 사용을 조절할 수 있습니다.

- `auto`(기본): 쓸지 말지 모델이 판단
- `any`: 반드시 도구 하나는 쓰라
- 특정 도구 지정: 반드시 이 도구를 쓰라
- `none`: 도구를 쓰지 말라

예를 들어 "이 문의를 분류해서 JSON으로 줘"처럼 **정해진 형식의 데이터만 필요할 때**는 `classify` 도구를 강제하면 항상 스키마에 맞는 인자(=원하는 JSON)를 받을 수 있습니다. 단, 강제하면 모델이 "이건 도구가 필요 없는 질문이야"라고 판단할 기회가 사라지므로, 일반 대화형 에이전트에는 `auto`를 씁니다.

### 구조화 출력의 세 가지 방법

LLM에게서 정해진 형식(JSON)의 출력을 받는 방법은 세 가지이고, 아래로 갈수록 확실합니다.

1. **프롬프트로 "JSON으로 답해" 요청 + 파싱:** 가장 약합니다. JSON이 중간에 잘리거나, ` ```json ` 같은 코드펜스가 붙거나, "다음은 결과입니다:" 같은 설명 문장이 섞입니다.
2. **도구 강제(tool_choice):** 위에서 본 방식. 도구 인자는 스키마를 따르도록 학습되어 있어서 훨씬 안정적이고, 대부분 공급자에서 동작합니다.
3. **네이티브 Structured Outputs:** 공급자가 모델이 글자를 고르는 단계 자체에서 스키마에 맞지 않는 글자를 원천 차단합니다(constrained decoding). 형식 오류가 사실상 없지만, 지원하는 스키마 기능에 제약이 있을 수 있습니다.

어느 방법이든 기억할 점: **형식이 맞는 것과 내용이 맞는 것은 다릅니다.** `{"amount": -50000}`은 형식상 완벽한 JSON이지만 환불 금액이 음수입니다. 값 범위나 비즈니스 규칙 같은 내용 검증은 Pydantic validator로 따로 합니다.

### 도구 개수와 정확도

도구가 많을수록 좋을 것 같지만, 메뉴판이 두꺼워지면 고르기 어려운 것처럼 **도구가 많아질수록 모델의 선택 정확도가 떨어지고**, 매 요청마다 보내는 도구 정의 토큰도 늘어납니다. 경험적으로 수십 개를 넘으면 문제가 드러납니다. 해법은 세 가지입니다.

1. 비슷한 도구를 합친다. (단, `file_ops(action=...)` 하나보다 명확한 도구 몇 개가 나을 때도 있으니 평가로 확인)
2. 상황에 필요한 도구만 보여준다 (동적 도구 로딩, 도구 검색).
3. 도구를 영역별 서브에이전트에게 나눠준다 (8주차).

### 모델 출력 = 신뢰할 수 없는 입력

모델이 만든 도구 인자는 **웹 폼에 사용자가 입력한 값과 같은 수준으로 의심**해야 합니다. 모델은 실수도 하고, 악의적인 문서를 읽고 조종당할 수도 있습니다. 그래서 파일 경로는 허용된 폴더 안인지, SQL은 읽기 전용인지, URL은 회사 내부망 주소가 아닌지(SSRF 공격 방지) 코드로 검사합니다. 17~18주차에서 본격적으로 다룹니다.

## 실습 과제: 3도구 리서치 에이전트

`weeks/w04_agent_loop/`

**요구사항**

1. 위 루프를 바탕으로 도구 3개를 갖춘 에이전트: `calculator`, `web_search`(Tavily·Brave 등 검색 API 또는 DuckDuckGo), `read_file`(지정된 `./sandbox` 폴더 안의 파일만).
2. `read_file`은 `../` 경로 탈출을 막는다(`Path.resolve()`로 검사).
3. 같은 도구·같은 인자 3회 반복 시 루프에 "다른 접근을 시도하라"는 메시지를 주입한다.
4. `submit_answer(answer: str, sources: list[str])` 종료 도구를 추가해 최종 답을 구조화한다.
5. 매 턴의 도구 호출·결과·토큰을 콘솔에 보기 좋게 출력하는 트레이스 출력기를 만든다.
6. 질문 10개로 돌려 평균 턴 수, 평균 토큰, 성공률을 표로 남긴다.

**채점 기준**

- [ ] 일부러 잘못된 인자를 유도해도(예: 계산식에 한글) 에이전트가 스스로 복구한다
- [ ] `read_file("../../.env")`가 차단된다
- [ ] 한 턴에 검색 2개를 동시에 부르는 경우가 트레이스에 보인다
- [ ] 10문항 성공률과 평균 비용을 README에 적었다

## 흔한 실수

- **`tool_result`를 빠뜨리거나 ID를 틀리게 넣음:** API가 400 에러를 냅니다. 모든 `tool_use`에는 같은 ID를 가진 `tool_result`가 바로 다음 메시지에 있어야 합니다. 주문서마다 영수증이 하나씩 있어야 하는 셈입니다.
- **도구 설명을 한 줄로 대충 씀:** 모델이 도구가 있는 줄 모르고 안 쓰거나, 엉뚱한 상황에 씁니다.
- **도구 에러를 예외로 던져 루프가 죽음:** 위 `run_tool`처럼 결과로 돌려주세요.
- **assistant 응답에서 텍스트만 추려서 저장:** `tool_use` 블록이 사라져서, 다음 요청의 `tool_result`가 짝 없는 결과가 되어 요청이 깨집니다. 응답 블록은 원본 그대로 보관하세요.

## 면접 질문

<details>
<summary>에이전트와 일반 LLM 애플리케이션(챗봇, RAG)의 차이는?</summary>

일반 LLM 앱은 개발자가 정한 고정 흐름(입력 → 검색 → 생성)으로 동작합니다. 에이전트는 LLM이 루프 안에서 **다음 행동(어떤 도구를, 어떤 인자로, 언제 멈출지)을 스스로 결정**하고, 행동의 결과를 관찰해 계획을 수정합니다. 그래서 개방형 문제에 강하지만 예측 가능성이 낮고 비용·지연이 크며 평가가 어렵습니다. 흐름을 미리 알 수 있는 문제라면 워크플로우가 더 낫습니다.
</details>

<details>
<summary>Function calling에서 모델은 실제로 함수를 실행하나요?</summary>

아닙니다. 모델은 "이 함수를 이 인자로 부르고 싶다"는 구조화된 요청만 생성합니다. 실행은 애플리케이션 코드가 하고, 결과를 다시 메시지로 넣어줍니다. 그래서 인자 검증, 권한 확인, 타임아웃, 결과 크기 제한 같은 통제는 전부 애플리케이션의 책임입니다. 공급자가 서버에서 실행해주는 도구(웹 검색, 코드 실행 등)도 있지만 원리는 같습니다.
</details>

<details>
<summary>도구 호출이 실패하면 어떻게 처리하나요?</summary>

예외로 루프를 죽이지 않고 에러 내용을 `is_error`가 붙은 도구 결과로 모델에게 돌려줍니다. 에러 메시지는 모델이 고칠 수 있게 구체적으로("order_id는 ORD-로 시작해야 함") 씁니다. 일시적 오류(타임아웃, 429)는 도구 계층에서 재시도하고, 같은 실패가 반복되면 루프에 경고를 주입하거나 중단합니다. 부수효과가 있는 도구는 재시도 전에 멱등성을 확인합니다.
</details>

<details>
<summary>에이전트가 무한 루프에 빠지지 않게 하려면?</summary>

최대 턴 수, 토큰·비용 예산, 벽시계 시간 제한을 하드 리밋으로 둡니다. 같은 도구·인자 반복 감지, 진전 없음 감지(새 정보가 없는 턴이 연속되면 경고), 명시적 종료 도구, 그리고 한도 도달 시 지금까지의 결과로 최선의 답을 내도록 하는 마무리 단계를 둡니다. 이 모든 것을 트레이스로 관측해 어느 지점에서 루프가 도는지 분석합니다.
</details>

<details>
<summary>좋은 도구(tool) 설계 원칙은?</summary>

① 이름과 설명이 모델에게 언제 쓰고 언제 쓰지 말아야 하는지 알려줄 것, ② 인자는 적고 명확하며 enum·형식 제약을 스키마에 담을 것, ③ 결과는 모델이 다음 결정을 내리는 데 필요한 만큼만 간결하게(페이지네이션, 요약), ④ 에러 메시지는 고치는 방법을 담을 것, ⑤ 비슷한 도구를 여러 개 두지 말 것, ⑥ 위험한 동작은 별도 도구로 분리해 승인 절차를 붙일 것. 그리고 도구 설계를 평가 세트로 검증합니다.
</details>
