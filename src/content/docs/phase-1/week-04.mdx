## 학습 목표

- 에이전트를 "LLM이 루프 안에서 도구를 골라 쓰며 스스로 다음 행동을 정하는 시스템"으로 정의하고 설명한다
- tool calling의 메시지 흐름을 바이트 수준에서 이해한다
- 오류 복구, 반복 제한, 예산 제한, 병렬 호출을 갖춘 루프를 100줄 안팎으로 구현한다
- 프레임워크가 내부에서 무엇을 해주는지 알게 되어, 이후 어떤 프레임워크도 빠르게 익힌다

## 에이전트의 최소 정의

```
while not done:
    response = LLM(system, tools, messages)
    if response에 도구 호출이 있으면:
        결과 = 도구 실행(response.tool_calls)
        messages += [response, 결과]
    else:
        done = True   # 모델이 최종 답을 냈다
```

이게 전부입니다. LangGraph, Agents SDK, Claude Agent SDK 모두 이 루프 위에 상태 관리, 스트리밍, 재시도, 관측, 사람 승인 같은 것을 얹은 것입니다. 이 루프를 직접 짜보면 "에이전트가 이상하게 동작할 때 어디를 봐야 하는지"를 알게 됩니다.

## 핵심 개념

### 1. Tool calling의 메시지 흐름

1. 개발자가 도구 목록(이름, 설명, 입력 JSON Schema)을 요청에 포함한다.
2. 모델이 도구를 쓰기로 하면 **텍스트 대신 tool_use 블록**(도구 이름, 인자, 호출 ID)을 내고 `stop_reason="tool_use"`로 멈춘다.
3. 개발자 코드가 도구를 실행한다. **모델은 도구를 실행하지 않는다.**
4. 결과를 `tool_result`(같은 호출 ID) 메시지로 대화에 붙여 다시 요청한다.
5. 모델이 결과를 보고 다음 도구를 부르거나 최종 답을 낸다.

```json
// 2단계에서 모델이 내는 블록 (Anthropic 형식)
{"type": "tool_use", "id": "toolu_01A", "name": "get_weather", "input": {"city": "서울"}}

// 4단계에서 붙이는 결과
{"role": "user", "content": [
  {"type": "tool_result", "tool_use_id": "toolu_01A", "content": "{\"temp_c\": 3, \"sky\": \"맑음\"}"}
]}
```

### 2. 도구 정의는 프롬프트다

모델은 도구의 **이름과 설명만 보고** 언제 무엇을 쓸지 정합니다. 도구 설명은 사람에게 쓰는 API 문서가 아니라 모델에게 쓰는 지시문입니다.

```python
TOOLS = [{
    "name": "search_orders",
    "description": (
        "고객의 주문을 조회한다. 고객이 주문 상태, 배송, 환불을 물을 때 사용한다. "
        "이메일 또는 주문번호 중 하나는 반드시 필요하다. 결과는 최근 주문 최대 10건이다. "
        "주문번호를 모르면 먼저 고객에게 이메일을 물어라."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "email": {"type": "string", "description": "고객 이메일"},
            "order_id": {"type": "string", "description": "'ORD-' 로 시작하는 주문번호"},
        },
    },
}]
```

좋은 도구 설명의 요소: **언제 쓰는지, 언제 쓰지 말아야 하는지, 필요한 인자, 결과 형태, 제약**. Anthropic은 이를 에이전트-컴퓨터 인터페이스(ACI) 설계라고 부르며, 사람용 UI(HCI)만큼 공을 들이라고 권합니다.

### 3. 맨손 루프 전체 코드

```python
# weeks/w04_agent_loop/agent.py
import json, asyncio
import anthropic
from pydantic import BaseModel, ValidationError

client = anthropic.AsyncAnthropic()

class CalcArgs(BaseModel):
    expression: str

def calculator(expression: str) -> str:
    import ast, operator as op
    ops = {ast.Add: op.add, ast.Sub: op.sub, ast.Mult: op.mul, ast.Div: op.truediv, ast.Pow: op.pow, ast.USub: op.neg}
    def ev(n):
        if isinstance(n, ast.Constant): return n.value
        if isinstance(n, ast.BinOp): return ops[type(n.op)](ev(n.left), ev(n.right))
        if isinstance(n, ast.UnaryOp): return ops[type(n.op)](ev(n.operand))
        raise ValueError("허용되지 않는 식")
    return str(ev(ast.parse(expression, mode="eval").body))   # eval() 금지: 보안

REGISTRY = {"calculator": (CalcArgs, calculator)}
TOOL_DEFS = [{"name": "calculator", "description": "사칙연산과 거듭제곱 식을 계산한다. 숫자 계산이 필요하면 반드시 사용한다.",
              "input_schema": CalcArgs.model_json_schema()}]

async def run_tool(name: str, args: dict) -> tuple[str, bool]:
    if name not in REGISTRY:
        return f"알 수 없는 도구: {name}. 사용 가능: {list(REGISTRY)}", True
    model, fn = REGISTRY[name]
    try:
        parsed = model.model_validate(args)
    except ValidationError as e:
        return f"인자 오류: {e.errors(include_url=False)}. 스키마에 맞게 다시 호출하라.", True
    try:
        out = await asyncio.wait_for(asyncio.to_thread(fn, **parsed.model_dump()), timeout=20)
        return out[:8000], False            # 결과 크기 제한
    except Exception as e:
        return f"도구 실행 실패: {e!r}", True

async def agent(task: str, *, max_turns=10, token_budget=50_000, model="claude-haiku-4-5"):
    messages = [{"role": "user", "content": task}]
    used = 0
    for turn in range(max_turns):
        resp = await client.messages.create(model=model, max_tokens=2048, tools=TOOL_DEFS,
                                            system="필요하면 도구를 써서 정확히 답하라.", messages=messages)
        used += resp.usage.input_tokens + resp.usage.output_tokens
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return "".join(b.text for b in resp.content if b.type == "text"), {"turns": turn + 1, "tokens": used}
        if used > token_budget:
            return "토큰 예산 초과로 중단했습니다.", {"turns": turn + 1, "tokens": used}
        calls = [b for b in resp.content if b.type == "tool_use"]
        results = await asyncio.gather(*(run_tool(c.name, c.input) for c in calls))   # 병렬 실행
        messages.append({"role": "user", "content": [
            {"type": "tool_result", "tool_use_id": c.id, "content": out, "is_error": err}
            for c, (out, err) in zip(calls, results)]})
    return "최대 턴 수에 도달했습니다.", {"turns": max_turns, "tokens": used}

if __name__ == "__main__":
    print(asyncio.run(agent("(1234*5678) + 2**20 을 계산하고 결과가 짝수인지 알려줘")))
```

### 4. 이 코드가 담고 있는 설계 결정

| 결정 | 이유 |
| --- | --- |
| 도구 오류를 예외로 올리지 않고 `is_error` 결과로 돌려줌 | 모델이 에러를 읽고 인자를 고치거나 다른 방법을 시도할 수 있다 |
| Pydantic으로 인자 검증 | 모델이 스키마를 어기는 일은 생각보다 흔하다 |
| `max_turns`, `token_budget` | 무한 루프와 비용 폭주를 막는 안전장치 |
| 결과 8,000자 절단 | 큰 결과가 컨텍스트를 잠식하는 것을 막는다 (11주차에서 정교하게) |
| 병렬 `gather` | 모델이 한 턴에 여러 도구를 부르면 동시에 실행 |
| `eval()` 대신 AST 파서 | 모델 출력은 신뢰할 수 없는 입력이다 (17주차) |

## 심화

### 종료 조건은 생각보다 어렵다

"모델이 도구를 안 부르면 끝"은 가장 단순한 종료 조건입니다. 실무에서는 추가로:

- **명시적 종료 도구:** `submit_answer(answer, sources)` 같은 도구를 주고 그것을 불러야 끝나게 하면, 최종 답이 항상 구조화됩니다.
- **진전 없음 감지:** 같은 도구를 같은 인자로 3번 이상 부르면 루프를 멈추거나 경고를 주입합니다.
- **사람에게 질문:** `ask_user(question)` 도구로 루프를 일시정지합니다(7주차 interrupt).

### tool_choice로 행동 강제하기

`tool_choice`를 `auto`(기본), `any`(반드시 도구 하나), 특정 도구, `none`으로 줄 수 있습니다. 구조화 추출만 필요하면 특정 도구를 강제해 JSON을 확실히 받습니다. 단, 강제하면 모델이 "도구가 필요 없다"고 판단할 기회가 사라집니다.

### 구조화 출력의 세 가지 방법

1. **프롬프트로 JSON 요청 + 파싱:** 가장 약함. 잘린 JSON, 코드펜스, 설명 문장이 섞입니다.
2. **도구 강제(tool_choice):** 스키마에 맞는 인자를 받는 방식. 대부분 공급자에서 동작합니다.
3. **네이티브 Structured Outputs:** 공급자가 디코딩 단계에서 스키마를 강제(constrained decoding)합니다. 형식 오류가 사실상 없지만 지원 스키마 기능에 제약이 있을 수 있습니다.

어느 쪽이든 **형식이 맞는 것과 내용이 맞는 것은 다릅니다.** 내용 검증(값 범위, 비즈니스 규칙)은 Pydantic validator로 따로 합니다.

### 도구 개수와 정확도

도구가 많아질수록 선택 정확도가 떨어지고 도구 정의 토큰이 늘어납니다. 경험적으로 수십 개가 넘으면 문제가 드러납니다. 해법은 ① 도구를 기능별로 합치고(`file_ops(action=...)`보다 명확한 몇 개가 나을 때도 있음), ② 상황별로 필요한 도구만 노출하고(동적 도구 로딩, 도구 검색), ③ 서브에이전트에 도구를 나눠주는 것입니다(8주차).

### 모델 출력 = 신뢰할 수 없는 입력

모델이 만든 인자는 사용자 입력과 같은 수준으로 의심해야 합니다. 파일 경로는 허용 디렉터리 안인지, SQL은 읽기 전용인지, URL은 내부망이 아닌지(SSRF) 검사합니다. 17~18주차에서 본격적으로 다룹니다.

## 실습 과제: 3도구 리서치 에이전트

`weeks/w04_agent_loop/`

**요구사항**

1. 위 루프를 바탕으로 도구 3개를 갖춘 에이전트: `calculator`, `web_search`(Tavily·Brave 등 검색 API 또는 DuckDuckGo), `read_file`(지정된 `./sandbox` 폴더 안의 파일만).
2. `read_file`은 `../` 경로 탈출을 막는다(`Path.resolve()`로 검사).
3. 같은 도구·같은 인자 3회 반복 시 루프에 "다른 접근을 시도하라"는 메시지를 주입한다.
4. `submit_answer(answer: str, sources: list[str])` 종료 도구를 추가해 최종 답을 구조화한다.
5. 매 턴의 도구 호출·결과·토큰을 콘솔에 보기 좋게 출력하는 트레이스 출력기를 만든다.
6. 질문 10개로 돌려 평균 턴 수, 평균 토큰, 성공률을 표로 남긴다.

**채점 기준**

- [ ] 일부러 잘못된 인자를 유도해도(예: 계산식에 한글) 에이전트가 스스로 복구한다
- [ ] `read_file("../../.env")`가 차단된다
- [ ] 한 턴에 검색 2개를 동시에 부르는 경우가 트레이스에 보인다
- [ ] 10문항 성공률과 평균 비용을 README에 적었다

## 흔한 실수

- `tool_result`를 assistant 메시지 뒤에 빠뜨리거나 ID를 틀리게 넣음 → API 400 에러. 모든 tool_use에는 짝이 되는 tool_result가 있어야 합니다.
- 도구 설명을 한 줄로 대충 씀 → 모델이 도구를 안 쓰거나 엉뚱하게 씁니다.
- 도구 에러를 예외로 던져 루프가 죽음 → 결과로 돌려주세요.
- assistant의 응답 블록을 텍스트만 추려서 저장 → tool_use 블록이 사라져 다음 요청이 깨집니다. 원본 블록을 그대로 보관하세요.

## 면접 질문

<details>
<summary>에이전트와 일반 LLM 애플리케이션(챗봇, RAG)의 차이는?</summary>

일반 LLM 앱은 개발자가 정한 고정 흐름(입력 → 검색 → 생성)으로 동작합니다. 에이전트는 LLM이 루프 안에서 **다음 행동(어떤 도구를, 어떤 인자로, 언제 멈출지)을 스스로 결정**하고, 행동의 결과를 관찰해 계획을 수정합니다. 그래서 개방형 문제에 강하지만 예측 가능성이 낮고 비용·지연이 크며 평가가 어렵습니다. 흐름을 미리 알 수 있는 문제라면 워크플로우가 더 낫습니다.
</details>

<details>
<summary>Function calling에서 모델은 실제로 함수를 실행하나요?</summary>

아닙니다. 모델은 "이 함수를 이 인자로 부르고 싶다"는 구조화된 요청만 생성합니다. 실행은 애플리케이션 코드가 하고, 결과를 다시 메시지로 넣어줍니다. 그래서 인자 검증, 권한 확인, 타임아웃, 결과 크기 제한 같은 통제는 전부 애플리케이션의 책임입니다. 공급자가 서버에서 실행해주는 도구(웹 검색, 코드 실행 등)도 있지만 원리는 같습니다.
</details>

<details>
<summary>도구 호출이 실패하면 어떻게 처리하나요?</summary>

예외로 루프를 죽이지 않고 에러 내용을 `is_error`가 붙은 도구 결과로 모델에게 돌려줍니다. 에러 메시지는 모델이 고칠 수 있게 구체적으로("order_id는 ORD-로 시작해야 함") 씁니다. 일시적 오류(타임아웃, 429)는 도구 계층에서 재시도하고, 같은 실패가 반복되면 루프에 경고를 주입하거나 중단합니다. 부수효과가 있는 도구는 재시도 전에 멱등성을 확인합니다.
</details>

<details>
<summary>에이전트가 무한 루프에 빠지지 않게 하려면?</summary>

최대 턴 수, 토큰·비용 예산, 벽시계 시간 제한을 하드 리밋으로 둡니다. 같은 도구·인자 반복 감지, 진전 없음 감지(새 정보가 없는 턴이 연속되면 경고), 명시적 종료 도구, 그리고 한도 도달 시 지금까지의 결과로 최선의 답을 내도록 하는 마무리 단계를 둡니다. 이 모든 것을 트레이스로 관측해 어느 지점에서 루프가 도는지 분석합니다.
</details>

<details>
<summary>좋은 도구(tool) 설계 원칙은?</summary>

① 이름과 설명이 모델에게 언제 쓰고 언제 쓰지 말아야 하는지 알려줄 것, ② 인자는 적고 명확하며 enum·형식 제약을 스키마에 담을 것, ③ 결과는 모델이 다음 결정을 내리는 데 필요한 만큼만 간결하게(페이지네이션, 요약), ④ 에러 메시지는 고치는 방법을 담을 것, ⑤ 비슷한 도구를 여러 개 두지 말 것, ⑥ 위험한 동작은 별도 도구로 분리해 승인 절차를 붙일 것. 그리고 도구 설계를 평가 세트로 검증합니다.
</details>
