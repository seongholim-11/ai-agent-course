## 가장 중요한 원칙: 가장 단순한 것부터

이번 주의 핵심 단어는 두 개입니다.

- **워크플로우:** 일의 순서를 **코드가** 미리 정해둔 방식. "1번 하고, 2번 하고, 결과가 이러면 3번" 같은 요리 레시피와 같습니다. LLM은 각 단계 안에서 글을 쓰거나 판단하는 일만 합니다.
- **에이전트:** 다음에 무엇을 할지 **모델이** 정하는 방식. 재료만 주고 "알아서 저녁 차려줘"라고 맡기는 것과 같습니다.

Anthropic의 글 "Building effective agents"가 가장 강조하는 결론은 **가능한 가장 단순한 해법부터 시작하고, 그걸로 부족할 때만 복잡도를 올리라**는 것입니다. 아래 사다리를 한 칸씩만 올라가세요.

```
단일 LLM 호출 (+ 검색, 예시)                 ← 대부분의 기능은 여기서 해결된다
   ↓ 부족하면
워크플로우 (Chaining / Routing / Parallelization / Orchestrator-Workers / Evaluator-Optimizer)
   ↓ 흐름을 미리 알 수 없으면
에이전트 (모델이 루프 안에서 도구와 다음 단계를 정함)
   ↓ 하나의 컨텍스트로 감당이 안 되면
멀티 에이전트
```

왜 단순한 쪽이 좋을까요? 에이전트는 **유연성을 얻는 대신 비용, 지연, 예측 불가능성, 디버깅 난이도라는 값을 치릅니다.** 매번 경로가 달라지니 같은 질문에 같은 품질이 나온다는 보장이 없고, 문제가 생겨도 어디서 틀렸는지 찾기 어렵습니다. 면접에서 "이 문제에 왜 에이전트를 썼나요?"라고 물으면 이 트레이드오프로 답할 수 있어야 합니다.

## 핵심 패턴

### 1. Prompt Chaining

큰 일을 **순서가 정해진 작은 단계**로 나누고, 앞 단계의 결과를 다음 단계의 입력으로 넘깁니다. 공장의 조립 라인과 같습니다. 그리고 단계 사이에 **코드로 된 검문소(gate)**를 둬서, 불량품이 다음 공정으로 넘어가지 않게 합니다.

```python
# 1단계: 개요 만들기
outline = await llm(f"다음 주제로 블로그 개요를 5개 항목으로: {topic}")
# 검문소: LLM이 아니라 "코드"로 확인한다. 항목이 정확히 5개인가?
if len(parse_items(outline)) != 5:
    outline = await llm(f"정확히 5개 항목으로 다시: {outline}")   # 아니면 한 번 고치게 한다
# 2단계: 개요를 바탕으로 본문 쓰기 (검증된 개요만 들어온다)
draft = await llm(f"개요에 따라 본문 작성:\n{outline}")
# 3단계: 교정
final = await llm(f"다음 글을 존댓말·맞춤법 기준으로 교정:\n{draft}")
```

한 번에 "개요 짜고 본문 쓰고 교정까지 해"라고 하는 것보다, 각 호출이 **더 쉬운 한 가지 일**만 하니 정확도가 오릅니다. 대신 호출이 여러 번이라 시간이 더 걸립니다.

### 2. Routing

입력을 먼저 **분류**해서, 종류별로 가장 잘 맞는 처리 경로로 보냅니다. 병원 접수처에서 증상을 듣고 내과·외과로 안내하는 것과 같습니다. 분류는 쉬운 일이라 작고 싼 모델 + 구조화 출력(4주차)으로 빠르게 합니다.

```python
from typing import Literal
from pydantic import BaseModel

class Route(BaseModel):
    # Literal: 네 가지 중 하나만 나오게 강제 → 분기 코드가 안전해진다
    category: Literal["refund", "shipping", "tech_support", "other"]
    confidence: float          # 모델이 스스로 매긴 확신도 (0~1)

# 작은 모델로 분류. 결과는 항상 Route 형식으로 받는다
route = await structured_llm(Route, f"고객 문의를 분류하라: {msg}", model="small")
if route.confidence < 0.6:
    route.category = "other"           # 애매하면 엉뚱한 전문 경로보다 안전한 기본 경로로
# 분류 결과에 따라 처리 함수를 고른다
handler = {"refund": refund_flow, "shipping": shipping_flow, ...}[route.category]
```

각 경로의 프롬프트를 그 일에만 맞게 최적화할 수 있다는 것이 큰 장점입니다. 라우팅은 **모델 라우팅**에도 씁니다. 쉬운 질문은 작은 모델, 어려운 질문은 큰 모델로 보내서 비용을 크게 줄이는 방법이고, 19주차 비용 최적화의 핵심입니다.

### 3. Parallelization

서로 기다릴 필요가 없는 일을 **동시에** 실행합니다(1주차 asyncio). 두 가지 방식이 있습니다.

- **Sectioning(나눠서 동시에):** 독립적인 하위 작업을 동시에 실행합니다. 보고서의 각 섹션을 동시에 쓰거나, 본 답변을 만드는 동안 옆에서 "이 질문이 위험한가?" 검사를 같이 돌리는 식입니다.
- **Voting(같은 일을 여러 번):** 같은 작업을 여러 번 시켜 다수결로 정하거나, 가장 엄격한 결과를 채택합니다. 예를 들어 코드 취약점 검사를 3번 시켜서 한 번이라도 "위험"이 나오면 사람이 보게 합니다. 의사 여러 명에게 소견을 받는 것과 같습니다.

### 4. Orchestrator–Workers

팀장(중앙 LLM)이 일을 보고 **그때그때** 쪼개서 팀원(워커)들에게 나눠주고, 결과를 모아 합칩니다. Parallelization과의 차이는 **하위 작업의 개수와 내용을 미리 알 수 없다**는 점입니다. "이 버그를 고쳐줘"라는 요청은 파일 1개를 고칠지 7개를 고칠지 해봐야 압니다. 여러 파일 수정, 여러 각도의 리서치에 씁니다. 8주차에서 깊게 다룹니다.

### 5. Evaluator–Optimizer

작가(생성자)가 초안을 쓰고, 편집자(평가자)가 피드백을 주면, 작가가 고쳐 쓰는 루프입니다. **평가 기준이 명확하고, 피드백을 반영하면 실제로 나아지는 작업**에 맞습니다. 번역의 어색한 표현 다듬기, 테스트를 통과할 때까지 코드 고치기, 검색 쿼리 개선 같은 일입니다. 편집자가 영원히 만족하지 않을 수 있으니 **반복 횟수 상한**을 꼭 둡니다.

### 6. ReAct (Reason + Act)

**생각(Thought) → 행동(Action) → 관찰(Observation)**을 반복하는 패턴입니다. 형사가 "범인은 2층에 있을 것 같다(생각) → 2층에 가본다(행동) → 발자국이 3층으로 이어진다(관찰) → 3층으로 가야겠다(생각)…"처럼 단서를 보며 다음 행동을 정하는 것과 같습니다.

2022년 논문에서 제안되어 지금 에이전트 루프의 원형이 되었습니다. 4주차에 만든 tool calling 루프가 바로 ReAct를 API 수준에서 구현한 것이고, 최신 추론 모델은 "생각" 단계를 내부 추론 토큰으로 처리합니다.

| 장점 | 단점 |
| --- | --- |
| 관찰 결과에 따라 계획을 바꿀 수 있다 | 한 번에 한 걸음씩이라 턴이 많고 느리다 |
| 추론 과정이 보여 디버깅이 쉽다 | 초반에 잘못된 방향으로 가면 계속 헤맨다 |
| 구현이 단순하다 | 긴 작업에서 컨텍스트가 빠르게 커진다 |

이 단점을 보완한 방법이 **Plan-and-Execute**(먼저 전체 계획을 세우고 실행하다가, 필요하면 계획을 다시 세움)와 **todo 리스트 도구**(12주차)입니다. 지도 없이 한 걸음씩 길을 찾는 대신, 먼저 경로를 그려두고 걸으면서 수정하는 방식입니다.

## 심화

### 선택 기준 표

어떤 패턴을 쓸지 고민될 때 위에서부터 질문해보세요.

| 질문 | 예라면 |
| --- | --- |
| 단계와 순서를 미리 알 수 있는가? | 워크플로우 |
| 단계 수가 입력에 따라 크게 달라지는가? | 에이전트 또는 Orchestrator-Workers |
| 실패 비용이 큰가(결제, 삭제, 외부 발송)? | 워크플로우 + 사람 승인 |
| 지연 요구가 엄격한가(< 2초)? | 단일 호출 또는 라우팅 |
| 결과 검증이 코드로 가능한가? | Evaluator-Optimizer 또는 자동 재시도 |
| 탐색 범위가 넓고 독립적인가? | Parallelization / 멀티 에이전트 |

### 하이브리드가 정답인 경우가 많다

실무 시스템은 "전부 워크플로우" 아니면 "전부 에이전트"가 아니라, 대부분 **워크플로우 안에 작은 에이전트가 박힌** 형태입니다. 예를 들어 고객센터 시스템은 이렇게 짭니다.

1. 문의 분류 (라우팅 = 워크플로우)
2. 환불 요청 → 정해진 단계 + 사람 승인 (워크플로우. 돈이 걸린 일은 예측 가능해야 함)
3. 기술 문의 → 문서를 이리저리 검색하는 에이전트 (어떤 문서를 봐야 할지 미리 알 수 없음)

이렇게 하면 **위험한 부분은 결정적으로(항상 같은 방식으로), 개방적인 부분은 유연하게** 다룰 수 있습니다.

### 로우코드(n8n) vs SDK vs 직접 구현

같은 에이전트를 만드는 도구도 여러 층이 있습니다.

| | n8n 같은 로우코드 | Agents SDK (OpenAI, Claude 등) | 직접 구현 / LangGraph |
| --- | --- | --- | --- |
| 한 줄 설명 | 블록을 끌어다 연결해서 만든다 | 에이전트에 필요한 부품을 라이브러리로 제공 | 흐름과 상태를 코드로 직접 짠다 |
| 강점 | SaaS 연동 수백 개, 비개발자와 협업, 빠른 프로토타입 | 루프·핸드오프·가드레일·트레이싱이 기본 제공 | 상태·흐름을 완전히 통제, 테스트 용이 |
| 약점 | 복잡한 분기·테스트·버전 관리가 어려움 | 프레임워크의 추상화에 묶임 | 직접 만들 것이 많음 |
| 적합 | 사내 자동화, 알림, 데이터 이동 | 표준적인 에이전트 서비스 | 복잡한 프로덕션 에이전트 |

면접에서는 "n8n을 써봤다"보다 **"이런 기준으로 이걸 골랐다"**를 말할 수 있는 것이 중요합니다. 이번 주 실습이 바로 그 근거를 만드는 과정입니다.

## 실습 과제: 같은 문제, 세 가지 구현

**문제:** "주제를 받으면 웹에서 최신 자료 5개를 찾아 핵심을 요약하고, 출처를 단 뉴스레터(마크다운)를 만든다."

1. **워크플로우 버전:** 검색 쿼리 생성 → 병렬 검색 → 결과 요약(Parallelization) → 뉴스레터 작성 → 형식 검증(gate). 직접 파이썬으로.
2. **에이전트 버전:** 4주차 루프에 `web_search`, `fetch_page`, `submit_newsletter` 도구를 주고 모델이 알아서 하게.
3. **프레임워크 버전:** n8n 또는 OpenAI Agents SDK 중 하나로.
4. 세 버전을 같은 주제 5개로 돌려 **비용, 지연, 출처 수, 품질(직접 1~5점)**을 표로 비교한다.
5. 라우터를 추가한다: 주제가 "간단한 정의 질문"이면 검색 없이 단일 호출로 답한다.

**채점 기준**

- [ ] 비교표에 3개 버전 × 5개 주제의 수치가 있다
- [ ] "이 문제에는 ○○ 버전이 맞다"는 결론과 근거를 README에 3문장으로 썼다
- [ ] 라우터 정확도를 10개 예시로 측정했다

## 흔한 실수

- **모든 것을 에이전트로 만듦:** 순서가 뻔한 일까지 모델에게 맡기면 느리고 비싸고 결과가 들쭉날쭉합니다.
- **체인의 단계 사이에 검증 없이 넘김:** 1단계의 작은 오류가 2단계, 3단계를 거치며 점점 커집니다. 조립 라인에 검사원이 없는 것과 같습니다.
- **라우터 분류 결과를 그대로 신뢰:** 분류기도 틀립니다. 확신도가 낮을 때 보낼 안전한 기본 경로(사람 상담원, 일반 답변)가 필요합니다.

## 면접 질문

<details>
<summary>워크플로우와 에이전트는 어떻게 구분하고, 언제 무엇을 쓰나요?</summary>

워크플로우는 LLM과 도구가 **코드로 미리 정한 경로**를 따라 실행되고, 에이전트는 **LLM이 동적으로 경로를 결정**합니다. 단계를 미리 알 수 있고 예측 가능성·비용·지연이 중요하면 워크플로우, 단계 수와 내용을 미리 알 수 없는 개방형 문제(리서치, 코딩, 복잡한 문제 해결)면 에이전트를 씁니다. 실무에서는 위험한 부분은 워크플로우로, 탐색이 필요한 부분만 에이전트로 만드는 하이브리드가 흔합니다.
</details>

<details>
<summary>ReAct 패턴을 설명하고 한계를 말해보세요.</summary>

ReAct는 추론(Thought)과 행동(Action), 관찰(Observation)을 번갈아 반복해 외부 정보를 바탕으로 계획을 고쳐가는 패턴입니다. 관찰에 적응할 수 있고 해석이 쉽지만, 한 단계씩 진행해 턴이 많아 느리고 비싸며, 초기 판단 오류에서 헤어나기 어렵고, 긴 작업에서 컨텍스트가 커집니다. Plan-and-Execute, todo 리스트 도구, 병렬 도구 호출, 재계획(replanning), 서브에이전트로 보완합니다.
</details>

<summary>Evaluator-Optimizer 패턴은 언제 효과가 있나요?</summary>
