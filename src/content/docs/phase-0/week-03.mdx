## 학습 목표

- LLM이 다음 토큰을 예측하는 방식과 그 결과(환각, 비결정성)를 설명한다
- 컨텍스트 윈도우, 토큰, 샘플링 파라미터가 에이전트 설계에 주는 제약을 안다
- 주요 공급자 API의 메시지 구조를 이해하고 직접 호출한다
- 요청 비용을 계산하고 프롬프트 캐싱으로 줄인다
- 임베딩이 무엇이고 어디에 쓰는지 안다

## 핵심 개념

### 1. LLM은 무엇을 하는가

LLM이 하는 일은 놀랄 만큼 단순합니다. **지금까지의 글을 보고, 다음에 올 조각(토큰)이 무엇일지 확률을 계산해서 하나를 고른다.** 그리고 고른 조각을 글 뒤에 붙여서 같은 일을 또 합니다. 휴대폰 키보드의 "다음 단어 추천"을 엄청나게 똑똑하게 만든 것이라고 생각하면 됩니다.

이 단순한 원리에서 에이전트를 설계할 때 꼭 알아야 할 성질 세 가지가 나옵니다.

- **환각(hallucination):** 모델은 "그럴듯한" 다음 조각을 고를 뿐, 그게 사실인지 확인하지 않습니다. 그래서 모르는 것도 자신 있게 지어냅니다. 해결책은 사실을 모델의 기억에 맡기지 않고 검색·도구로 **넣어주는 것**(RAG, 6주차)과, 나온 결과를 **검증하는 것**입니다.
- **비결정성:** 같은 질문을 해도 답이 조금씩 다를 수 있습니다. "가장 확률 높은 것만 골라라"(temperature 0)로 설정해도 서버가 여러 요청을 묶어 계산하는 방식, 계산 순서의 미세한 차이 때문에 결과가 달라질 수 있습니다. 그래서 평가할 때 같은 문제를 여러 번 돌려봅니다(14주차).
- **상태 없음:** 모델은 이전 호출을 전혀 기억하지 않습니다. ChatGPT가 대화를 기억하는 것처럼 보이는 건, 매번 **지금까지의 대화 전체를 다시 보내주기** 때문입니다. "메모리"는 모델이 아니라 우리가 만드는 애플리케이션이 구현하는 기능입니다.

### 2. 토큰과 컨텍스트 윈도우

**토큰**은 모델이 글을 읽고 쓰는 단위로, 단어보다 작은 조각입니다. "unbelievable"이 "un" + "believ" + "able"로 쪼개지는 식입니다. 영어는 대략 1토큰이 4글자 정도인데, **한국어는 같은 뜻을 표현하는 데 영어보다 토큰이 더 많이 듭니다.** API 요금은 토큰 수로 매겨지므로, 한국어 서비스는 비용을 추정할 때 이 점을 반영해야 합니다.

**컨텍스트 윈도우**는 모델이 한 번에 다룰 수 있는 **입력 + 출력 토큰의 최대 합**입니다. 모델의 "작업대 크기"라고 보면 됩니다. 요즘은 수십만~백만 토큰을 지원하는 모델이 많지만, 작업대가 넓다고 다 올려두면 좋은 건 아닙니다.

- 길수록 **비싸고 느립니다**(요금과 처리 시간이 입력 길이에 비례).
- 길수록 **중간에 있는 정보를 놓치는 경향**이 있습니다. 긴 문서의 처음과 끝은 잘 보는데 가운데는 흐릿하게 보는 현상(lost in the middle), 입력이 길어질수록 전반적으로 정확도가 떨어지는 현상(context rot)이 알려져 있습니다.

그래서 "무엇을 작업대에 올릴지 고르는 기술"이 중요해지고, 이게 11주차 컨텍스트 엔지니어링의 출발점입니다.

### 3. 메시지 구조

LLM API에 요청을 보낼 때는 대화를 **역할(role)이 붙은 메시지 목록**으로 보냅니다. 공급자마다 이름은 조금 다르지만 구조는 같습니다.

- `system`: 모델의 역할과 규칙 ("너는 고객센터 상담원이다")
- `user`: 사용자가 한 말
- `assistant`: 모델이 이전에 한 답

```python
import anthropic
client = anthropic.Anthropic()          # 환경 변수 ANTHROPIC_API_KEY를 자동으로 읽는다

resp = client.messages.create(
    model="claude-haiku-4-5",           # 실습은 작고 싼 모델로
    max_tokens=512,                     # 출력 최대 길이 (이걸 넘으면 답이 잘린다)
    system="너는 간결하게 답하는 한국어 비서다.",   # 시스템 프롬프트: 역할·규칙
    messages=[
        # 모델은 이전 대화를 기억하지 못하므로, 지난 대화를 매번 전부 다시 보낸다
        {"role": "user", "content": "SSE가 뭐야?"},
        {"role": "assistant", "content": "서버가 클라이언트로 이벤트를 보내는 HTTP 스트림이야."},
        {"role": "user", "content": "WebSocket이랑 차이는?"},   # 이번에 새로 물은 것
    ],
)
print(resp.content[0].text)   # 답변 텍스트 (content는 블록 목록이라 [0]으로 첫 블록을 꺼낸다)
print(resp.usage)             # input_tokens, output_tokens, cache_* 토큰 → 비용 계산의 근거
```

```python
from openai import OpenAI
client = OpenAI()                       # 환경 변수 OPENAI_API_KEY를 자동으로 읽는다
resp = client.responses.create(
    model="gpt-5-mini",
    instructions="너는 간결하게 답하는 한국어 비서다.",   # Anthropic의 system에 해당
    input="SSE가 뭐야?",
)
print(resp.output_text, resp.usage)     # 답변 텍스트와 사용량
```

두 코드를 비교해 보면 이름(`system` vs `instructions`)만 다를 뿐, "역할 지시 + 대화 + 출력 설정"이라는 뼈대는 같습니다. 이번 주 실습에서 이 차이를 감춰주는 공통 클라이언트를 만듭니다.

<Aside type="caution" title="모델 이름">

### 4. 샘플링 파라미터

모델은 다음 토큰 후보마다 확률을 매깁니다(예: "환불" 60%, "반품" 30%, "교환" 10%). **샘플링 파라미터**는 이 후보 중에서 어떻게 고를지 정하는 손잡이입니다.

| 파라미터 | 의미 | 에이전트에서 |
| --- | --- | --- |
| `temperature` | 낮추면 확률 높은 후보만 고집하고(안정적), 높이면 낮은 후보도 자주 고른다(창의적) | 도구 선택·추출·분류는 낮게, 아이디어 생성은 높게 |
| `top_p` | 확률 높은 순으로 더해서 p가 될 때까지의 후보 안에서만 고른다 | 보통 temperature와 둘 중 하나만 조정 |
| `max_tokens` | 출력 길이 상한 | 너무 작으면 도구 호출 JSON이 중간에 잘려 파싱 실패 |
| `stop` | 이 문자열이 나오면 생성 중단 | 구조화 출력을 쓰면 거의 안 씀 |

**추론(reasoning/thinking) 모델**은 답을 내기 전에 속으로 "생각하는" 토큰을 먼저 만듭니다. 수학 문제를 풀 때 연습장에 풀이를 쓰는 것과 같습니다. 추론 예산(effort, budget)을 올리면 어려운 계획·코딩 문제를 더 잘 풀지만, 그 생각 토큰도 돈과 시간이 듭니다. 그래서 "어느 단계에서 추론을 켤지"(예: 계획 세우기는 켜고, 단순 분류는 끄기)가 하나의 설계 결정입니다.

### 5. 비용 계산

```
요청 비용 = 입력토큰 × 입력단가 + 출력토큰 × 출력단가 (+ 캐시 쓰기/읽기 단가)
```

단가는 보통 "100만 토큰당 몇 달러"로 표시되고, **출력 단가가 입력보다 4~5배 비쌉니다.** 그러면 출력만 줄이면 될 것 같지만, 에이전트는 사정이 다릅니다.

에이전트는 도구를 쓸 때마다 모델을 다시 부르는데, 모델은 기억이 없으니 **매 턴마다 지금까지의 대화 전체를 다시 입력**합니다. 예를 들어 10턴짜리 루프에서 턴마다 대화가 2,000토큰씩 늘어나면:

- 1턴: 2,000 입력
- 2턴: 4,000 입력 (1턴 내용 + 새 내용)
- …
- 10턴: 20,000 입력
- **합계: 2k + 4k + … + 20k = 110,000 토큰**

대화 길이는 턴 수에 비례해 늘지만, 총 입력량은 **턴 수의 제곱에 비례해** 늘어납니다. 그래서 에이전트에서는 입력 비용이 지배적이고, 턴 수를 줄이고 대화를 짧게 유지하는 것이 비용 절감의 핵심이 됩니다.

### 6. 프롬프트 캐싱

매 턴 대화 전체를 다시 보낸다면, 앞부분은 매번 똑같다는 뜻입니다. 공급자는 이걸 이용해 **이전 요청과 앞부분(prefix)이 똑같은 입력**을 저장해뒀다가 재사용하고, 그 부분은 할인된 가격(대략 정가의 10% 수준)과 짧은 지연으로 처리해줍니다. 이게 **프롬프트 캐싱**입니다.

핵심 규칙은 **"앞에서부터 한 글자라도 다르면 그 뒤는 전부 캐시가 안 된다"**는 것입니다.

- 그래서 순서가 중요합니다: 시스템 프롬프트 → 도구 정의 → 고정 문서 → 대화. **변하지 않는 것을 앞에** 둡니다.
- 시스템 프롬프트 맨 앞에 현재 시각이나 요청 ID를 넣으면, 맨 앞이 매번 달라지니 캐시가 매번 깨집니다.
- 에이전트 루프는 매 턴 앞부분(시스템 프롬프트, 도구, 이전 대화)이 같으므로 캐싱 효과가 아주 큽니다. 19주차에서 적중률을 측정합니다.

```python
resp = client.messages.create(
    model="claude-haiku-4-5", max_tokens=512,
    # system을 블록 목록으로 주고, 캐시할 블록에 cache_control 표시를 단다
    # → "여기까지의 내용을 캐시해줘"라는 뜻 (Anthropic 방식. OpenAI는 자동 캐싱)
    system=[{"type": "text", "text": LONG_POLICY_DOC, "cache_control": {"type": "ephemeral"}}],
    messages=[{"role": "user", "content": "환불 규정 요약해줘"}],   # 변하는 부분은 뒤에
)
# 첫 호출: cache_creation(캐시 저장) 토큰이 잡힌다 / 두 번째 호출부터: cache_read(캐시 읽기) 토큰이 잡힌다
print(resp.usage.cache_creation_input_tokens, resp.usage.cache_read_input_tokens)
```

### 7. 임베딩

**임베딩**은 글의 "의미"를 숫자 목록(벡터)으로 바꾼 것입니다. 지도에서 장소를 위도·경도 두 숫자로 나타내듯, 임베딩은 글을 수백~수천 개의 숫자로 나타냅니다. 이때 **뜻이 비슷한 글은 가까운 위치에** 놓입니다. "환불은 7일 이내 가능합니다"와 "구매 후 일주일 안에 반품할 수 있어요"는 단어가 거의 다르지만 위치는 가깝습니다.

두 벡터가 얼마나 같은 방향을 가리키는지 재는 값이 **코사인 유사도**이고, 1에 가까울수록 의미가 비슷합니다. RAG 검색(질문과 비슷한 문서 찾기), 중복 제거, 비슷한 것끼리 묶기(클러스터링), 라우팅, 메모리 검색에 씁니다.

```python
import numpy as np
from openai import OpenAI
c = OpenAI()
texts = ["환불은 7일 이내 가능합니다", "구매 후 일주일 안에 반품할 수 있어요", "배송은 2일 걸립니다"]
# 세 문장을 한 번에 임베딩 → 각 문장이 숫자 1,536개짜리 벡터가 된다
E = np.array([d.embedding for d in c.embeddings.create(model="text-embedding-3-small", input=texts).data])
# 각 벡터를 길이 1로 정규화한다 → 이후 내적(@)이 곧 코사인 유사도가 된다
E /= np.linalg.norm(E, axis=1, keepdims=True)
print(E @ E.T)   # 3×3 유사도 표. 0번(환불)과 1번(반품)의 값이 가장 높게 나온다
```

## 심화

### 지연 시간의 구성

사용자가 느끼는 "느리다"는 두 부분으로 나뉩니다.

- **TTFT(Time To First Token, 첫 토큰까지 시간):** 모델이 입력 전체를 읽고(prefill) 첫 글자를 내놓기까지의 시간입니다. 입력이 길수록 길어지고, 캐시가 적중하면 크게 줄어듭니다. 사용자가 "반응이 있다"고 느끼는 시점입니다.
- **TPOT(Time Per Output Token, 출력 토큰당 시간):** 그 뒤로 한 글자씩 써 내려가는 속도입니다. 총 출력 시간은 출력 토큰 수에 비례합니다.

에이전트 전체 지연은 `Σ(턴별 TTFT + 출력 시간) + 도구 실행 시간`입니다. 턴마다 모델을 다시 부르니 이 비용이 턴 수만큼 반복됩니다. 그래서 **턴 수를 줄이는 것**(도구 여러 개를 한 턴에 동시에 호출, 처음부터 좋은 계획 세우기)이 가장 큰 지연 개선입니다.

### 공급자 추상화 계층을 어떻게 만들까

Claude와 GPT를 바꿔가며 쓰려면, 그 차이를 감춰주는 얇은 중간 계층이 필요합니다. 하지만 너무 두껍게 감추면 공급자만의 좋은 기능(캐싱, 추론 예산, 서버 측 도구)을 못 쓰게 됩니다. 여러 나라 콘센트에 쓰는 **여행용 어댑터**처럼, 모양만 맞춰주고 전기(기능)는 그대로 통하게 하는 게 목표입니다. 실무 원칙:

1. 내부 표준 메시지 형식을 하나 정하고, 공급자별 어댑터에서 변환한다.
2. 사용량(토큰, 캐시, 비용)은 공급자와 상관없이 **항상 같은 형식으로 기록**한다. 그래야 비교와 비용 집계가 된다.
3. 공급자 고유 기능은 `provider_options` 같은 탈출구로 열어둔다.
4. 이미 잘 만들어진 게이트웨이(LiteLLM 등)를 쓸지 직접 만들지는 19주차에 다시 판단한다.

### 토크나이저 차이와 비용 추정

글을 토큰으로 자르는 규칙(토크나이저)은 모델마다 다릅니다. 같은 문장도 모델 A에서는 20토큰, 모델 B에서는 26토큰일 수 있습니다. 그래서 비용은 글자 수로 어림하지 말고 반드시 **실제 API 응답의 `usage` 값**으로 계산하고, 보내기 전에 미리 알아야 하면 공급자의 토큰 카운트 API를 씁니다.

## 실습 과제: 공통 LLM 클라이언트

`libs/llm/`에 만들고 이후 모든 주차에서 재사용합니다.

**요구사항**

1. `complete(messages, model, **opts) -> Completion`과 `stream(...)` 두 함수. Claude와 OpenAI 두 공급자를 지원한다.
2. `Completion`은 `text`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cost_usd`, `latency_ms`, `ttft_ms`를 갖는다.
3. 가격표는 `prices.yaml`로 분리한다.
4. 1주차의 재시도·백오프를 적용한다.
5. 모든 호출을 JSONL 파일에 기록한다(시간, 모델, 토큰, 비용, 지연).
6. 실험 노트북: 같은 질문을 temperature 0 / 0.7 / 1.0으로 각 5회 호출해 결과 다양성을 비교하고, 긴 시스템 프롬프트(3,000토큰 이상)로 캐싱 전후 비용·TTFT를 비교한다.

**시작 코드**

```python
# libs/llm/types.py
from dataclasses import dataclass

@dataclass
class Completion:
    """공급자와 상관없이 같은 모양으로 돌려주는 호출 결과"""
    text: str                       # 답변 텍스트
    model: str
    input_tokens: int               # 입력 토큰 (캐시 적중분 포함 전체)
    output_tokens: int
    cache_read_tokens: int = 0      # 입력 중 캐시에서 읽은 토큰 (할인 대상)
    cost_usd: float = 0.0
    latency_ms: int = 0             # 요청부터 응답 완료까지
    ttft_ms: int | None = None      # 첫 토큰까지 (스트리밍일 때만 측정 가능)

def cost(model: str, inp: int, out: int, cache_read: int, prices: dict) -> float:
    p = prices[model]  # {"input": 1.0, "output": 5.0, "cache_read": 0.1}  (USD / 1M tokens)
    # 캐시 안 된 입력은 정가, 캐시 적중 입력은 할인가, 출력은 출력 단가. 100만으로 나눠 토큰당 가격으로
    return ((inp - cache_read) * p["input"] + cache_read * p["cache_read"] + out * p["output"]) / 1_000_000
```

**채점 기준**

- [ ] 공급자를 바꿔도 호출 코드는 한 줄(model 이름)만 바뀐다
- [ ] 캐싱 실험에서 두 번째 호출의 `cache_read_tokens > 0`이고 비용이 줄었다
- [ ] 로그 JSONL로 하루 총비용을 계산하는 스크립트가 있다

## 흔한 실수

- **`max_tokens`를 너무 작게 줘서 응답이 잘림:** 잘린 응답은 겉보기엔 정상처럼 보여서 놓치기 쉽습니다. 응답의 `stop_reason`(Anthropic)이나 `finish_reason`(OpenAI)이 `max_tokens`/`length`인지 항상 확인합니다.
- **대화 기록을 무한정 쌓음:** 위 비용 계산처럼 총비용이 턴 수의 제곱으로 늘어납니다. 오래된 대화는 요약하거나 잘라냅니다(11주차).
- **시스템 프롬프트 앞쪽에 날짜·사용자 이름을 넣음:** 앞부분이 매번 달라져 캐시가 매번 깨집니다. 변하는 값은 뒤쪽 사용자 메시지에 넣으세요.

## 면접 질문

<details>
<summary>LLM은 왜 환각을 일으키나요? 에이전트에서는 어떻게 줄이나요?</summary>

LLM은 사실을 조회하는 것이 아니라 학습 분포상 그럴듯한 다음 토큰을 생성하기 때문에, 모르는 내용도 자신 있게 지어낼 수 있습니다. 에이전트에서는 ① 검색·DB·API 도구로 근거를 주입하고(grounding), ② 답변에 출처를 달게 하고, ③ 근거가 없으면 "모른다"고 답하도록 지시·평가하고, ④ 구조화 출력과 검증 단계(스키마 검증, 사실 확인 에이전트)를 둡니다. 그리고 환각률을 평가 세트로 측정합니다.
</details>

<details>
<summary>컨텍스트 윈도우가 100만 토큰이면 RAG가 필요 없지 않나요?</summary>

아닙니다. 첫째, 비용과 지연이 입력 길이에 비례해 커집니다. 둘째, 긴 컨텍스트에서는 중간 정보를 놓치거나 관련 없는 정보에 주의가 분산되어 정확도가 떨어집니다. 셋째, 실제 지식 베이스는 수백만 토큰을 넘고 계속 바뀝니다. 넷째, 권한별로 볼 수 있는 문서가 다릅니다. 긴 컨텍스트는 "검색한 결과를 넉넉히 넣을 수 있게" 해주는 것이지 검색을 대체하지 않습니다. 작은 고정 문서는 통째로 넣고 캐싱하는 편이 나을 수 있습니다.
</details>

<details>
<summary>에이전트 비용이 예상보다 훨씬 많이 나오는 이유는?</summary>

매 턴마다 지금까지의 대화와 도구 결과 전체를 다시 입력하기 때문에 입력 토큰이 턴 수에 대해 제곱으로 늘어납니다. 큰 도구 결과(웹페이지 전문, 긴 JSON)를 그대로 넣거나, 실패한 도구를 반복 호출하거나, 멀티 에이전트가 같은 컨텍스트를 여러 번 읽는 것도 원인입니다. 프롬프트 캐싱, 도구 결과 요약·절단, 반복 제한, 작은 모델 라우팅, compaction으로 줄입니다.
</details>

<details>
<summary>프롬프트 캐싱이 동작하는 조건은?</summary>

입력의 앞부분(prefix)이 이전 요청과 바이트 단위로 같아야 하고, 공급자가 정한 최소 길이 이상이며, 캐시 유효 시간(보통 수 분, 옵션으로 더 길게) 안에 다시 요청해야 합니다. 그래서 시스템 프롬프트, 도구 정의, 고정 문서처럼 변하지 않는 것을 앞에 두고, 변하는 값은 뒤에 둡니다. 도구 목록 순서를 바꾸거나 시스템 프롬프트에 타임스탬프를 넣으면 캐시가 깨집니다.
</details>

<details>
<summary>temperature 0이면 항상 같은 답이 나오나요?</summary>

대체로 비슷하지만 보장되지 않습니다. 서버 측 배치 구성, 병렬 연산 순서, 하드웨어 차이로 로짓이 미세하게 달라져 다른 토큰이 선택될 수 있습니다. 그래서 재현성이 중요한 평가는 같은 입력을 여러 번 돌려 분포로 보고, 테스트는 정확한 문자열 대신 의미·구조 기준으로 검증합니다.
</details>
