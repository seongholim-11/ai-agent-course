## 학습 목표

- 에이전트 코드에서 쓰는 파이썬 기능을 **왜** 쓰는지 설명할 수 있다
- 타입 힌트와 Pydantic으로 LLM 입출력을 검증한다

- 비동기 코드를 테스트한다

## 왜 이게 에이전트의 기초인가

에이전트가 하는 일을 시간 단위로 쪼개 보면, 실제로 "계산"하는 시간은 거의 없고 대부분 **기다리는 시간**입니다. LLM이 답을 만들 때까지 기다리고, 웹 검색 결과를 기다리고, DB 조회를 기다립니다. 이런 일을 **네트워크 I/O**(입출력)라고 부릅니다.

식당 주방에 비유하면 이렇습니다. 요리사 한 명이 라면 5개를 끓일 때, 한 냄비의 물이 끓을 때까지 멍하니 서 있다가 다음 냄비를 올리면 5배의 시간이 걸립니다. 냄비 5개를 한꺼번에 올려두고 끓는 순서대로 면을 넣으면 거의 1개 끓이는 시간에 끝납니다. **asyncio는 이 "냄비 여러 개 동시에 올리기"를 코드로 하는 방법**입니다. 도구 5개를 순서대로 부르면 5초, 동시에 부르면 1초가 됩니다.

두 번째 축은 **검증**입니다. LLM은 결국 글자(문자열)를 내놓습니다. "검색어는 `MCP spec`, 결과는 3개"라는 뜻의 JSON을 줄 수도 있지만, 따옴표를 빠뜨리거나 숫자 자리에 "세 개"라고 쓸 수도 있습니다. 그래서 LLM이 준 문자열을 **믿을 수 있는 데이터로 바꾸는 관문**이 필요하고, 그 역할을 Pydantic이 합니다.

## 핵심 개념

### 1. 타입 힌트와 Pydantic

**타입 힌트**는 "이 변수에는 문자열이 들어간다", "이 함수는 정수를 돌려준다"를 코드에 적어두는 표기입니다. 파이썬은 원래 이걸 강제하지 않지만, **Pydantic**은 이 표기를 읽어서 실제로 값을 검사해줍니다.

에이전트에서 이게 중요한 이유: LLM에게 도구를 알려줄 때는 "이 도구는 이런 모양의 입력을 받는다"는 설명서를 **JSON Schema**라는 형식으로 줘야 합니다. Pydantic 모델 하나를 만들면 ① 입력 검증, ② JSON 변환(직렬화), ③ JSON Schema 생성을 한 번에 얻을 수 있어서, 설명서와 실제 코드가 어긋날 일이 없습니다.

```python
from typing import Literal
from pydantic import BaseModel, Field, field_validator

class SearchArgs(BaseModel):
    """웹에서 최신 정보를 검색한다."""          # 이 docstring이 도구 설명으로도 쓰인다
    # Field(...)로 제약 조건과 설명을 단다. description은 LLM이 읽는 안내문이다.
    query: str = Field(min_length=2, description="검색어. 구체적인 키워드로.")
    # ge=1, le=20: 1 이상 20 이하만 허용 (greater-or-equal / less-or-equal)
    max_results: int = Field(default=5, ge=1, le=20)
    # Literal: 정해진 네 값 중 하나만 허용. 그 외 값은 검증 오류
    recency: Literal["day", "week", "month", "any"] = "any"

    @field_validator("query")       # query 필드를 검증할 때 이 함수를 추가로 실행
    @classmethod
    def strip(cls, v: str) -> str:
        return v.strip()            # 앞뒤 공백 제거 (LLM이 공백을 붙여 보내는 일이 흔하다)

# LLM이 준 JSON 문자열을 검증하면서 객체로 바꾼다. 형식이 틀리면 ValidationError가 난다.
args = SearchArgs.model_validate_json('{"query": "  MCP spec  ", "max_results": 3}')
print(args.query)                       # "MCP spec"  ← 공백이 정리됨
print(SearchArgs.model_json_schema())   # 도구 정의(input_schema)에 그대로 넣을 수 있는 JSON Schema
```

검증에 실패하면 `ValidationError`가 나는데, 이 오류 메시지에는 "max_results는 20 이하여야 합니다"처럼 **무엇이 왜 틀렸는지**가 들어 있습니다. 이 메시지를 **그대로 모델에게 돌려주면** 모델이 읽고 스스로 고쳐서 다시 호출합니다. 에이전트에서 가장 흔한 오류 복구 방식이고, 4주차에 직접 구현합니다.

### 2. asyncio의 핵심 모델

asyncio를 이해하는 데 필요한 단어는 세 개입니다.

- **코루틴**(`async def`로 만든 함수): "중간에 멈췄다가 이어서 실행할 수 있는 함수"입니다. 주의할 점은, 그냥 호출하면 실행되지 않고 "실행 예약권" 같은 객체만 돌아온다는 것입니다. `await`를 붙이거나 태스크로 등록해야 실제로 돕니다.
- **이벤트 루프**: 코루틴들을 번갈아 실행해주는 관리자입니다. 한 코루틴이 `await`에서 "나 지금 네트워크 응답 기다려"라고 멈추면, 루프는 그동안 다른 코루틴을 실행합니다. 스레드는 하나뿐인데 여러 일이 동시에 진행되는 것처럼 보이는 이유입니다.
- **블로킹 호출**: 기다리는 동안 루프에 제어권을 돌려주지 않는 호출입니다. `time.sleep()`, `requests.get()`이 대표적입니다. 이걸 async 함수 안에서 쓰면 **루프 전체가 그 자리에서 멈춰서**, 다른 코루틴도 전부 같이 기다립니다. 냄비 하나 앞에서 요리사가 얼어붙는 것과 같습니다.

해결책은 비동기 버전(`httpx.AsyncClient`, `asyncio.sleep`)을 쓰는 것이고, 비동기 버전이 없는 라이브러리라면 `asyncio.to_thread()`로 별도 스레드에서 돌립니다.

```python
import asyncio, httpx

async def fetch(client: httpx.AsyncClient, url: str) -> int:
    # await: 응답이 올 때까지 이 코루틴은 멈추고, 그동안 루프는 다른 fetch를 실행한다
    r = await client.get(url, timeout=10)
    return r.status_code

async def main(urls: list[str]):
    # AsyncClient는 연결(커넥션 풀)을 재사용하므로 하나를 만들어 여러 요청에 함께 쓴다
    async with httpx.AsyncClient() as client:
        # gather: 여러 코루틴을 동시에 실행하고, 결과를 "입력 순서대로" 리스트로 모은다
        # return_exceptions=True: 하나가 실패해도 예외를 던지지 않고 결과 자리에 예외 객체를 넣는다
        results = await asyncio.gather(*(fetch(client, u) for u in urls), return_exceptions=True)
    return results

# 프로그램 진입점에서는 asyncio.run(main([...]))으로 이벤트 루프를 시작한다
```

### 3. gather vs TaskGroup

여러 작업을 동시에 돌리는 방법은 두 가지가 대표적이고, **하나가 실패했을 때의 태도**가 다릅니다.

| | `asyncio.gather` | `asyncio.TaskGroup` (3.11+) |
| --- | --- | --- |
| 하나가 실패하면 | 기본은 첫 예외를 올리지만 **나머지 태스크는 계속 돈다** | 나머지를 **취소**하고 `ExceptionGroup`으로 모아 올린다 |
| 부분 실패 허용 | `return_exceptions=True`로 쉽게 | 각 태스크 안에서 try/except 필요 |
| 적합한 상황 | 병렬 검색처럼 "일부 실패해도 계속" | 트랜잭션처럼 "하나라도 실패하면 전부 중단" |

비유하면 gather는 "친구 다섯에게 각자 장을 봐오라고 보내고, 한 명이 못 사 와도 나머지 재료로 요리하는" 방식이고, TaskGroup은 "다섯 명이 한 팀이라 한 명이 실패하면 전원 철수하는" 방식입니다.

에이전트가 도구 여러 개를 동시에 부를 때는 보통 **gather 쪽(부분 실패 허용)**이 맞습니다. 검색 3개 중 1개가 실패해도 나머지 2개 결과로 답할 수 있기 때문입니다. 실패한 도구는 "검색 실패: 타임아웃" 같은 메시지를 결과로 돌려주고, 그걸 보고 어떻게 할지는 모델이 판단하게 합니다.

### 4. 동시성 제한과 타임아웃

"동시에 하면 빠르다"고 해서 1,000개를 한꺼번에 보내면 안 됩니다. LLM API에는 **분당 요청 수(RPM)**와 **분당 토큰 수(TPM)** 한도가 있어서, 한도를 넘으면 `429 Too Many Requests` 에러가 바로 돌아옵니다.

그래서 "동시에 최대 몇 개까지만"이라는 상한이 필요합니다. **Semaphore**는 입장권이 정해진 개수만 있는 매표소라고 생각하면 됩니다. 입장권을 받은 작업만 안으로 들어가고, 하나가 끝나서 입장권을 반납해야 다음 작업이 들어갑니다.

```python
sem = asyncio.Semaphore(8)  # 입장권 8장: 동시에 최대 8개까지만 실행

async def limited(coro_fn, *args):
    async with sem:          # 입장권을 받을 때까지 기다렸다가 들어간다 (나갈 때 자동 반납)
        # wait_for: 30초 안에 안 끝나면 TimeoutError. 응답 없는 요청이 입장권을 영원히 쥐고 있지 않게 한다
        return await asyncio.wait_for(coro_fn(*args), timeout=30)
```

타임아웃이 없으면, 응답이 오지 않는 요청 하나가 입장권을 계속 붙잡고 있어서 전체가 서서히 멈춥니다. **동시성 제한과 타임아웃은 항상 한 쌍**으로 둡니다.

## 심화

### 지수 백오프와 지터

네트워크 에러가 났을 때 무조건 다시 시도하면 안 되고, **다시 해볼 가치가 있는 에러**만 골라야 합니다.

- 재시도할 에러: `429`(너무 많이 보냄), `503`·`529`(서버가 잠시 과부하), 타임아웃. 잠시 뒤에는 성공할 수 있는 일시적인 문제입니다.
- 재시도하면 안 되는 에러: `400`(요청 형식이 틀림), `401`(인증 실패). 똑같이 다시 보내면 똑같이 실패합니다.

**지수 백오프**는 실패할 때마다 기다리는 시간을 0.5초 → 1초 → 2초 → 4초처럼 두 배씩 늘리는 방식입니다. 서버가 회복할 시간을 줍니다.

**지터**는 그 대기 시간에 무작위 값을 섞는 것입니다. 왜 필요할까요? 서버가 잠깐 멈췄다가 살아나면, 동시에 실패한 클라이언트 100개가 정확히 "1초 뒤"에 한꺼번에 재시도해서 서버를 다시 쓰러뜨립니다. 이걸 **thundering herd**(우르르 몰려드는 소 떼)라고 부릅니다. 대기 시간을 0.7초, 1.3초, 0.9초…처럼 흩어놓으면 재시도가 고르게 퍼집니다.

공급자가 `retry-after` 헤더로 "몇 초 뒤에 다시 와"라고 알려주면 그 값을 우선합니다.

```python
import random

# 다시 시도할 가치가 있는 HTTP 상태 코드 (일시적 문제들)
RETRYABLE = {408, 409, 429, 500, 502, 503, 504, 529}

async def with_retry(fn, *, attempts=5, base=0.5, cap=20):
    for i in range(attempts):                    # i = 0, 1, 2, 3, 4
        try:
            return await fn()                    # 성공하면 바로 결과 반환
        except httpx.HTTPStatusError as e:
            # 재시도 대상이 아니거나, 마지막 시도였다면 포기하고 예외를 그대로 올린다
            if e.response.status_code not in RETRYABLE or i == attempts - 1:
                raise
            ra = e.response.headers.get("retry-after")   # 서버가 알려준 대기 시간(초)
            # 서버 지시가 있으면 따르고, 없으면 base * 2^i (최대 cap초)에 0.5~1.5배 무작위(지터)
            delay = float(ra) if ra else min(cap, base * 2 ** i) * random.uniform(0.5, 1.5)
            await asyncio.sleep(delay)           # 비동기 대기: 기다리는 동안 다른 작업은 계속 돈다
```

### 취소(cancellation)는 기능이다

사용자가 "중지" 버튼을 누르거나 타임아웃이 나면, 화면에서만 멈춘 척하는 게 아니라 **진행 중인 LLM 호출과 도구 실행을 실제로 멈춰야** 합니다. 그래야 아무도 안 보는 답변에 돈이 계속 나가지 않습니다.

asyncio에서 취소는 해당 코루틴 안에 `asyncio.CancelledError`라는 예외를 던지는 방식으로 일어납니다. 그래서 이 예외를 **삼키면(잡아서 무시하면) 취소가 안 됩니다.** `except Exception:`은 괜찮지만(CancelledError는 Exception의 자식이 아님), `except BaseException:`이나 맨 `except:`는 취소까지 잡아버려서 위험합니다. 파일 닫기, 부분 결과 저장 같은 정리 작업은 `finally`에 둡니다.

### 구조화된 동시성으로 생각하기

작업을 띄울 때마다 "이 작업은 누가 책임지고, 누가 끝날 때까지 기다리는가?"를 분명히 해야 합니다. `asyncio.create_task()`로 작업을 던져놓고 잊어버리면 두 가지 문제가 생깁니다. 그 작업에서 난 예외가 아무에게도 보고되지 않고 조용히 사라지고, 그 작업을 가리키는 변수가 없으면 파이썬이 쓰레기로 보고 치워버릴 수도 있습니다.

해결책은 TaskGroup 안에서 만들어 그룹이 끝을 책임지게 하거나, 만든 태스크를 리스트 같은 곳에 보관해두는 것입니다.

### 제너레이터와 스트리밍

ChatGPT처럼 답이 한 글자씩 흘러나오는 화면을 **스트리밍**이라고 합니다. 코드에서 LLM 스트리밍은 `async for chunk in stream:`처럼 조각을 하나씩 꺼내 쓰는 **비동기 이터레이터** 형태입니다.

`async def` 함수 안에서 `yield`를 쓰면 **비동기 제너레이터**가 됩니다. "값을 하나 내보내고 잠깐 멈췄다가, 다음 값을 달라고 하면 이어서 실행"하는 함수입니다. 이걸 직접 만들 줄 알면 2주차에 SSE로 브라우저까지 토큰을 흘려보내는 구현이 쉬워집니다.

```python
async def tokens(stream):
    async for event in stream:                    # 공급자가 보내는 이벤트를 하나씩 받는다
        if event.type == "content_block_delta":   # 텍스트 조각이 들어 있는 이벤트만 골라서
            yield event.delta.text                # 바깥으로 한 조각씩 내보낸다
```

## 실습 과제: 비동기 URL 수집·요약기

`weeks/w01_async_crawler/`에 만듭니다.

**요구사항**

1. URL 목록(최소 30개)을 받아 동시에 가져온다. 동시 요청은 최대 5개.
2. 각 요청은 10초 타임아웃, 재시도 가능한 에러는 지수 백오프로 최대 3회 재시도.
3. 결과를 Pydantic 모델 `PageResult(url, status, title, elapsed_ms, error)`로 반환한다.
4. 일부가 실패해도 전체는 끝까지 돈다.
5. 순차 실행과 병렬 실행의 총 소요 시간을 비교해 출력한다.
6. pytest로 최소 3개 테스트: 성공, 타임아웃, 재시도 후 성공 (`respx`나 가짜 서버로 네트워크를 흉내 낸다).

**시작 코드**

```python
# weeks/w01_async_crawler/crawler.py
import asyncio, time, re
import httpx
from pydantic import BaseModel

class PageResult(BaseModel):
    url: str
    status: int | None = None       # 실패하면 상태 코드가 없을 수 있으므로 None 허용
    title: str | None = None
    elapsed_ms: int                 # 걸린 시간(밀리초)
    error: str | None = None        # 실패 이유. 성공이면 None

async def fetch_one(client: httpx.AsyncClient, url: str, sem: asyncio.Semaphore) -> PageResult:
    t0 = time.perf_counter()        # 경과 시간 측정용 시작 시각
    async with sem:                 # 동시 요청 수 제한 (입장권)
        try:
            # TODO: 재시도 로직 적용
            r = await client.get(url, timeout=10, follow_redirects=True)
            # <title>...</title> 사이의 글자를 찾는다. re.S: 줄바꿈이 있어도 찾기
            m = re.search(r"<title>(.*?)</title>", r.text, re.I | re.S)
            return PageResult(url=url, status=r.status_code, title=m and m.group(1).strip(),
                              elapsed_ms=int((time.perf_counter() - t0) * 1000))
        except Exception as e:
            # 예외를 던지지 않고 "실패한 결과"로 돌려준다 → 하나가 실패해도 전체가 계속 돈다
            return PageResult(url=url, error=repr(e), elapsed_ms=int((time.perf_counter() - t0) * 1000))

async def crawl(urls: list[str], concurrency: int = 5) -> list[PageResult]:
    sem = asyncio.Semaphore(concurrency)
    # User-Agent: 어떤 프로그램이 요청하는지 밝힌다 (없으면 차단하는 사이트가 있다)
    async with httpx.AsyncClient(headers={"User-Agent": "agent-lab/0.1"}) as client:
        return await asyncio.gather(*(fetch_one(client, u, sem) for u in urls))
```

**채점 기준 (스스로)**

- [ ] 병렬 실행이 순차 대비 4배 이상 빠르다
- [ ] 동시 요청 수가 5를 넘지 않음을 로그로 증명했다
- [ ] 테스트가 실제 네트워크 없이 통과한다
- [ ] `ruff check`가 깨끗하다

**확장 과제:** 각 페이지 제목을 LLM으로 한 줄 요약하는 단계를 추가하고, LLM 호출에는 별도 Semaphore(2)를 둡니다. 왜 I/O 종류마다 다른 한도를 두는지 README에 적으세요.

## 흔한 실수

- **async 함수 안에서 `requests` 사용:** `requests`는 블로킹 라이브러리라 루프가 멈춥니다. 코드는 async로 썼는데 실제로는 하나씩 순서대로 실행되어 동시성이 전혀 생기지 않습니다.
- **이미 루프가 도는 곳에서 `asyncio.run()` 호출:** Jupyter 노트북이나 FastAPI 안에는 이미 이벤트 루프가 돌고 있어서 에러가 납니다. Jupyter에서는 그냥 `await main()`처럼 바로 씁니다.
- **`except Exception: pass`로 에러 삼키기:** 실패했는데 빈 결과가 돌아가면, 에이전트는 "도구가 성공했고 결과가 없다"고 착각하고 엉뚱한 답을 만듭니다. 에러는 반드시 결과에 담아 돌려주세요.
- **`httpx.AsyncClient`를 요청마다 새로 만들기:** 클라이언트는 연결을 재사용하는 커넥션 풀을 갖고 있습니다. 매번 새로 만들면 매번 연결을 새로 맺느라 느려집니다.

## 면접 질문

<details>
<summary>파이썬 GIL이 있는데 asyncio가 왜 빨라지나요?</summary>

GIL은 한 번에 한 스레드만 **파이썬 바이트코드**를 실행하게 하지만, I/O를 기다리는 동안에는 CPU를 쓰지 않습니다. asyncio는 한 스레드에서 I/O 대기 시간을 겹쳐서 활용하는 방식이라 GIL과 무관하게 I/O 바운드 작업이 빨라집니다. 반대로 CPU 바운드 작업(대량 파싱, 임베딩 계산)은 asyncio로 빨라지지 않으며 프로세스 풀이나 네이티브 라이브러리가 필요합니다. 에이전트는 대부분 I/O 바운드라 asyncio가 잘 맞습니다.
</details>

<details>
<summary>gather와 TaskGroup 중 병렬 도구 호출에는 무엇을 쓰나요?</summary>

도구 중 일부가 실패해도 나머지 결과로 모델이 판단할 수 있어야 하므로, 보통 `gather(..., return_exceptions=True)`나 각 태스크 내부에서 예외를 결과로 변환하는 방식을 씁니다. TaskGroup은 하나가 실패하면 나머지를 취소하므로 "모두 성공해야 의미가 있는" 작업에 맞습니다. 어느 쪽이든 타임아웃과 동시성 제한을 함께 둡니다.
</details>

<details>
<summary>LLM API 429 에러는 어떻게 처리하나요?</summary>

재시도 가능한 에러로 분류하고, `retry-after` 헤더가 있으면 따르고 없으면 지터를 섞은 지수 백오프로 재시도합니다. 근본적으로는 Semaphore나 토큰 버킷으로 요청률을 공급자 한도 아래로 유지하고, 여러 워커가 있으면 Redis 같은 공유 저장소로 전역 레이트 리밋을 둡니다. 한도에 자주 닿으면 배치 API, 캐싱, 작은 모델로 분산하는 것도 방법입니다.
</details>

<details>
<summary>Pydantic을 에이전트에서 어디에 쓰나요?</summary>

세 군데입니다. 도구 입력 스키마 정의(JSON Schema 자동 생성), LLM의 구조화 출력 검증(검증 실패 시 에러를 모델에 돌려 재시도), API 요청·응답 모델(FastAPI)입니다. 하나의 모델이 문서, 검증, 직렬화의 단일 출처가 되므로 스키마와 코드가 어긋나는 버그를 줄입니다.
</details>
