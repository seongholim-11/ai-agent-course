## 학습 목표

- 에이전트를 FastAPI 서비스로 감싸고 요청·응답 스키마를 정의한다
- SSE로 토큰과 중간 이벤트(도구 호출 시작/끝)를 스트리밍한다
- 대화 기록과 작업 상태를 PostgreSQL·Redis에 저장한다
- 전체 스택을 docker compose로 한 번에 띄운다

## 에이전트 서비스의 기본 모양

에이전트 API는 일반 CRUD API와 세 가지가 다릅니다.

1. **오래 걸린다.** 응답 하나에 수 초에서 수 분이 걸립니다. 그래서 스트리밍이나 비동기 작업(job) 패턴이 필요합니다.
2. **중간 과정이 있다.** "검색 중…", "파일 읽는 중…"처럼 진행 상황을 보여줘야 사용자가 기다립니다.
3. **상태가 있다.** 대화 기록, 작업 진행도, 체크포인트를 저장해야 이어서 실행할 수 있습니다.

```
Client ──POST /chat (SSE)──▶ FastAPI ──▶ Agent loop ──▶ LLM API
   ▲                            │            │
   └──── event: token/tool ─────┘            ├──▶ Tools (HTTP, DB)
                                             └──▶ Postgres(대화) / Redis(캐시·락)
```

## 핵심 개념

### 1. FastAPI 기본 구조

```python
# app/main.py
from contextlib import asynccontextmanager
from fastapi import FastAPI, Depends
from pydantic import BaseModel
import httpx

class ChatRequest(BaseModel):
    session_id: str
    message: str

class ChatResponse(BaseModel):
    answer: str
    input_tokens: int
    output_tokens: int

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(timeout=30)   # 앱 전체에서 공유
    yield
    await app.state.http.aclose()

app = FastAPI(lifespan=lifespan)

@app.get("/healthz")
async def health():
    return {"ok": True}
```

`lifespan`으로 HTTP 클라이언트, DB 풀, LLM 클라이언트를 **앱 시작 시 한 번** 만들고 공유합니다. 요청마다 만들면 커넥션 재사용이 안 됩니다.

### 2. SSE(Server-Sent Events) 스트리밍

SSE는 서버 → 클라이언트 단방향 텍스트 스트림입니다. 형식은 단순합니다.

```
event: token
data: {"text": "안녕"}

event: tool_start
data: {"name": "web_search", "args": {"query": "..."}}

```

빈 줄 하나가 이벤트의 끝입니다. WebSocket보다 단순하고, HTTP 그대로라 프록시·로드밸런서를 잘 통과하며, 브라우저 `EventSource`가 재연결을 자동으로 해줍니다. 대부분의 LLM API도 SSE로 스트리밍합니다.

```python
import json
from fastapi.responses import StreamingResponse

def sse(event: str, data: dict) -> str:
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"

@app.post("/chat/stream")
async def chat_stream(req: ChatRequest):
    async def gen():
        yield sse("start", {"session_id": req.session_id})
        async for text in llm_stream(req.message):     # 3주차에서 구현
            yield sse("token", {"text": text})
        yield sse("done", {})
    return StreamingResponse(gen(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

`X-Accel-Buffering: no`는 Nginx가 스트림을 모아서 한 번에 보내는 것을 막습니다. 배포 후 "로컬에선 스트리밍되는데 서버에선 한 번에 나온다"는 문제의 90%가 프록시 버퍼링입니다.

### 3. 클라이언트 연결 끊김 처리

사용자가 탭을 닫으면 서버는 계속 LLM을 호출하며 돈을 씁니다. 연결이 끊기면 제너레이터가 취소되도록 하고, 정리 작업을 `finally`에 둡니다.

```python
from fastapi import Request

async def gen(request: Request):
    try:
        async for text in llm_stream(...):
            if await request.is_disconnected():
                break
            yield sse("token", {"text": text})
    finally:
        await save_partial_answer(...)   # 부분 응답 저장, 사용량 기록
```

### 4. 저장소 역할 나누기

| 저장소 | 에이전트에서의 용도 |
| --- | --- |
| PostgreSQL | 대화 기록, 사용자, 작업(job) 상태, 평가 결과, pgvector로 벡터 검색까지 |
| Redis | 세션 캐시, 레이트 리밋 카운터, 분산 락, 작업 큐(간단한 경우) |
| 객체 저장소(S3 등) | 업로드 파일, 긴 도구 결과, 생성된 보고서 |

대화 메시지 테이블은 LLM 메시지 형식을 그대로 담을 수 있게 `role`, `content(JSONB)`, `tool_call_id`, `tokens`, `created_at` 정도를 둡니다. content를 JSONB로 두면 텍스트·이미지·도구 호출 블록을 모두 담을 수 있습니다.

### 5. Docker와 compose

```dockerfile
# Dockerfile (멀티 스테이지)
FROM python:3.12-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project
COPY . .
RUN uv sync --frozen --no-dev

FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /app /app
ENV PATH="/app/.venv/bin:$PATH"
USER 1000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```yaml
# docker-compose.yml
services:
  api:
    build: .
    env_file: .env
    ports: ["8000:8000"]
    depends_on:
      db: { condition: service_healthy }
  db:
    image: pgvector/pgvector:pg17
    environment: { POSTGRES_PASSWORD: dev, POSTGRES_DB: agent }
    healthcheck: { test: ["CMD", "pg_isready", "-U", "postgres"], interval: 5s }
    volumes: ["pgdata:/var/lib/postgresql/data"]
  redis:
    image: redis:7
volumes:
  pgdata:
```

의존성 레이어(`pyproject.toml`, `uv.lock`)를 소스보다 먼저 복사해야 코드만 바뀔 때 빌드 캐시가 살아납니다. 컨테이너는 root가 아닌 사용자로 실행합니다(18주차 보안과 연결).

## 심화

### 스트리밍 vs 작업(job) 패턴

| | SSE 스트리밍 | 비동기 작업 + 폴링/웹훅 |
| --- | --- | --- |
| 응답 시간 | 수 초 ~ 2분 | 수 분 ~ 수 시간 |
| 연결 | 열려 있어야 함 | 끊겨도 됨 |
| 예 | 채팅, 짧은 에이전트 | 딥리서치, 보고서 생성, 배치 |
| 구현 | StreamingResponse | `POST /jobs` → `202 + job_id` → `GET /jobs/{id}` 또는 `GET /jobs/{id}/events`(SSE, 재접속 시 `Last-Event-ID`로 이어받기) |

실무에서는 둘을 합칩니다. 작업은 워커가 돌리고, 진행 이벤트는 Redis Stream이나 DB에 쌓고, 클라이언트는 SSE로 구독하다 끊기면 `Last-Event-ID`로 이어받습니다. 21주차에서 구현합니다.

### 멱등성 키

네트워크가 불안정하면 클라이언트가 같은 요청을 두 번 보냅니다. 에이전트가 "메일 보내기" 같은 부수효과를 두 번 실행하면 안 됩니다. `Idempotency-Key` 헤더를 받아 Redis에 저장하고 같은 키가 오면 이전 결과를 돌려줍니다.

### 백프레셔

생성 속도가 소비 속도보다 빠르면 메모리가 쌓입니다. SSE 제너레이터는 `yield`가 소비될 때까지 기다리므로 기본적으로 백프레셔가 걸리지만, 중간에 무제한 `asyncio.Queue()`를 두면 깨집니다. 큐에는 항상 `maxsize`를 줍니다.

## 실습 과제: 채팅 API 서버

`weeks/w02_chat_api/`

**요구사항**

1. `POST /chat` (일반 JSON 응답)과 `POST /chat/stream` (SSE) 두 엔드포인트. 이번 주는 LLM 대신 **가짜 스트림**(단어를 0.05초 간격으로 내보내는 제너레이터)을 써도 됩니다.
2. 대화 기록을 PostgreSQL `messages` 테이블에 저장하고, 같은 `session_id`로 다시 부르면 이전 기록을 불러온다.
3. 클라이언트가 연결을 끊으면 생성이 멈추고, 그때까지의 부분 응답이 저장된다.
4. `Idempotency-Key` 헤더를 지원한다.
5. `docker compose up` 한 줄로 api + db + redis가 뜬다.
6. 간단한 HTML 페이지(`static/index.html`)에서 `fetch` + `ReadableStream`으로 스트림을 화면에 찍는다.

**시작 코드: 브라우저에서 POST SSE 읽기**

```js
// EventSource는 GET만 지원하므로 POST 스트림은 fetch로 읽는다
const res = await fetch('/chat/stream', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ session_id: 's1', message: '안녕' }),
});
const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
let buf = '';
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buf += value;
  let i;
  while ((i = buf.indexOf('\n\n')) >= 0) {
    const raw = buf.slice(0, i); buf = buf.slice(i + 2);
    const ev = Object.fromEntries(raw.split('\n').map(l => [l.slice(0, l.indexOf(':')), l.slice(l.indexOf(':') + 2)]));
    if (ev.event === 'token') document.querySelector('#out').textContent += JSON.parse(ev.data).text;
  }
}
```

**채점 기준**

- [ ] curl `-N`으로 스트림이 토큰 단위로 나오는 것을 확인했다
- [ ] 스트림 도중 curl을 Ctrl+C 했을 때 서버 로그에 취소가 찍히고 부분 응답이 저장된다
- [ ] 같은 Idempotency-Key로 두 번 보내면 DB에 메시지가 한 번만 저장된다
- [ ] 이미지 크기가 300MB 이하다

## 흔한 실수

- 스트리밍 응답 안에서 DB 세션을 요청 스코프 의존성(`Depends`)으로 받아 쓰기 → 응답이 시작되면 의존성이 정리되어 세션이 닫힐 수 있습니다. 제너레이터 안에서 직접 세션을 엽니다.
- `.env`를 이미지에 복사 → 시크릿 유출. `.dockerignore`에 `.env`를 넣습니다.
- 헬스체크 없이 `depends_on`만 사용 → DB가 준비되기 전에 api가 떠서 실패합니다.

## 면접 질문

<details>
<summary>LLM 응답 스트리밍에 WebSocket 대신 SSE를 쓰는 이유는?</summary>

LLM 응답은 서버 → 클라이언트 단방향이라 SSE로 충분합니다. SSE는 일반 HTTP라 인증 헤더, 프록시, 로드밸런서, CDN과 호환이 좋고, 이벤트 ID 기반 재연결이 표준에 있습니다. WebSocket은 양방향 실시간(음성, 협업 편집, 사용자가 생성 중간에 끼어드는 인터랙션)이 필요할 때 씁니다. 대신 SSE는 프록시 버퍼링과 브라우저당 동시 연결 수 제한(HTTP/1.1에서 6개)에 주의해야 합니다.
</details>

<details>
<summary>10분 걸리는 에이전트 작업을 API로 어떻게 제공하나요?</summary>

요청을 받으면 작업을 큐에 넣고 `202 Accepted`와 job_id를 돌려줍니다. 워커가 작업을 실행하며 진행 이벤트와 체크포인트를 저장하고, 클라이언트는 상태 조회 API나 SSE 구독(재연결 시 Last-Event-ID), 또는 웹훅으로 결과를 받습니다. 워커가 죽어도 체크포인트에서 재개할 수 있게 하고, 작업에는 타임아웃과 취소 API를 둡니다.
</details>

<details>
<summary>사용자가 스트리밍 중에 창을 닫으면 서버에서는 무슨 일이 일어나야 하나요?</summary>

연결 종료를 감지해 LLM 스트림과 진행 중인 도구 호출을 취소해야 비용이 멈춥니다. 다만 부분 응답과 토큰 사용량은 저장해 과금·분석에 반영하고, 부수효과가 있는 도구가 실행 중이었다면 완료 여부를 기록해 재시도 시 중복 실행을 막습니다. 백그라운드 작업형이라면 반대로 연결과 무관하게 계속 진행하는 것이 맞습니다.
</details>
