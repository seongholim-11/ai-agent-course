## 학습 목표

- 에이전트를 FastAPI 서비스로 감싸고 요청·응답 스키마를 정의한다
- SSE로 토큰과 중간 이벤트(도구 호출 시작/끝)를 스트리밍한다
- 대화 기록과 작업 상태를 PostgreSQL·Redis에 저장한다
- 전체 스택을 docker compose로 한 번에 띄운다

## 에이전트 서비스의 기본 모양

에이전트를 내 컴퓨터에서 스크립트로 돌리는 것과, 여러 사람이 웹이나 앱에서 쓰는 **서비스**로 만드는 것은 다른 일입니다. 서비스로 만들려면 요청을 받아 처리하고 응답을 돌려주는 **API 서버**가 필요한데, 에이전트 API는 회원가입·게시글 같은 일반 API(CRUD)와 세 가지가 다릅니다.

1. **오래 걸린다.** 일반 API는 0.1초면 답하지만, 에이전트는 응답 하나에 수 초에서 수 분이 걸립니다. 그동안 화면이 멈춰 있으면 사용자는 고장 난 줄 압니다. 그래서 답을 조금씩 흘려보내는 **스트리밍**이나, "접수했으니 나중에 확인하세요" 방식의 **비동기 작업(job) 패턴**이 필요합니다.
2. **중간 과정이 있다.** 택배 배송 조회처럼 "검색 중…", "파일 읽는 중…" 같은 진행 상황을 보여줘야 사용자가 기다립니다.
3. **상태가 있다.** 이전 대화를 기억해야 하고, 긴 작업이 어디까지 진행됐는지 저장해둬야 서버가 재시작돼도 이어서 실행할 수 있습니다.

전체 흐름을 그림으로 보면 다음과 같습니다. 브라우저(Client)가 요청을 보내면 FastAPI 서버가 에이전트 루프를 돌리고, 그 과정에서 나오는 토큰과 도구 호출 이벤트를 실시간으로 다시 브라우저에 흘려보냅니다.

```
Client ──POST /chat (SSE)──▶ FastAPI ──▶ Agent loop ──▶ LLM API
   ▲                            │            │
   └──── event: token/tool ─────┘            ├──▶ Tools (HTTP, DB)
                                             └──▶ Postgres(대화) / Redis(캐시·락)
```

## 핵심 개념

### 1. FastAPI 기본 구조

**FastAPI**는 파이썬으로 API 서버를 만드는 프레임워크입니다. 1주차의 Pydantic 모델을 요청·응답 형식으로 그대로 쓸 수 있고, async를 기본으로 지원해서 에이전트 서버에 잘 맞습니다.

```python
# app/main.py
from contextlib import asynccontextmanager
from fastapi import FastAPI, Depends
from pydantic import BaseModel
import httpx

# 요청 본문의 형식. 이 형식에 맞지 않는 요청은 FastAPI가 자동으로 422 에러로 거절한다
class ChatRequest(BaseModel):
    session_id: str     # 어느 대화인지 구분하는 ID
    message: str        # 사용자가 보낸 메시지

# 응답 형식. 문서(/docs)에도 자동으로 표시된다
class ChatResponse(BaseModel):
    answer: str
    input_tokens: int   # 비용 추적을 위해 사용량도 함께 돌려준다
    output_tokens: int

@asynccontextmanager
async def lifespan(app: FastAPI):
    # yield 앞: 서버가 켜질 때 한 번 실행 → 공용 자원을 만든다
    app.state.http = httpx.AsyncClient(timeout=30)   # 앱 전체에서 공유하는 HTTP 클라이언트
    yield                                             # 여기서 서버가 요청을 받기 시작한다
    # yield 뒤: 서버가 꺼질 때 한 번 실행 → 자원을 정리한다
    await app.state.http.aclose()

app = FastAPI(lifespan=lifespan)

@app.get("/healthz")        # 서버가 살아 있는지 확인하는 엔드포인트 (Docker·로드밸런서가 호출)
async def health():
    return {"ok": True}
```

`lifespan`은 "서버가 켜질 때 준비하고, 꺼질 때 정리하는" 자리입니다. HTTP 클라이언트, DB 연결 풀, LLM 클라이언트처럼 만들기 비싼 객체를 여기서 **한 번만** 만들어 모든 요청이 함께 씁니다. 요청마다 새로 만들면 매번 연결을 새로 맺어야 해서 느려집니다. 식당으로 치면 손님이 올 때마다 냄비를 새로 사 오는 셈입니다.

### 2. SSE(Server-Sent Events) 스트리밍

**SSE**는 서버가 클라이언트에게 데이터를 **한 방향으로 계속 흘려보내는** 방식입니다. 한 번의 HTTP 요청에 대한 응답을 끝내지 않고 열어둔 채, 새 데이터가 생길 때마다 조금씩 써 보내는 것입니다. 라디오 방송처럼 서버가 말하고 클라이언트는 듣기만 합니다.

형식은 아주 단순한 텍스트입니다.

```
event: token
data: {"text": "안녕"}

event: tool_start
data: {"name": "web_search", "args": {"query": "..."}}

```

`event:` 줄은 이벤트 종류, `data:` 줄은 내용이고, **빈 줄 하나가 "이벤트 하나 끝"이라는 신호**입니다. 클라이언트는 빈 줄을 기준으로 잘라서 하나씩 처리합니다.

왜 SSE를 쓸까요? 양방향 통신인 WebSocket보다 단순하고, 일반 HTTP 그대로라 회사 프록시·로드밸런서를 잘 통과하며, 브라우저의 `EventSource`가 연결이 끊기면 자동으로 다시 붙어줍니다. OpenAI, Anthropic 같은 LLM API도 스트리밍을 SSE로 보냅니다.

```python
import json
from fastapi.responses import StreamingResponse

def sse(event: str, data: dict) -> str:
    # SSE 형식 한 덩어리를 만든다. 끝의 \n\n(빈 줄)이 이벤트 구분자다
    # ensure_ascii=False: 한글을 \uXXXX로 바꾸지 않고 그대로 보낸다
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"

@app.post("/chat/stream")
async def chat_stream(req: ChatRequest):
    async def gen():                                   # 비동기 제너레이터 (1주차)
        yield sse("start", {"session_id": req.session_id})
        async for text in llm_stream(req.message):     # LLM이 토큰을 줄 때마다 (3주차에서 구현)
            yield sse("token", {"text": text})         # 바로 클라이언트로 흘려보낸다
        yield sse("done", {})                          # 끝났다는 신호
    # media_type이 text/event-stream이어야 브라우저가 SSE로 인식한다
    return StreamingResponse(gen(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache",      # 중간에서 캐시하지 말 것
                                      "X-Accel-Buffering": "no"})       # Nginx가 모아서 보내지 말 것
```

`X-Accel-Buffering: no`는 Nginx 같은 중간 서버(프록시)가 응답을 모아뒀다가 한꺼번에 보내는 것을 막습니다. 배포 후 "로컬에서는 한 글자씩 나오는데 서버에 올리니 다 끝나고 한 번에 나온다"는 문제의 90%가 이 **프록시 버퍼링** 때문입니다.

### 3. 클라이언트 연결 끊김 처리

사용자가 답변이 나오는 도중에 탭을 닫았다고 해봅시다. 아무 처리도 안 하면 서버는 아무도 보지 않는 답변을 끝까지 만들면서 LLM 비용을 계속 씁니다. 그래서 **연결이 끊겼는지 확인하고, 끊겼으면 생성을 멈춰야** 합니다. 멈추더라도 그때까지 만든 부분 응답과 사용량은 기록해야 하므로, 정리 작업은 `finally`에 둡니다(어떻게 끝나든 반드시 실행되는 자리).

```python
from fastapi import Request

async def gen(request: Request):
    try:
        async for text in llm_stream(...):
            if await request.is_disconnected():   # 클라이언트가 떠났는가?
                break                              # 떠났으면 더 만들지 않는다 → 비용이 멈춘다
            yield sse("token", {"text": text})
    finally:
        # 정상 종료든, 끊김이든, 에러든 항상 실행된다
        await save_partial_answer(...)   # 부분 응답 저장, 사용량(토큰) 기록
```

### 4. 저장소 역할 나누기

에이전트 서비스는 성격이 다른 데이터를 여러 저장소에 나눠 담습니다.

| 저장소 | 비유 | 에이전트에서의 용도 |
| --- | --- | --- |
| PostgreSQL | 장부 (오래, 정확하게) | 대화 기록, 사용자, 작업(job) 상태, 평가 결과, pgvector로 벡터 검색까지 |
| Redis | 메모지 (빠르게, 잠깐) | 세션 캐시, 레이트 리밋 카운터, 분산 락, 작업 큐(간단한 경우) |
| 객체 저장소(S3 등) | 창고 (큰 파일) | 업로드 파일, 긴 도구 결과, 생성된 보고서 |

대화 메시지 테이블에는 LLM 메시지 형식을 그대로 담을 수 있게 `role`(누가 말했나), `content`(내용, JSONB), `tool_call_id`, `tokens`, `created_at` 정도를 둡니다. `content`를 JSONB(구조화된 JSON 컬럼)로 두는 이유는, 메시지 하나에 텍스트·이미지·도구 호출 블록이 섞여 들어가기 때문입니다. 텍스트 컬럼 하나로는 이 구조를 담기 어렵습니다.

### 5. Docker와 compose

**Docker**는 "내 컴퓨터에선 되는데 서버에선 안 돼요" 문제를 없애는 도구입니다. 파이썬 버전, 라이브러리, 코드를 하나의 **이미지**로 포장해서 어디서나 똑같이 실행합니다. **compose**는 여러 컨테이너(API 서버, DB, Redis)를 설정 파일 하나로 한 번에 띄우는 도구입니다.

```dockerfile
# Dockerfile (멀티 스테이지: 빌드용 단계와 실행용 단계를 나눈다)

# ── 1단계: 빌드 ── 의존성 설치에 필요한 도구(uv)는 여기서만 쓴다
FROM python:3.12-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv
WORKDIR /app
COPY pyproject.toml uv.lock ./               # ① 의존성 목록만 먼저 복사
RUN uv sync --frozen --no-dev --no-install-project   # ② 라이브러리 설치 (이 층은 캐시된다)
COPY . .                                     # ③ 그다음에 소스 코드 복사
RUN uv sync --frozen --no-dev

# ── 2단계: 실행 ── 빌드 도구 없이 결과물만 가져와 이미지를 작게 만든다
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /app /app                # 1단계에서 만든 가상환경과 코드만 복사
ENV PATH="/app/.venv/bin:$PATH"              # 가상환경의 python/uvicorn을 기본으로
USER 1000                                    # root가 아닌 일반 사용자로 실행 (보안)
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```yaml
# docker-compose.yml: 서비스 세 개를 한 번에 띄운다
services:
  api:
    build: .                     # 위 Dockerfile로 이미지를 만든다
    env_file: .env               # API 키 등은 이미지에 넣지 않고 실행 시 주입
    ports: ["8000:8000"]         # 내 컴퓨터 8000번 → 컨테이너 8000번
    depends_on:
      db: { condition: service_healthy }   # DB가 "준비 완료" 상태가 된 뒤에 api를 띄운다
  db:
    image: pgvector/pgvector:pg17          # 벡터 검색 확장이 들어간 PostgreSQL
    environment: { POSTGRES_PASSWORD: dev, POSTGRES_DB: agent }
    healthcheck: { test: ["CMD", "pg_isready", "-U", "postgres"], interval: 5s }  # 5초마다 준비 여부 확인
    volumes: ["pgdata:/var/lib/postgresql/data"]   # 컨테이너를 지워도 데이터는 남게
  redis:
    image: redis:7
volumes:
  pgdata:
```

Dockerfile에서 **의존성 목록(`pyproject.toml`, `uv.lock`)을 소스 코드보다 먼저 복사하는 이유**가 있습니다. Docker는 각 줄의 결과를 층(layer)으로 저장해두고, 입력이 그대로면 다시 실행하지 않습니다. 의존성을 먼저 설치해두면, 코드만 바꿨을 때는 라이브러리 설치 층을 그대로 재사용해서 빌드가 몇 분에서 몇 초로 줄어듭니다. 그리고 컨테이너는 root(관리자)가 아닌 사용자로 실행합니다. 코드가 뚫려도 피해 범위를 줄이기 위해서입니다(18주차 보안과 연결).

## 심화

### 스트리밍 vs 작업(job) 패턴

응답 시간에 따라 API 모양을 다르게 가져갑니다. 식당에 비유하면, 스트리밍은 "카운터 앞에서 기다리며 요리가 나오는 과정을 지켜보는" 방식이고, 작업 패턴은 "주문 번호표를 받고 자리에 가 있다가 진동벨이 울리면 받으러 가는" 방식입니다.

| | SSE 스트리밍 | 비동기 작업 + 폴링/웹훅 |
| --- | --- | --- |
| 응답 시간 | 수 초 ~ 2분 | 수 분 ~ 수 시간 |
| 연결 | 열려 있어야 함 | 끊겨도 됨 |
| 예 | 채팅, 짧은 에이전트 | 딥리서치, 보고서 생성, 배치 |
| 구현 | StreamingResponse | `POST /jobs` → `202 + job_id` → `GET /jobs/{id}` 또는 `GET /jobs/{id}/events`(SSE, 재접속 시 `Last-Event-ID`로 이어받기) |

실무에서는 둘을 합칩니다. 작업은 별도 워커가 돌리고, 진행 이벤트는 Redis Stream이나 DB에 차곡차곡 쌓고, 클라이언트는 SSE로 구독합니다. 중간에 연결이 끊기면 "마지막으로 받은 이벤트 번호(`Last-Event-ID`)"를 알려주고 그 다음부터 이어받습니다. 21주차에서 구현합니다.

### 멱등성 키

**멱등성**(idempotency)은 "같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같다"는 성질입니다.

왜 필요할까요? 사용자가 "보내기"를 눌렀는데 네트워크가 느려서 응답이 안 오면, 앱은 실패한 줄 알고 같은 요청을 다시 보냅니다. 그런데 사실 첫 요청은 서버에 도착해서 처리됐을 수 있습니다. 에이전트가 "메일 보내기"나 "환불하기" 같은 **부수효과**(바깥 세상을 바꾸는 행동)를 두 번 실행하면 큰 문제가 됩니다.

해결 방법: 클라이언트가 요청마다 고유한 `Idempotency-Key` 헤더를 붙여 보내고, 서버는 그 키와 결과를 Redis나 DB에 저장합니다. 같은 키가 다시 오면 처리하지 않고 저장해둔 결과를 그대로 돌려줍니다.

### 백프레셔

**백프레셔**(back-pressure)는 "받는 쪽이 느리면 보내는 쪽도 속도를 늦추는" 흐름 제어입니다. 수도꼭지(생성)가 배수구(소비)보다 빠르면 싱크대(메모리)가 넘치는 것과 같습니다.

SSE 제너레이터는 `yield`한 값이 클라이언트로 전송될 때까지 다음 줄로 넘어가지 않으므로, 기본적으로 백프레셔가 자연스럽게 걸립니다. 그런데 생성과 전송 사이에 크기 제한 없는 `asyncio.Queue()`를 끼워 넣으면 생성 쪽이 끝없이 쌓기만 해서 이 장치가 깨집니다. 큐를 쓴다면 항상 `maxsize`를 줘서 "가득 차면 기다리게" 합니다.

## 실습 과제: 채팅 API 서버

`weeks/w02_chat_api/`

**요구사항**

1. `POST /chat` (일반 JSON 응답)과 `POST /chat/stream` (SSE) 두 엔드포인트. 이번 주는 LLM 대신 **가짜 스트림**(단어를 0.05초 간격으로 내보내는 제너레이터)을 써도 됩니다.
2. 대화 기록을 PostgreSQL `messages` 테이블에 저장하고, 같은 `session_id`로 다시 부르면 이전 기록을 불러온다.
3. 클라이언트가 연결을 끊으면 생성이 멈추고, 그때까지의 부분 응답이 저장된다.
4. `Idempotency-Key` 헤더를 지원한다.
5. `docker compose up` 한 줄로 api + db + redis가 뜬다.
6. 간단한 HTML 페이지(`static/index.html`)에서 `fetch` + `ReadableStream`으로 스트림을 화면에 찍는다.

**시작 코드: 브라우저에서 POST SSE 읽기**

브라우저 내장 `EventSource`는 GET 요청만 보낼 수 있어서, 메시지를 본문에 담아 POST로 보내야 하는 채팅에는 쓸 수 없습니다. 그래서 `fetch`로 요청하고 응답 본문을 직접 조각조각 읽어 SSE 형식을 해석합니다.

```js
// EventSource는 GET만 지원하므로 POST 스트림은 fetch로 읽는다
const res = await fetch('/chat/stream', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ session_id: 's1', message: '안녕' }),
});
// 응답 본문(바이트 스트림)을 텍스트 스트림으로 바꾸고, 조각을 하나씩 읽는 reader를 얻는다
const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
let buf = '';                        // 아직 처리 못 한 텍스트를 모아두는 버퍼
while (true) {
  const { value, done } = await reader.read();   // 다음 조각을 기다린다
  if (done) break;                               // 서버가 응답을 끝냈다
  buf += value;
  // 조각이 이벤트 경계와 맞지 않을 수 있으므로, 빈 줄(\n\n)을 찾을 때마다 이벤트 하나를 꺼낸다
  let i;
  while ((i = buf.indexOf('\n\n')) >= 0) {
    const raw = buf.slice(0, i); buf = buf.slice(i + 2);     // 이벤트 하나를 잘라내고 나머지는 버퍼에
    // "event: token\ndata: {...}" → { event: "token", data: "{...}" }
    const ev = Object.fromEntries(raw.split('\n').map(l => [l.slice(0, l.indexOf(':')), l.slice(l.indexOf(':') + 2)]));
    if (ev.event === 'token') document.querySelector('#out').textContent += JSON.parse(ev.data).text;
  }
}
```

**채점 기준**

- [ ] curl `-N`으로 스트림이 토큰 단위로 나오는 것을 확인했다
- [ ] 스트림 도중 curl을 Ctrl+C 했을 때 서버 로그에 취소가 찍히고 부분 응답이 저장된다
- [ ] 같은 Idempotency-Key로 두 번 보내면 DB에 메시지가 한 번만 저장된다
- [ ] 이미지 크기가 300MB 이하다

## 흔한 실수

- **스트리밍 응답 안에서 `Depends`로 받은 DB 세션 쓰기:** FastAPI의 의존성은 "요청 처리 함수가 반환될 때" 정리됩니다. 그런데 스트리밍은 함수가 `StreamingResponse`를 반환한 **뒤에** 제너레이터가 돌기 시작하므로, 그 시점엔 세션이 이미 닫혀 있을 수 있습니다. 제너레이터 안에서 직접 세션을 엽니다.
- **`.env`를 이미지에 복사:** `COPY . .`를 하면 API 키가 든 `.env`까지 이미지에 들어가고, 이미지를 공유하는 순간 시크릿이 유출됩니다. `.dockerignore`에 `.env`를 넣습니다.
- **헬스체크 없이 `depends_on`만 사용:** `depends_on`만 쓰면 DB 컨테이너가 "시작"되자마자 api를 띄우는데, DB가 접속을 받을 "준비"가 되려면 몇 초가 더 걸립니다. 그 사이 api가 접속을 시도하다 실패합니다. `condition: service_healthy`와 healthcheck를 함께 씁니다.

<details>
<summary>LLM 응답 스트리밍에 WebSocket 대신 SSE를 쓰는 이유는?</summary>

LLM 응답은 서버 → 클라이언트 단방향이라 SSE로 충분합니다. SSE는 일반 HTTP라 인증 헤더, 프록시, 로드밸런서, CDN과 호환이 좋고, 이벤트 ID 기반 재연결이 표준에 있습니다. WebSocket은 양방향 실시간(음성, 협업 편집, 사용자가 생성 중간에 끼어드는 인터랙션)이 필요할 때 씁니다. 대신 SSE는 프록시 버퍼링과 브라우저당 동시 연결 수 제한(HTTP/1.1에서 6개)에 주의해야 합니다.
</details>

<details>
<summary>10분 걸리는 에이전트 작업을 API로 어떻게 제공하나요?</summary>

요청을 받으면 작업을 큐에 넣고 `202 Accepted`와 job_id를 돌려줍니다. 워커가 작업을 실행하며 진행 이벤트와 체크포인트를 저장하고, 클라이언트는 상태 조회 API나 SSE 구독(재연결 시 Last-Event-ID), 또는 웹훅으로 결과를 받습니다. 워커가 죽어도 체크포인트에서 재개할 수 있게 하고, 작업에는 타임아웃과 취소 API를 둡니다.
</details>

<details>
<summary>사용자가 스트리밍 중에 창을 닫으면 서버에서는 무슨 일이 일어나야 하나요?</summary>

연결 종료를 감지해 LLM 스트림과 진행 중인 도구 호출을 취소해야 비용이 멈춥니다. 다만 부분 응답과 토큰 사용량은 저장해 과금·분석에 반영하고, 부수효과가 있는 도구가 실행 중이었다면 완료 여부를 기록해 재시도 시 중복 실행을 막습니다. 백그라운드 작업형이라면 반대로 연결과 무관하게 계속 진행하는 것이 맞습니다.
</details>
