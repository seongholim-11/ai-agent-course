## 1. 기초 개념

<details>
<summary>AI 에이전트란 무엇인가요?</summary>

LLM이 루프 안에서 도구를 사용하며, 관찰한 결과를 바탕으로 다음 행동을 스스로 결정해 목표를 달성하는 시스템입니다. 구성 요소는 추론을 담당하는 모델, 외부 세계와 상호작용하는 도구, 반복 실행과 종료를 관리하는 루프, 그리고 상태·메모리입니다. 고정된 흐름을 따르는 일반 LLM 앱과 달리 실행 경로가 동적이어서 개방형 문제에 강하지만, 비용·지연·예측 불가능성이 커지고 평가가 어렵습니다. → [4주차](../../phase-1/week-04/)
</details>

<details>
<summary>에이전트, 워크플로우, 챗봇의 차이는?</summary>

챗봇은 대화형 인터페이스로 보통 단일 호출이나 RAG로 답합니다. 워크플로우는 LLM과 도구가 코드로 미리 정한 경로(체이닝, 라우팅, 병렬화)를 따릅니다. 에이전트는 LLM이 다음 단계를 동적으로 결정합니다. 단계를 미리 알 수 있으면 워크플로우가 더 싸고 예측 가능하며, 에이전트는 단계 수와 내용을 미리 알 수 없을 때 씁니다. 실무에서는 하이브리드가 흔합니다. → [5주차](../../phase-1/week-05/)
</details>

<details>
<summary>LLM은 어떻게 텍스트를 생성하나요? 에이전트 설계에 어떤 영향을 주나요?</summary>

지금까지의 토큰을 보고 다음 토큰의 확률 분포를 계산해 샘플링하는 일을 반복합니다. 이 때문에 사실 확인 없이 그럴듯한 내용을 만들 수 있고(환각), 같은 입력에도 결과가 달라질 수 있으며(비결정성), 이전 호출을 기억하지 못합니다(상태 없음). 에이전트는 도구로 근거를 주입하고, 출력을 검증하고, 상태와 메모리를 애플리케이션에서 관리하고, 여러 번 실행해 평가해야 합니다. → [3주차](../../phase-0/week-03/)
</details>

<details>
<summary>Function calling(tool use)은 어떻게 동작하나요?</summary>

개발자가 도구의 이름·설명·입력 JSON Schema를 요청에 넣으면, 모델은 도구가 필요할 때 텍스트 대신 도구 이름과 인자를 담은 구조화된 호출을 생성하고 멈춥니다. 애플리케이션이 실제로 도구를 실행하고 결과를 호출 ID와 함께 다시 메시지로 넣으면, 모델은 결과를 보고 다음 호출이나 최종 답을 냅니다. 모델은 실행하지 않으므로 검증·권한·타임아웃은 애플리케이션의 책임입니다.
</details>

<details>
<summary>구조화 출력(Structured Output)을 안정적으로 받는 방법은?</summary>

프롬프트로 JSON을 요청하는 방법은 가장 약하고, 도구 호출을 강제해 인자로 받는 방법이 널리 쓰이며, 공급자가 디코딩 단계에서 스키마를 강제하는 네이티브 Structured Outputs가 가장 안정적입니다. 어느 경우든 Pydantic 같은 검증으로 값의 범위와 비즈니스 규칙을 확인하고, 검증 실패 시 에러를 모델에 돌려 재시도합니다. 형식이 맞는 것과 내용이 맞는 것은 다릅니다.
</details>

<details>
<summary>추론(reasoning) 모델은 에이전트에서 언제 쓰나요?</summary>

답하기 전에 내부 추론 토큰을 생성하는 모델로, 계획 수립, 복잡한 도구 선택, 코딩, 다단계 논리처럼 어려운 결정에서 정확도가 오릅니다. 대신 비용과 지연이 늘어나므로 모든 단계에 쓰지 않고, 계획·종합 같은 핵심 단계에 높은 추론 예산을, 분류·추출·요약 같은 단계에는 낮은 예산이나 작은 모델을 씁니다.
</details>

<details>
<summary>환각(hallucination)을 어떻게 줄이고 측정하나요?</summary>

검색·DB·API 도구로 근거를 주입하고, 근거 기반으로만 답하고 출처를 달게 하며, 근거가 없으면 거절하도록 지시합니다. 출력에 대해 사실 확인 단계나 인용 검증을 두고, 구조화 출력으로 형식을 고정합니다. 측정은 답의 각 주장이 근거 문서로 뒷받침되는지(충실도)를 검증된 judge와 사람 샘플로 평가하고, 답이 없는 질문을 평가 세트에 넣어 거절 정확도를 봅니다.
</details>

<details>
<summary>temperature는 에이전트에서 어떻게 설정하나요?</summary>

도구 선택, 분류, 추출, 코드 생성처럼 정확성이 중요한 단계는 낮게, 아이디어 생성이나 다양한 후보가 필요한 단계는 높게 둡니다. temperature 0도 완전히 결정적이지 않으므로 재현성은 평가를 여러 번 돌려 분포로 확인합니다. 추론 모델은 샘플링 파라미터 조정이 제한되는 경우가 있어 공급자 문서를 따릅니다.
</details>

## 2. 설계 패턴과 아키텍처

<details>
<summary>대표적인 에이전트 설계 패턴을 설명해보세요.</summary>

워크플로우 패턴으로는 단계를 순서대로 잇는 Prompt Chaining, 입력을 분류해 전문 경로로 보내는 Routing, 독립 작업을 동시에 하거나 여러 번 투표하는 Parallelization, 중앙에서 동적으로 작업을 나누는 Orchestrator–Workers, 생성과 평가를 반복하는 Evaluator–Optimizer가 있습니다. 에이전트 패턴으로는 생각-행동-관찰을 반복하는 ReAct, 먼저 계획하고 실행하는 Plan-and-Execute, 스스로 돌아보고 고치는 Reflection이 있습니다. 가장 단순한 것부터 시작해 필요할 때만 복잡도를 올리는 것이 원칙입니다.
</details>

<details>
<summary>ReAct와 Plan-and-Execute의 차이는?</summary>

ReAct는 한 걸음씩 생각하고 행동하고 관찰해 계획을 계속 조정하므로 적응력이 좋지만 턴이 많고 장기 목표를 잃기 쉽습니다. Plan-and-Execute는 먼저 전체 계획을 세운 뒤 단계를 실행하고 필요하면 재계획하므로 긴 작업에서 방향을 유지하고 일부 단계를 병렬화하거나 작은 모델로 실행할 수 있지만, 초기 계획이 틀리면 재계획 비용이 듭니다. 현대 코딩 에이전트는 todo 리스트로 두 방식을 섞습니다.
</details>

<details>
<summary>멀티 에이전트 시스템의 장단점은?</summary>

장점은 독립 작업의 병렬화로 시간 단축, 서브에이전트마다 깨끗한 컨텍스트를 써서 긴 작업을 감당하는 컨텍스트 격리, 하위 작업별로 다른 도구·모델·권한을 쓰는 전문화입니다. 단점은 토큰 사용량이 몇 배에서 십수 배로 늘어나는 비용, 에이전트 간 정보 손실과 결과 충돌, 디버깅과 평가의 어려움, 서로 얽힌 결정을 나눠 내리면 일관성이 깨지는 문제입니다. 가치가 높고 병렬화 가능한 넓은 탐색 작업에 맞습니다. → [8주차](../../phase-2/week-08/)
</details>

<details>
<summary>에이전트 시스템에서 상태(state)는 어떻게 관리하나요?</summary>

대화 메시지와 작업 상태를 명시적인 스키마로 정의하고, 단계마다 체크포인트로 외부 저장소에 저장합니다. 상태에는 결정에 필요한 것만 두고 큰 데이터는 파일·객체 저장소에 두어 참조만 넣습니다. 병렬 단계가 같은 키를 쓰면 병합 규칙(reducer)을 정의하고, thread 단위로 대화를 구분하며, 재개·되돌리기·사람 승인 대기를 지원합니다. → [7주차](../../phase-2/week-07/)
</details>

<details>
<summary>에이전트 프레임워크(LangGraph, Agents SDK, Claude Agent SDK, CrewAI 등)는 어떻게 고르나요?</summary>

통제와 내구성이 중요하고 고정 단계와 동적 판단이 섞인 복잡한 흐름이면 LangGraph처럼 명시적 그래프와 체크포인트가 있는 것을, 표준적인 도구 루프와 핸드오프·가드레일·트레이싱을 빠르게 원하면 OpenAI Agents SDK를, 파일·셸·서브에이전트·Skills 같은 코딩 에이전트형 하네스가 필요하면 Claude Agent SDK나 Deep Agents를, 비개발자와 협업하는 SaaS 자동화면 n8n 같은 로우코드를 고릅니다. 어느 것이든 내부의 루프를 직접 짤 수 있어야 디버깅이 됩니다.
</details>

<details>
<summary>에이전트에 사람 승인(HITL)은 어디에 넣나요?</summary>

되돌릴 수 없고 피해가 큰 행동(결제, 삭제, 외부 발송, 권한 변경), 신뢰할 수 없는 콘텐츠를 본 뒤의 외부 전송, 확신도가 낮은 판단에 넣습니다. 상태를 저장하고 멈췄다가 재개하는 방식으로 구현하고, 승인 화면에는 행동·인자·영향·되돌림 가능 여부를 보여줍니다. 승인이 너무 잦으면 습관적으로 누르게 되므로 위험도별로 정책을 나눕니다.
</details>

## 3. RAG와 검색

<details>
<summary>RAG 파이프라인을 설명하고 각 단계의 핵심 선택지를 말해보세요.</summary>

색인 시점에는 문서 파싱, 청킹(고정 길이, 구조 기반, 부모-자식), 문맥 추가, 임베딩, 벡터·키워드 색인과 메타데이터 저장을 합니다. 질의 시점에는 질의 재작성·분해, 하이브리드 검색(벡터 + BM25를 RRF로 결합), 리랭커로 상위 문서 선별, 권한 필터, 출처 인용이 있는 생성을 합니다. 품질 문제의 대부분은 검색에서 생기므로 Recall@k로 검색을 먼저 평가합니다. → [6주차](../../phase-1/week-06/)
</details>

<details>
<summary>임베딩이란 무엇이고 RAG 외에 어디에 쓰나요?</summary>

텍스트를 의미가 비슷하면 가까운 벡터로 바꾼 표현입니다. RAG 검색 외에 중복 제거, 클러스터링, 분류·라우팅, 메모리 검색, 유사 질문 기반 few-shot 예시 선택, 시맨틱 캐시에 씁니다. 도메인과 언어에 맞는 임베딩 모델을 평가 세트로 골라야 하고, 모델을 바꾸면 전체 재색인이 필요합니다.
</details>

<details>
<summary>리랭커는 왜 쓰나요?</summary>

1차 검색의 bi-encoder는 질문과 문서를 따로 임베딩해 빠르지만 정밀도가 낮습니다. cross-encoder 리랭커는 질문과 문서를 함께 읽어 관련도를 정확히 매기지만 느리므로, 1차로 수십 개를 뽑은 뒤 리랭커로 상위 몇 개를 고릅니다. 적은 수의 정확한 청크만 컨텍스트에 넣을 수 있어 생성 품질과 비용이 모두 좋아집니다.
</details>

<details>
<summary>RAG 평가 지표에는 무엇이 있나요?</summary>

검색 단계는 Recall@k(정답 청크가 상위 k개 안에 있는 비율), MRR, nDCG를 보고, 생성 단계는 충실도(답이 근거로 뒷받침되는가), 답변 관련성, 정답 일치, 거절 정확도를 봅니다. 생성 지표는 보통 LLM-as-judge로 계산하므로 사람 라벨로 검증해야 하고, 비용과 지연도 함께 봅니다.
</details>

<details>
<summary>긴 컨텍스트 모델 vs RAG, 어떻게 선택하나요?</summary>

작고 고정된 문서는 통째로 넣고 프롬프트 캐싱하는 것이 단순하고 정확할 수 있습니다. 지식 베이스가 크거나 자주 바뀌거나, 권한별로 볼 수 있는 문서가 다르거나, 비용·지연이 중요하면 RAG가 필요합니다. 긴 컨텍스트도 길어질수록 정확도가 떨어지는 문제가 있으므로, 실무에서는 검색으로 후보를 좁힌 뒤 넉넉히 넣는 조합이 흔합니다.
</details>

## 4. 프로토콜과 통합

<details>
<summary>MCP를 설명해주세요.</summary>

Model Context Protocol은 AI 애플리케이션이 외부 도구와 데이터에 연결되는 방식을 표준화한 오픈 프로토콜입니다. Host 안의 Client가 Server와 JSON-RPC로 통신하고, 서버는 모델이 호출하는 Tools, 애플리케이션이 컨텍스트로 붙이는 Resources, 사용자가 고르는 Prompts를 제공합니다. 로컬은 stdio, 원격은 Streamable HTTP와 OAuth 2.1을 씁니다. 통합을 한 번 만들면 여러 Host에서 재사용할 수 있어 N×M 통합 문제를 줄입니다. → [9주차](../../phase-2/week-09/)
</details>

<details>
<summary>MCP와 A2A의 차이는?</summary>

MCP는 에이전트가 도구·데이터에 접근하는 규격이고, A2A는 독립적인 에이전트끼리 작업을 위임하는 규격입니다. MCP의 도구는 스키마로 정의된 투명한 함수지만, A2A의 상대는 내부를 공개하지 않는 자율 에이전트로 Agent Card로 능력을 알리고 Task 수명주기(진행, 추가 정보 요청, 완료)와 아티팩트로 협업합니다. 조직 경계를 넘는 에이전트 협업에 A2A가 맞습니다. → [10주차](../../phase-2/week-10/)
</details>

<details>
<summary>좋은 도구(또는 MCP 서버)는 어떻게 설계하나요?</summary>

API를 1:1로 노출하지 말고 사용자 작업 단위로 묶어 개수를 줄이고, 이름과 설명에 언제 쓰고 언제 쓰지 말지를 쓰며, 인자는 적고 enum·형식 제약을 스키마에 담습니다. 결과는 다음 결정에 필요한 만큼만 간결하게 주고 페이지네이션과 잘림 표시를 하며, 에러 메시지는 고치는 방법을 담습니다. 읽기와 쓰기를 분리해 쓰기에 승인을 붙이고, 도구 설계 변경은 에이전트 성공률로 평가합니다.
</details>

## 5. 컨텍스트와 메모리

<details>
<summary>컨텍스트 엔지니어링이란?</summary>

에이전트가 매 턴 보는 전체 입력(시스템 프롬프트, 도구 정의, 대화, 도구 결과, 검색 문서, 메모리)을 동적으로 구성하는 일입니다. 컨텍스트는 길수록 비싸고 품질이 떨어지는 유한 자원이므로, 외부에 쓰기(노트, 파일), 필요할 때만 고르기(just-in-time 로딩, 검색), 압축하기(결과 절단, 오래된 결과 삭제, compaction), 격리하기(서브에이전트)로 고신호 정보만 남깁니다. 캐시 적중률도 함께 설계합니다. → [11주차](../../phase-3/week-11/)
</details>

<details>
<summary>Compaction의 장점과 위험은?</summary>

대화가 한도에 가까워질 때 지금까지의 내용을 요약해 새 컨텍스트로 이어가므로 긴 작업을 계속할 수 있습니다. 위험은 요약 과정에서 원래 제약 조건, 미묘한 실패 원인, 출처 정보가 사라지는 것입니다. 그래서 요약 프롬프트를 목표·제약·확정 사실·결정·실패·남은 일 체크리스트로 쓰고, 최근 턴은 원문 유지하며, 압축 전후 품질을 평가합니다. 가능하면 결과 삭제나 외부화 같은 덜 손실적인 방법을 먼저 씁니다.
</details>

<details>
<summary>에이전트 메모리의 종류와 구현은?</summary>

현재 세션의 작업 메모리(컨텍스트와 체크포인트), 사용자·도메인 사실의 의미 기억(프로필 문서나 사실 컬렉션), 과거 경험의 에피소드 기억(사건 요약 + 임베딩 검색), 일하는 방법의 절차 기억(규칙 파일, Skill)이 있습니다. 대화 후 백그라운드에서 추출해 기존 기억과 추가·갱신·삭제로 병합하고, 관련도·최신성·중요도로 검색해 넣습니다. 오래된 정보, 추측의 고착, 민감 정보, 메모리 인젝션을 관리해야 합니다. → [13주차](../../phase-3/week-13/)
</details>

<details>
<summary>Agent Skills란 무엇인가요?</summary>

특정 작업을 수행하는 절차적 지식을 폴더로 패키징한 것으로, SKILL.md의 이름·설명·지침과 보조 스크립트·템플릿으로 구성됩니다. 평소에는 이름과 설명만 컨텍스트에 있고, 작업에 맞는 Skill을 고르면 본문과 참고 파일을 그때 읽는 점진적 공개 방식이라 많이 설치해도 컨텍스트 비용이 작습니다. 외부 시스템 접근은 MCP·도구가, 어떻게 일할지는 Skill이 담당하는 식으로 함께 씁니다. → [12주차](../../phase-3/week-12/)
</details>

## 6. 평가와 관측

<details>
<summary>에이전트를 어떻게 평가하나요?</summary>

컴포넌트(검색 Recall, 라우터, 도구 인자), 궤적(필수·금지 도구, 효율), 엔드투엔드 결과(성공률, 비용, 지연), 온라인 지표(해결률, 이관률, 피드백)의 층위로 나눕니다. 실제 작업 기반 평가 세트를 만들고, 가능하면 환경 상태를 확인하는 코드 채점을, 열린 답에는 사람 라벨로 검증한 LLM-as-judge를 씁니다. 각 항목을 여러 번 실행해 pass^k와 신뢰구간을 보고, 지표를 정하기 전에 실패 사례를 직접 읽는 오류 분석을 합니다. → [14주차](../../phase-4/week-14/)
</details>

<details>
<summary>LLM-as-judge의 편향과 대응은?</summary>

긴 답을 선호하는 장황함 편향, 비교 평가에서 앞쪽 답을 선호하는 위치 편향, 자기 계열 모델 출력을 선호하는 자기 선호 편향, 척도가 넓을수록 일관성이 떨어지는 문제가 있습니다. 기준을 분리한 이진 판정, 근거 먼저 쓰기, 참고 정답 제공, 순서 바꿔 두 번 평가, 생성 모델과 다른 모델 사용으로 줄이고, 사람 라벨과의 일치율·kappa로 검증합니다.
</details>

<details>
<summary>프로덕션에서 무엇을 모니터링하나요?</summary>

요청당 비용과 캐시 적중률, 엔드투엔드·TTFT·도구별 지연의 p50·p95, LLM·도구 에러율과 재시도·타임아웃, 최대 턴 도달 비율, 온라인 judge 점수와 사용자 피드백, 거절·이관률, 도구 호출 패턴과 반복 루프를 봅니다. 모든 것을 트레이스 단위로 기록하고 프롬프트·모델·코드 버전을 붙여 변경 영향을 추적합니다. → [15주차](../../phase-4/week-15/)
</details>

<details>
<summary>프롬프트나 모델 변경의 회귀를 어떻게 막나요?</summary>

프롬프트를 코드처럼 버전 관리하고, 변경 PR마다 CI에서 평가 세트를 반복 실행해 기준 대비 점수·비용·지연과 항목별 변화를 비교합니다. 안전·정책 필수 항목은 하나라도 실패하면 막고, 전체 점수는 신뢰구간이나 임계값으로 판단합니다. 배포 후에는 점진 배포와 온라인 지표로 다시 확인하고, 프로덕션 실패를 평가 세트에 계속 추가합니다. → [16주차](../../phase-4/week-16/)
</details>

## 7. 보안

<details>
<summary>프롬프트 인젝션이란? 직접과 간접의 차이는?</summary>

입력 속 지시를 따르는 LLM의 성질을 악용해 의도하지 않은 행동을 하게 하는 공격입니다. 직접 인젝션은 사용자가 직접 입력하고, 간접 인젝션은 에이전트가 읽는 웹페이지·문서·메일·도구 결과·MCP 도구 설명·메모리에 지시를 숨깁니다. 에이전트에서는 공격자가 사용자가 아니어도 되는 간접 인젝션이 더 위험합니다. LLM에는 지시와 데이터를 구분하는 구조적 경계가 없어 근본적 해결책이 없습니다. → [17주차](../../phase-5/week-17/)
</details>

<details>
<summary>에이전트 보안을 위한 설계 원칙은?</summary>

뚫려도 피해가 제한되게 설계합니다. 최소 권한 도구와 사용자 권한 검사를 코드에서 강제하고, 기본값 거부 정책 엔진으로 위험 행동에 사람 승인을 붙이며, 비공개 데이터·신뢰할 수 없는 콘텐츠·외부 전송이 한 세션에 모이지 않게 lethal trifecta를 끊습니다. 모델이 만든 코드는 샌드박스에서, 외부 콘텐츠는 표시·격리하고, 출력의 PII와 외부 링크·이미지 렌더링을 제한하며, 감사 로그와 예산 제한을 둡니다. 공격 평가 세트로 방어율을 측정합니다. → [18주차](../../phase-5/week-18/)
</details>

<details>
<summary>에이전트가 고객 데이터를 다룰 때 개인정보는 어떻게 보호하나요?</summary>

도구가 필요한 최소 필드만 반환하고, 사용자 권한으로만 조회하며, 트레이스·로그 전송 전에 PII를 마스킹하고, 보존 기간과 접근 권한을 정합니다. 장기 메모리에 민감 정보를 저장하지 않는 규칙과 열람·삭제 기능을 두고, 외부 LLM·관측 서비스로의 전송이 개인정보 처리 위탁에 해당하는지 검토하며, 필요하면 민감 단계를 내부 모델로 처리합니다.
</details>

## 8. 프로덕션: 비용, 지연, 신뢰성

<details>
<summary>에이전트의 비용과 지연을 줄이는 방법은?</summary>

먼저 트레이스로 단계별로 분해합니다. 입력 토큰이 크면 프롬프트 캐싱 구조와 도구 결과 정리, 턴이 많으면 병렬 도구 호출과 도구·계획 개선, 모든 단계가 큰 모델이면 단계별 모델 분리·라우팅·캐스케이드, 실시간이 필요 없으면 배치 API를 씁니다. 체감 지연은 스트리밍과 진행 이벤트로 줄입니다. 각 변경은 평가 세트로 품질을 확인합니다. → [19주차](../../phase-6/week-19/)
</details>

<details>
<summary>프롬프트 캐싱은 어떻게 동작하고, 에이전트에서 왜 중요한가요?</summary>

입력의 앞부분이 이전 요청과 똑같으면 공급자가 처리 결과를 재사용해 할인된 가격과 짧은 TTFT로 처리합니다. 에이전트는 매 턴 시스템 프롬프트·도구 정의·이전 대화를 반복 입력하므로 효과가 큽니다. 변하지 않는 것을 앞에 두고, 시스템 프롬프트의 타임스탬프 같은 변하는 값을 제거하며, 도구 순서를 고정하고, 적중률을 측정합니다.
</details>

<details>
<summary>장시간 에이전트 작업의 신뢰성은 어떻게 확보하나요?</summary>

작업 큐와 워커 구조로 바꾸고, 체크포인트로 상태를 외부화해 마지막 완료 단계부터 재개하며, 일시적 오류는 지터 백오프로 재시도하고, 부수효과 도구는 멱등 키로 중복을 막습니다. LLM 호출·도구·턴·전체 작업에 계층적 타임아웃을 두고, 진행 이벤트를 저장해 재접속 시 이어받게 하며, 취소와 부분 완료를 지원합니다. 필요하면 durable execution 엔진을 쓰고 장애 시나리오로 검증합니다. → [21주차](../../phase-6/week-21/)
</details>

<details>
<summary>상용 API와 오픈 모델 자체 서빙은 어떻게 선택하나요?</summary>

품질이 최우선이고 사용량이 들쭉날쭉하면 상용 API, 데이터가 외부로 나가면 안 되거나(폐쇄망, 규제) 사용량이 크고 일정해 GPU 비용이 정당화되거나 파인튜닝 모델이 필요하면 자체 서빙입니다. 오픈 모델은 긴 다단계 도구 사용에서 격차가 남아 있는 경우가 많아, 민감 단계만 내부 모델로 보내는 하이브리드가 흔합니다. → [20주차](../../phase-6/week-20/)
</details>

<details>
<summary>파인튜닝은 언제 하나요?</summary>

프롬프트, 예시, RAG, 라우팅, 캐싱으로 충분하지 않고, 좁고 반복적인 작업(분류, 추출, 특정 형식·문체)을 대량으로 해서 작은 모델로 비용·지연을 크게 줄일 수 있을 때입니다. 지식 주입이 목적이면 보통 RAG가 낫습니다. 축적된 라벨 데이터와 평가 세트가 전제이고, 기반 모델 갱신마다 재학습하는 유지보수 부담을 고려합니다.
</details>

## 9. 트렌드와 견해

<details>
<summary>2026년 에이전트 엔지니어링의 주요 흐름은?</summary>

모델 바깥의 루프·도구·검증 장치를 설계하는 harness·loop 엔지니어링, 지시문보다 컨텍스트 구성 전체를 다루는 컨텍스트 엔지니어링, 작은 재사용 단위로 능력을 확장하는 Skills, MCP의 확산과 stateless 원격 서버·Tasks·에이전트 신원 같은 운영 기능, 코딩 에이전트가 개발의 기본 인터페이스가 된 것, 일반 벤치마크 대신 실제 작업 기반 평가, 그리고 에이전트 자체보다 게이트웨이·평가·가드레일·관측 같은 주변 시스템에 더 많은 공수가 드는 현상입니다.
</details>

<details>
<summary>에이전트를 도입하려는 회사에 가장 먼저 조언할 것은?</summary>

가장 단순한 해법부터 시작하고, 처음부터 평가 세트를 만들라고 하겠습니다. 실제 작업 20~50개와 성공 기준이 있으면 단일 호출, 워크플로우, 에이전트를 비교해 근거 있게 고를 수 있고, 이후 모델 교체와 프롬프트 변경도 숫자로 판단할 수 있습니다. 동시에 되돌릴 수 없는 행동에는 사람 승인을 두고 권한을 최소화해 안전하게 시작합니다.
</details>

<details>
<summary>에이전트가 아직 잘 못하는 것은 무엇이라고 생각하나요?</summary>

매번 같은 품질을 내는 일관성(pass^k), 수백 단계에 걸친 장기 작업에서의 목표 유지와 오류 누적, 애매한 상황에서 스스로 멈추고 묻는 판단, 프롬프트 인젝션에 대한 근본적 견고성, 그리고 서로 얽힌 결정을 여러 에이전트가 나눠 내릴 때의 일관성입니다. 그래서 지금은 검증 장치·사람 승인·좁은 권한으로 자율성의 범위를 설계하는 것이 엔지니어의 핵심 역할이라고 봅니다.
</details>

## 10. 경험 질문 답변 틀

경험 질문("가장 어려웠던 문제", "실패한 경험", "의견이 갈렸던 설계")은 아래 순서로 1~2분에 답합니다.

1. **상황:** 무엇을 만들고 있었나 (한 문장)
2. **문제:** 무엇이 안 됐나, **수치로**
3. **시도:** 처음 시도와 그것이 실패한 이유
4. **해결:** 최종 방법과 선택 이유(대안과 비교)
5. **결과:** 전후 수치
6. **배운 것:** 다음에 다르게 할 것

각 주차의 **회고 메모**에 이 틀로 적어둔 것이 그대로 답변 재료가 됩니다.

**필수**는 직접 써서 결과를 낸 경험이 있어야 하고, **우대**는 하나 이상 써봤으면 충분합니다.

| 영역 | 필수 | 우대 |
| --- | --- | --- |
| 언어·백엔드 | Python(asyncio, Pydantic), FastAPI, PostgreSQL, Docker, Git | TypeScript, Redis, Kubernetes |
| LLM API | 2개 이상 공급자, tool calling, 구조화 출력, 프롬프트 캐싱, 스트리밍 | 배치 API, 추론 예산 조절 |
| 에이전트 프레임워크 | LangGraph + Agent SDK 1곳 (OpenAI Agents SDK 또는 Claude Agent SDK) | Google ADK, CrewAI, n8n |
| 프로토콜 | MCP 서버·클라이언트 구현 | A2A, MCP OAuth |
| 검색 | 벡터 DB 1곳, 하이브리드 검색, 리랭킹, 검색 평가 | GraphRAG(Neo4j), 한국어 형태소 BM25 |
| 컨텍스트·메모리 | 결과 절단, compaction, 서브에이전트 격리, 장기 메모리 병합 | Skills 설계, Deep Agents |
| 평가·관측 | 평가 세트, 코드·궤적·judge 채점, judge 보정, Langfuse 또는 LangSmith, CI 평가 | OpenTelemetry GenAI, Ragas, Braintrust |
| 서빙·운영 | LiteLLM 라우팅·Fallback, 클라우드 1곳 배포, 작업 큐, 체크포인트 재개 | vLLM, Temporal, LoRA 파인튜닝 |
| 보안 | 인젝션 위협 모델, 정책 엔진, 샌드박스, HITL, PII 마스킹 | 레드팀 도구(garak, PyRIT) |
