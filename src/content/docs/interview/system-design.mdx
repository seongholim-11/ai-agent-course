## 45분 진행 프레임워크

| 시간 | 단계 | 할 일 |
| --- | --- | --- |
| 0–5분 | 요구사항 | 사용자, 핵심 작업, 규모(일 요청 수, 동시 사용자), 지연 요구, 정확도 요구, 위험한 행동, 데이터 민감도, 예산 |
| 5–10분 | 성공 기준 | 어떤 지표로 성공을 판단할지(작업 성공률, 해결률, 비용, p95), 평가 세트를 어떻게 만들지 |
| 10–25분 | 고수준 설계 | 단일 호출 / 워크플로우 / 에이전트 / 멀티 에이전트 중 선택과 **이유**, 구성 요소와 데이터 흐름 그리기 |
| 25–38분 | 깊이 파기 | 면접관이 고르거나 내가 제안: 컨텍스트·메모리, 도구 설계, 신뢰성, 보안, 비용 |
| 38–45분 | 운영 | 평가·관측·배포·장애 대응, 확장 시 병목, 트레이드오프 정리 |

<Aside type="tip" title="점수를 가르는 것">
면접관이 가장 높게 보는 것은 **"가장 단순한 해법에서 출발해, 요구사항 때문에 복잡도를 올리는 과정을 말로 보여주는 것"**과 **"어떻게 측정할 것인가"**를 먼저 꺼내는 것입니다. 프레임워크 이름 나열은 점수가 되지 않습니다.
</Aside>

## 공통으로 그리는 구성 요소

```
Client ─▶ API Gateway(인증, 레이트 리밋) ─▶ Agent Service ─▶ LLM Gateway(라우팅, Fallback, 예산) ─▶ 공급자 / 자체 모델
                                              │
                         ┌────────────────────┼─────────────────────┐
                    Tool Layer           State Store            Job Queue + Workers
              (정책 엔진, MCP 서버,      (체크포인트, 대화,       (장기 작업, 재시도)
               권한 검사, 샌드박스)       메모리, 벡터 DB)
                                              │
                               Observability (트레이스, 비용, 평가 점수) ─▶ Eval/CI
```

## 연습 문제 1. 커머스 고객 지원 에이전트

**요구사항 예:** 일 5만 건 문의, 70%를 사람 없이 해결, p95 8초, 환불·주소 변경 가능, 개인정보 포함.

설계 포인트:

- **라우팅:** 단순 FAQ는 고정 RAG(싸고 빠름), 주문·환불은 도구 에이전트, 불만·복잡 건은 사람 이관. 분류기는 작은 모델.
- **도구:** `get_order`, `check_refund_policy`, `request_refund`(금액·조건별 승인), `update_address`(본인 확인 후). 고객 본인 데이터만 반환하도록 도구 계층에서 강제.
- **RAG:** 정책 문서 하이브리드 검색 + 리랭크, 정책 버전·유효일 메타데이터.
- **인젝션:** 주문 메모·리뷰 등 고객 입력 필드는 untrusted로 표시, 결제 도구는 정책 엔진 통과 필수.
- **평가:** 실제 문의 로그에서 평가 세트, 해결률·정책 위반 0건(must-pass)·pass^k, 사람 이관률과 해결 문의당 비용.
- **규모:** 5만 건/일 ≈ 피크 초당 수 건. LLM 레이트 리밋과 비용 예산이 실질 제약. 캐싱과 작은 모델 비중으로 단가 계산.

## 연습 문제 2. 사내 딥리서치 에이전트

**요구사항 예:** 직원 1만 명, 사내 문서(권한 다양) + 웹, 보고서 10~30분, 동시 작업 수백 개.

설계 포인트:

- **멀티 에이전트 정당화:** 하위 주제 조사가 독립적이고 넓음 → Orchestrator–Worker. 단순 질문은 싱글 에이전트로 라우팅해 비용 절감.
- **권한:** 사내 문서 검색에 요청자 권한 필터를 검색 엔진 수준에서 적용. 서브에이전트도 요청자 권한을 상속.
- **작업 모델:** `POST /jobs` → 큐 → 워커, SSE 진행 이벤트 + 완료 알림, 체크포인트 재개, 취소.
- **컨텍스트:** 워커 결과는 파일·객체 저장소, 오케스트레이터에는 요약과 참조만.
- **lethal trifecta:** 웹 콘텐츠를 읽는 워커에는 사내 문서 도구와 외부 전송 도구를 함께 주지 않음. 최종 보고서 내 외부 이미지·링크 렌더링 제한.
- **비용 통제:** 사용자·부서별 예산, 워커 작은 모델, 동시 작업 상한, 우선순위 큐.
- **평가:** 주제 세트, 루브릭 judge + 인용 정확도, 싱글 대비 비교.

## 연습 문제 3. 코딩 에이전트(PR 자동 생성) 플랫폼

**요구사항 예:** 이슈를 받아 코드 수정 PR을 생성, 사내 저장소 수백 개.

설계 포인트:

- **하네스:** 파일 읽기·편집·검색·테스트 실행 도구, todo 계획, 저장소별 메모리 파일(빌드·테스트 명령), Skills.
- **샌드박스:** 작업마다 일회용 컨테이너에 저장소 클론, 네트워크 허용 목록(패키지 레지스트리만), 비밀 없음.
- **검증 바깥 루프:** 테스트·린터·타입체크 통과까지 최대 N회 재시도, 실패 시 사람에게 요약과 함께 넘김.
- **멀티 에이전트 주의:** 하나의 변경은 단일 에이전트가 일관되게. 병렬화는 서로 다른 이슈 단위로.
- **권한:** PR 생성까지만, 머지는 사람. 보호 브랜치 푸시 금지 훅.
- **평가:** 내부 해결된 이슈로 만든 SWE-bench식 세트(테스트 통과율), 리뷰어 수정량, PR 채택률.
- **병목:** 사람 리뷰가 병목이 되므로 계획 단계에서 승인받는 흐름, 변경 요약 품질.

## 연습 문제 4. 폐쇄망 금융 문서 분석 에이전트

**요구사항 예:** 외부 API 사용 불가, 대출 심사 문서 분석 보조, 감사 추적 필수.

설계 포인트:

- **모델:** vLLM으로 오픈 모델 서빙(GPU 용량 산정: 모델 크기 × 정밀도 + KV 캐시), 양자화 품질 평가.
- **오픈 모델 한계 보완:** 자율 에이전트보다 단계가 명확한 워크플로우, 구조화 디코딩, 단계별 검증, 도구 수 최소화.
- **RAG:** 내부 임베딩·리랭커 모델, 문서 권한 필터.
- **감사:** 모든 입력·근거 문서·모델 버전·출력을 변경 불가능한 로그로, 사람 최종 판단 필수(에이전트는 보조).
- **공급망:** 모델·패키지 해시 검증, 오프라인 업데이트 절차.
- **평가:** 과거 심사 사례로 추출 정확도, 근거 인용률, 사람 검토 시간 단축.

## 면접관이 자주 던지는 꼬리 질문

1. 트래픽이 10배가 되면 무엇이 먼저 깨지나? (LLM 레이트 리밋, 비용, 상태 저장소, 사람 리뷰)
2. 주 LLM 공급자가 한 시간 다운되면? (게이트웨이 Fallback, 기능 강등, 큐 적체 관리)
3. 품질이 떨어졌다는 신고가 오면 어떻게 원인을 찾나? (버전 메타데이터 → 트레이스 비교 → 평가 재실행)
4. 이 설계에서 가장 위험한 보안 경로는? (lethal trifecta가 모이는 지점을 지목)
5. 비용을 절반으로 줄이라면? (분해 → 캐싱 → 모델 분리 → 턴 감소 → 배치)
6. 왜 멀티 에이전트가 아닌가 / 왜 멀티 에이전트인가?
