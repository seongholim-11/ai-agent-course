## 학습 목표

- 요청 하나의 비용과 지연을 단계별로 분해해 어디부터 줄일지 정한다
- 모델 라우팅·캐스케이드·Fallback을 구성한다
- 프롬프트 캐싱 적중률을 측정하고 높인다
- 최적화가 품질을 해치지 않았음을 평가로 증명한다

## 최적화의 순서

비용을 줄이는 원칙은 가계부 정리와 같습니다. 먼저 어디에 돈이 나가는지 영수증을 모으고(측정), 가장 큰 지출부터 줄이고(우선순위), 줄인 뒤에도 생활이 괜찮은지 확인합니다(품질 확인). 감으로 "커피값부터 줄이자"고 하면, 사실 월세가 대부분이었을 수 있습니다.

**측정 → 가장 큰 항목부터 → 품질 확인 → 반복.** 15주차 트레이스로 단계별 비용과 지연을 뽑아보면, 대개 다음 중 하나가 압도적입니다.

| 증상 | 흔한 원인 | 처방 |
| --- | --- | --- |
| 입력 토큰이 비용의 대부분 | 긴 대화를 매 턴 다시 입력, 큰 도구 결과 | 캐싱, 결과 절단, compaction (11주차) |
| 턴 수가 많음 | 순차 도구 호출, 나쁜 도구 설계, 헤매는 계획 | 병렬 호출, 도구 통합, 계획 단계, 예시 |
| 모든 단계에 큰 모델 | 기본값 그대로 | 라우팅, 단계별 모델 분리 |
| TTFT(첫 토큰까지)가 김 | 긴 프롬프트, 캐시 미스 | 캐시 구조 개선, 프롬프트 다이어트 |
| 출력 시간이 김 | 장황한 출력, 불필요한 추론 | 출력 형식 제한, 추론 예산 조절 |
| 같은 질문 반복 | 캐시 없음 | 응답·검색 결과 캐시(시맨틱 캐시는 신중히) |

## 핵심 개념

### 1. 단계별 모델 분리

에이전트의 모든 단계가 똑같이 똑똑한 모델을 필요로 하지 않습니다. 회사에서 서류 분류는 신입이, 전략 수립은 임원이 하듯, 쉬운 일에는 작고 싼 모델을, 어려운 판단에만 크고 비싼 모델을 씁니다. 큰 모델과 작은 모델의 가격 차이는 보통 5~20배입니다.

```python
MODELS = {
    "router":     "small",    # 문의 분류·라우팅: 선택지 몇 개 중 고르기 → 작은 모델로 충분
    "worker":     "small",    # 검색 결과 요약, 정보 추출: 범위가 좁고 반복적
    "planner":    "large",    # 계획·어려운 추론: 여기서 틀리면 뒤가 다 틀리므로 큰 모델
    "writer":     "medium",   # 최종 보고서 작성: 문장 품질이 중요
    "judge":      "medium",   # 평가: 생성 모델과 "다른 계열"을 권장 (14주차 자기 선호 편향)
    "guardrail":  "small",    # 위험 입력 감지: 빠르고 싸야 매 요청에 돌릴 수 있다
}
```

8주차 멀티 에이전트에서 워커만 작은 모델로 바꿔도 총비용이 크게 줄어드는 경우가 많습니다. 워커가 토큰의 대부분을 쓰기 때문입니다.

### 2. 라우팅과 캐스케이드

어떤 요청에 어떤 모델을 쓸지 정하는 방법은 두 가지입니다.

- **라우팅:** 입력을 보고 **처음부터** 적절한 모델로 보냅니다(5주차 Routing). 병원 접수처가 증상을 보고 동네 의원으로 보낼지 대학병원으로 보낼지 정하는 것과 같습니다. 분류기는 작은 LLM, 임베딩 기반 분류, 또는 단순 규칙("질문이 20자 이하면 small").
- **캐스케이드:** 작은 모델로 **먼저 시도**하고, 결과가 미덥지 않거나 검증에 실패하면 큰 모델로 다시 합니다. 동네 의원에서 먼저 진료받고, 해결이 안 되면 대학병원으로 가는 방식입니다. 결과를 코드로 검증할 수 있는 작업(구조화 추출, 테스트가 있는 코드)에 특히 효과적입니다.

```python
async def cascade(task):
    r = await run(task, model="small")         # 1) 싼 모델로 먼저 시도
    # 2) 결과가 형식 검증을 통과하고, 스스로 매긴 확신도도 높으면 그대로 쓴다
    if validate(r) and r.confidence >= 0.8:
        return r
    return await run(task, model="large")      # 3) 아니면 비싼 모델로 다시 (이때만 비용이 크게 든다)
```

캐스케이드가 제대로 동작하려면 `validate`가 믿을 만해야 합니다. 검증이 허술하면 틀린 답을 그대로 통과시키고, 너무 까다로우면 매번 큰 모델로 넘어가서 오히려 비용이 늘어납니다.

### 3. LiteLLM으로 게이트웨이 구성

**LLM 게이트웨이**는 앱과 여러 LLM 공급자 사이에 놓는 중간 관문입니다. 앱은 게이트웨이 하나만 보고 요청하고, 게이트웨이가 어느 공급자의 어느 모델로 보낼지, 실패하면 어디로 돌릴지, 예산을 넘었는지를 처리합니다. 3주차에 만든 공통 클라이언트를 별도 서버로 키운 것이라고 보면 됩니다. **LiteLLM**은 대표적인 오픈소스 게이트웨이입니다.

```yaml
# litellm_config.yaml
model_list:
  - model_name: fast                                  # 앱이 부르는 "별칭"
    litellm_params: { model: anthropic/claude-haiku-4-5 }
  - model_name: fast                                  # 같은 별칭에 두 모델 → 둘 사이에서 부하를 나누거나 대체
    litellm_params: { model: openai/gpt-5-mini }
  - model_name: smart
    litellm_params: { model: anthropic/claude-sonnet-4-5 }
router_settings:
  routing_strategy: latency-based-routing             # 같은 별칭 안에서 응답이 빠른 쪽으로 보낸다
  num_retries: 2                                      # 일시적 오류는 2번 재시도
  fallbacks: [{ smart: [fast] }]                      # smart가 장애면 fast로 대신 처리 (기능 강등)
  context_window_fallbacks: [{ fast: [smart] }]       # 입력이 fast 모델 한도를 넘으면 더 큰 모델로
litellm_settings:
  max_budget: 50                                      # 전체 예산 USD
  budget_duration: 30d                                # 30일마다 초기화
```

앱은 OpenAI 호환 주소 하나만 알고, 모델 이름 자리에 `fast`, `smart` 같은 별칭만 씁니다. 그러면 실제 모델 교체, 공급자 장애 대응, API 키 관리, 팀별 예산, 사용량 기록이 모두 게이트웨이 한곳에서 해결됩니다. 앱 코드를 고치지 않고 설정 파일만 바꿔 모델을 갈아끼울 수 있습니다. 단점은 공급자 고유 기능(일부 캐싱 옵션, 서버 측 도구)이 공통 인터페이스에 가려 쓰기 어려워질 수 있다는 것입니다.

### 4. 프롬프트 캐싱 최적화

3주차 프롬프트 캐싱을 실제로 얼마나 활용하고 있는지 **적중률**로 잽니다.

```python
def cache_hit_rate(logs):
    read = sum(l["cache_read_tokens"] for l in logs)   # 캐시에서 읽은(할인받은) 입력 토큰
    total_in = sum(l["input_tokens"] for l in logs)    # 전체 입력 토큰
    return read / total_in                              # 예: 0.78 → 입력의 78%가 캐시로 처리됨
```

적중률을 올리는 방법은 모두 "앞부분을 매번 똑같이 유지하라"로 요약됩니다.

- 고정된 내용을 앞으로: 시스템 → 도구 → 고정 문서 → 대화
- 도구 정의 순서를 고정한다. 요청마다 도구 목록이 바뀐다면 뒤쪽에 두거나 별도 방식으로
- 시스템 프롬프트에서 타임스탬프·요청 ID를 뺀다
- 오래된 도구 결과 삭제는 몇 턴에 한 번씩 묶어서 (매 턴 캐시를 깨지 않게, 11주차)
- 캐시 유효 시간(보통 수 분) 안에 다음 요청이 오게. 사람 승인을 30분 기다리면 캐시가 만료된다
- 서브에이전트들이 같은 시스템 프롬프트·도구 정의로 시작하게 해서 캐시를 공유한다

에이전트 루프는 매 턴 앞부분이 같아서 적중률 70~90%도 가능합니다. 그런데 막상 측정해보면 생각보다 낮은 경우가 많고, 원인은 대부분 앞쪽 어딘가에 매번 바뀌는 값이 숨어 있기 때문입니다.

### 5. 배치와 비동기

즉시 답이 필요 없는 작업(야간 평가 실행, 대량 문서 요약, 색인용 문맥 생성)은 **배치 API**로 보내면 보통 **절반 가격**입니다. 요청을 한꺼번에 맡기면 공급자가 한가한 시간에 처리하고 수 시간 안에 결과를 돌려줍니다. 급하지 않은 택배를 일반 배송으로 보내 배송비를 아끼는 것과 같습니다. 16주차 full 평가와 6주차 Contextual Retrieval 생성에 딱 맞습니다.

## 심화

### 지연을 줄이는 구조 변경

- **병렬 도구 호출 유도:** 시스템 프롬프트에 "독립적인 조회는 한 번에 동시에 호출하라"를 넣습니다. 3번 왕복할 것을 1번에 끝냅니다.
- **추측 실행(speculative):** 다음에 필요할 가능성이 높은 검색을 미리 시작해둡니다. 손님이 메뉴를 고르는 동안 자주 시키는 메뉴의 재료를 미리 꺼내두는 것과 같습니다.
- **스트리밍 UX:** 총 시간은 같아도 첫 글자와 "검색 중…" 같은 진행 표시를 빨리 보여주면 사람이 느끼는 지연이 크게 줄어듭니다(2주차).
- **단계 생략:** 라우터가 간단한 질문이라고 판단하면 계획·검증 단계를 건너뜁니다.
- **추론 예산 조절:** 어려운 계획 단계에만 높은 추론 예산을 주고, 나머지는 낮게(3주차).

### 시맨틱 캐시의 함정

**시맨틱 캐시**는 "뜻이 비슷한 질문이 오면 이전 답을 재사용"하는 캐시입니다. 그럴듯하지만 위험합니다.

- "환불 **가능**해?"와 "환불 **불가능**해?"는 임베딩이 매우 가깝지만 답은 정반대일 수 있습니다.
- "내 주문 언제 와?"는 사용자마다, 날마다 답이 다릅니다. 남의 배송 정보를 보여줄 수도 있습니다.

쓰더라도 공개 FAQ처럼 **누가 언제 물어도 답이 같은** 영역에만 쓰고, 높은 유사도 기준과 평가로 검증합니다. 대신 **검색 결과 캐시**나 **도구 결과 캐시**(같은 API를 같은 인자로 부르면 결과 재사용)가 훨씬 안전합니다.

### 비용의 단위경제

"요청당 $0.03"이라는 숫자는 그 자체로는 비싼지 싼지 알 수 없습니다. **"해결된 문의 1건당 비용"**, **"사람 상담 1건 대비 비용"**처럼 비즈니스 단위로 말해야 의미가 생깁니다. 에이전트가 문의당 500원이어도 사람 상담(건당 5,000원)을 대체하면 이득이고, 문의당 50원이어도 해결률이 10%라서 결국 사람이 다시 처리해야 한다면 손해입니다. 면접에서 비용을 이렇게 설명하면 시니어처럼 들립니다.

### 파인튜닝은 언제?

**파인튜닝**은 이미 학습된 모델을 내 데이터로 추가 학습시키는 것입니다. 프롬프트·라우팅·캐싱으로 충분하지 않고, 분류·추출·특정 형식 생성처럼 **좁은 작업을 대량으로** 할 때, 작은 모델을 파인튜닝(LoRA 등)하거나 큰 모델의 출력을 작은 모델에게 학습시키면(증류) 비용이 크게 줄 수 있습니다. 16주차에서 쌓은 라벨 데이터가 여기서 쓰입니다.

다만 유지보수 부담이 큽니다. 기반 모델이 새로 나올 때마다 다시 학습해야 하고, 학습 파이프라인도 관리해야 합니다. 그래서 **마지막 수단**으로 봅니다.

## 실습 과제: 품질 유지하며 비용 40% 줄이기

대상: 8주차 리서치 에이전트 또는 포트폴리오 프로젝트 1(Report Generation Agent).

**요구사항**

1. 기준선: 평가 세트(10~20개)를 3회 돌려 품질·요청당 비용·p50/p95 지연·캐시 적중률을 기록한다.
2. 비용 분해: 단계별(플래너, 워커, 작성, 검증) 토큰·비용 비율 차트.
3. 최적화를 **하나씩** 적용하며 매번 같은 평가를 돌린다.
   - 단계별 모델 분리
   - 캐시 구조 개선
   - 도구 결과 절단·정리
   - 병렬 도구 호출 유도
   - (선택) 캐스케이드
4. LiteLLM 프록시를 앞에 두고 Fallback(주 모델 장애 시뮬레이션)을 시험한다.
5. 최종 결과표와 "어떤 최적화가 얼마나 기여했는지" 워터폴 형태의 분석을 README에 쓴다.

**채점 기준**

- [ ] 요청당 비용 40% 이상 감소
- [ ] 품질 점수 하락이 신뢰구간 안(통계적으로 유의한 하락 없음)
- [ ] 캐시 적중률 전후 수치가 있다
- [ ] Fallback이 실제로 동작한 로그가 있다

"하나씩" 적용하는 이유: 다섯 가지를 한꺼번에 바꾸면 비용이 40% 줄어도 무엇이 효과였는지, 품질이 떨어졌다면 무엇 때문인지 알 수 없습니다.

먼저 트레이스로 단계별 비용을 분해해 가장 큰 항목을 찾습니다. 보통 입력 토큰이 지배적이므로 프롬프트 캐싱 구조(고정 내용 앞쪽, 변하는 값 제거)를 고치고, 큰 도구 결과를 절단·정리합니다. 다음으로 단계별로 모델을 나눠 라우팅·요약·추출은 작은 모델로 보내고, 턴 수를 줄이도록 병렬 호출과 도구 설계를 개선합니다. 실시간이 필요 없는 작업은 배치 API로 돌립니다. 각 변경마다 평가 세트로 품질이 유지되는지 확인합니다.
</details>

<details>
<summary>모델 라우팅과 캐스케이드의 차이는?</summary>

라우팅은 입력을 보고 처음부터 적절한 모델 하나를 고르는 방식이라 지연 추가가 적지만, 분류기가 틀리면 어려운 질문이 작은 모델로 갑니다. 캐스케이드는 작은 모델로 먼저 시도하고 검증이나 확신도 기준을 통과하지 못하면 큰 모델로 재시도하는 방식이라, 검증 가능한 작업에서 품질을 지키며 비용을 줄이지만 실패 시 지연이 늘어납니다. 둘을 섞어 쓰기도 합니다.
</details>

<details>
<summary>LLM 게이트웨이(LiteLLM 등)를 두는 이유는?</summary>

여러 공급자를 하나의 인터페이스로 통일하고, 공급자 장애 시 Fallback, 지연·비용 기반 라우팅, 재시도, 키·시크릿 중앙 관리, 팀·사용자별 예산과 레이트 리밋, 사용량·비용 기록을 한곳에서 처리하기 위해서입니다. 애플리케이션 코드가 특정 공급자에 묶이지 않습니다. 대신 공급자 고유 기능을 쓰기 어려워질 수 있고, 게이트웨이 자체가 장애 지점이 되므로 고가용성으로 운영해야 합니다.
</details>
