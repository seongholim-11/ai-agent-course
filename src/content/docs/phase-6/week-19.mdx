## 학습 목표

- 요청 하나의 비용과 지연을 단계별로 분해해 어디부터 줄일지 정한다
- 모델 라우팅·캐스케이드·Fallback을 구성한다
- 프롬프트 캐싱 적중률을 측정하고 높인다
- 최적화가 품질을 해치지 않았음을 평가로 증명한다

## 최적화의 순서

**측정 → 가장 큰 항목부터 → 품질 확인 → 반복.** 감으로 최적화하지 않습니다. 15주차 트레이스로 단계별 비용과 지연을 뽑으면, 대개 다음 중 하나가 압도적입니다.

| 증상 | 흔한 원인 | 처방 |
| --- | --- | --- |
| 입력 토큰이 비용의 대부분 | 긴 대화 반복 입력, 큰 도구 결과 | 캐싱, 결과 절단, compaction (11주차) |
| 턴 수가 많음 | 순차 도구 호출, 나쁜 도구 설계, 헤매는 계획 | 병렬 호출, 도구 통합, 계획 단계, 예시 |
| 모든 단계에 큰 모델 | 기본값 그대로 | 라우팅, 단계별 모델 분리 |
| TTFT가 김 | 긴 프롬프트, 캐시 미스 | 캐시 구조 개선, 프롬프트 다이어트 |
| 출력 시간이 김 | 장황한 출력, 불필요한 추론 | 출력 형식 제한, 추론 예산 조절 |
| 같은 질문 반복 | 캐시 없음 | 응답·검색 결과 캐시(시맨틱 캐시는 신중히) |

## 핵심 개념

### 1. 단계별 모델 분리

에이전트의 모든 단계가 같은 지능을 필요로 하지 않습니다.

```python
MODELS = {
    "router":     "small",    # 분류·라우팅
    "worker":     "small",    # 검색 결과 요약, 추출
    "planner":    "large",    # 계획·어려운 추론
    "writer":     "medium",   # 최종 작성
    "judge":      "medium",   # 평가 (생성 모델과 다른 계열 권장)
    "guardrail":  "small",
}
```

8주차 멀티 에이전트에서 워커를 작은 모델로 바꾸는 것만으로 총비용이 크게 줄어드는 경우가 많습니다.

### 2. 라우팅과 캐스케이드

- **라우팅:** 입력을 보고 처음부터 적절한 모델로 보냅니다. 분류기는 작은 LLM, 임베딩 기반 분류, 또는 규칙.
- **캐스케이드:** 작은 모델로 먼저 시도하고, 결과의 확신도가 낮거나 검증에 실패하면 큰 모델로 다시 합니다. 검증 가능한 작업(구조화 추출, 테스트가 있는 코드)에 특히 효과적입니다.

```python
async def cascade(task):
    r = await run(task, model="small")
    if validate(r) and r.confidence >= 0.8:
        return r
    return await run(task, model="large")
```

### 3. LiteLLM으로 게이트웨이 구성

```yaml
# litellm_config.yaml
model_list:
  - model_name: fast
    litellm_params: { model: anthropic/claude-haiku-4-5 }
  - model_name: fast
    litellm_params: { model: openai/gpt-5-mini }     # 같은 이름 = 로드밸런싱/대체
  - model_name: smart
    litellm_params: { model: anthropic/claude-sonnet-4-5 }
router_settings:
  routing_strategy: latency-based-routing
  num_retries: 2
  fallbacks: [{ smart: [fast] }]                      # smart 실패 시 fast로
  context_window_fallbacks: [{ fast: [smart] }]       # 컨텍스트 초과 시 큰 모델로
litellm_settings:
  max_budget: 50          # USD
  budget_duration: 30d
```

애플리케이션은 OpenAI 호환 엔드포인트 하나만 보고 모델 이름(`fast`, `smart`)으로 부릅니다. 공급자 장애 대응, 키 관리, 팀별 예산, 사용량 기록이 한곳에 모입니다. 단점은 공급자 고유 기능(일부 캐싱 옵션, 서버 도구)이 추상화에 가려질 수 있다는 것입니다.

### 4. 프롬프트 캐싱 최적화

```python
def cache_hit_rate(logs):
    read = sum(l["cache_read_tokens"] for l in logs)
    total_in = sum(l["input_tokens"] for l in logs)
    return read / total_in
```

적중률을 올리는 방법:

- 고정 내용을 앞으로: 시스템 → 도구 → 고정 문서 → 대화
- 도구 정의 순서 고정, 동적으로 바뀌는 도구 목록은 뒤쪽이나 별도 메커니즘으로
- 시스템 프롬프트에서 타임스탬프·요청 ID 제거
- 오래된 도구 결과 삭제는 묶어서(캐시를 매 턴 깨지 않게)
- 캐시 유효 시간 안에 다음 요청이 오도록(긴 사람 대기 후에는 미스)
- 서브에이전트들이 같은 시스템 프롬프트·도구 접두사를 공유하게

에이전트 루프는 매 턴 접두사가 같아서 적중률 70~90%도 가능합니다. 측정해보면 생각보다 낮은 경우가 많은데, 대부분 앞쪽에 변하는 값이 있기 때문입니다.

### 5. 배치와 비동기

실시간이 필요 없는 작업(야간 평가, 대량 문서 요약, 색인용 문맥 생성)은 **배치 API**로 보내면 보통 절반 가격입니다. 응답은 수 시간 안에 옵니다. 16주차 full 평가와 6주차 Contextual Retrieval 생성에 적합합니다.

## 심화

### 지연을 줄이는 구조 변경

- **병렬 도구 호출을 유도:** 시스템 프롬프트에 "독립적인 조회는 한 번에 동시에 호출하라".
- **추측 실행(speculative):** 다음에 필요할 가능성이 높은 검색을 미리 시작.
- **스트리밍 UX:** 총 시간은 같아도 첫 토큰과 진행 이벤트를 빨리 보여주면 체감 지연이 크게 줄어듭니다.
- **단계 생략:** 라우터가 간단한 질문이라 판단하면 계획·검증 단계를 건너뜀.
- **추론 예산 조절:** 어려운 계획 단계만 높은 추론, 나머지는 낮게.

### 시맨틱 캐시의 함정

"비슷한 질문이면 이전 답을 재사용"하는 시맨틱 캐시는 위험합니다. "환불 가능해?"와 "환불 불가능해?"는 임베딩이 매우 가깝습니다. 사용자별·시점별로 답이 달라지는 질문에도 쓸 수 없습니다. 쓰더라도 공개 FAQ처럼 답이 고정된 영역에 한정하고, 높은 임계값과 평가로 검증합니다. **검색 결과 캐시**나 **도구 결과 캐시**(같은 API 호출)가 더 안전합니다.

### 비용의 단위경제

"요청당 $0.03"보다 **"해결된 문의당 비용"**, **"사람 상담 대비 비용"**처럼 비즈니스 단위로 말할 수 있어야 합니다. 에이전트가 비싸도 사람 상담 1건을 대체하면 이득이고, 싸도 해결률이 낮으면 손해입니다. 면접에서 이렇게 말하면 시니어처럼 들립니다.

### 파인튜닝은 언제?

프롬프트·라우팅·캐싱으로 충분하지 않고, 특정 좁은 작업(분류, 추출, 특정 형식 생성)을 대량으로 할 때 작은 모델을 파인튜닝(LoRA 등)하거나 큰 모델의 출력으로 증류하면 비용이 크게 줄 수 있습니다. 16주차에서 쌓은 라벨 데이터가 여기서 쓰입니다. 다만 유지보수 부담(모델 갱신마다 재학습)이 있으므로 마지막 수단으로 봅니다.

## 실습 과제: 품질 유지하며 비용 40% 줄이기

대상: 8주차 리서치 에이전트 또는 포트폴리오 프로젝트 1(Report Generation Agent).

**요구사항**

1. 기준선: 평가 세트(10~20개)를 3회 돌려 품질·요청당 비용·p50/p95 지연·캐시 적중률을 기록한다.
2. 비용 분해: 단계별(플래너, 워커, 작성, 검증) 토큰·비용 비율 차트.
3. 최적화를 **하나씩** 적용하며 매번 같은 평가를 돌린다.
   - 단계별 모델 분리
   - 캐시 구조 개선
   - 도구 결과 절단·정리
   - 병렬 도구 호출 유도
   - (선택) 캐스케이드
4. LiteLLM 프록시를 앞에 두고 Fallback(주 모델 장애 시뮬레이션)을 시험한다.
5. 최종 결과표와 "어떤 최적화가 얼마나 기여했는지" 워터폴 형태의 분석을 README에 쓴다.

**채점 기준**

- [ ] 요청당 비용 40% 이상 감소
- [ ] 품질 점수 하락이 신뢰구간 안(통계적으로 유의한 하락 없음)
- [ ] 캐시 적중률 전후 수치가 있다
- [ ] Fallback이 실제로 동작한 로그가 있다

## 면접 질문

<details>
<summary>에이전트 비용을 절반으로 줄여야 한다면 무엇부터 하나요?</summary>

먼저 트레이스로 단계별 비용을 분해해 가장 큰 항목을 찾습니다. 보통 입력 토큰이 지배적이므로 프롬프트 캐싱 구조(고정 내용 앞쪽, 변하는 값 제거)를 고치고, 큰 도구 결과를 절단·정리합니다. 다음으로 단계별로 모델을 나눠 라우팅·요약·추출은 작은 모델로 보내고, 턴 수를 줄이도록 병렬 호출과 도구 설계를 개선합니다. 실시간이 필요 없는 작업은 배치 API로 돌립니다. 각 변경마다 평가 세트로 품질이 유지되는지 확인합니다.
</details>

<details>
<summary>모델 라우팅과 캐스케이드의 차이는?</summary>

라우팅은 입력을 보고 처음부터 적절한 모델 하나를 고르는 방식이라 지연 추가가 적지만, 분류기가 틀리면 어려운 질문이 작은 모델로 갑니다. 캐스케이드는 작은 모델로 먼저 시도하고 검증이나 확신도 기준을 통과하지 못하면 큰 모델로 재시도하는 방식이라, 검증 가능한 작업에서 품질을 지키며 비용을 줄이지만 실패 시 지연이 늘어납니다. 둘을 섞어 쓰기도 합니다.
</details>

<details>
<summary>LLM 게이트웨이(LiteLLM 등)를 두는 이유는?</summary>

여러 공급자를 하나의 인터페이스로 통일하고, 공급자 장애 시 Fallback, 지연·비용 기반 라우팅, 재시도, 키·시크릿 중앙 관리, 팀·사용자별 예산과 레이트 리밋, 사용량·비용 기록을 한곳에서 처리하기 위해서입니다. 애플리케이션 코드가 특정 공급자에 묶이지 않습니다. 대신 공급자 고유 기능을 쓰기 어려워질 수 있고, 게이트웨이 자체가 장애 지점이 되므로 고가용성으로 운영해야 합니다.
</details>
