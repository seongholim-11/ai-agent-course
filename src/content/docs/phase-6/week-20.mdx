## 상용 API vs 자체 서빙

지금까지는 Anthropic·OpenAI 같은 공급자의 API를 불러 썼습니다. 다른 방법은 Llama, Qwen 같은 **오픈 모델**(가중치가 공개된 모델)을 내려받아 **내 GPU 서버에서 직접 돌리는 것(자체 서빙)**입니다. 전기를 한전에서 사 쓰느냐, 자가 발전기를 돌리느냐의 차이와 비슷합니다.

| | 상용 API | 자체 서빙 (vLLM 등) |
| --- | --- | --- |
| 품질 | 최상위 모델 사용 가능 | 오픈 모델 한정 (격차는 줄고 있음) |
| 초기 비용 | 없음 | GPU, 운영 인력 |
| 단가 | 토큰당 과금 | 사용량이 많고 일정하면 유리 |
| 데이터 | 외부로 전송 (계약으로 보호) | 내부에 머묾 (폐쇄망, 규제 산업) |
| 운영 | 공급자 책임 | 스케일링·장애 대응 직접 |
| 커스터마이징 | 제한적 | 파인튜닝 모델, 특수 디코딩 |

LangChain 조사에서 약 3분의 1의 조직이 자체 오픈소스 모델 배포에 투자하고 있다고 답했습니다. 한국에서는 금융·공공·제조처럼 **외부 인터넷과 끊긴 폐쇄망**에서 일해야 하는 곳이 많아 수요가 크고, 원본 강의가 vLLM을 다루는 이유이기도 합니다.

## 핵심 개념

### 1. LLM 추론의 두 단계

모델이 답을 만드는 과정(추론)은 두 단계로 나뉘고, 각 단계의 병목이 다릅니다. 책을 읽고 독후감을 쓰는 것에 비유할 수 있습니다.

- **Prefill(읽기):** 입력 토큰 전체를 한 번에 처리합니다. 책 전체를 한꺼번에 훑는 것처럼 병렬로 처리할 수 있어서, GPU의 **계산 능력**이 병목입니다(compute-bound). 이 단계가 **TTFT**(첫 토큰까지 시간)를 결정합니다. 입력이 길수록 오래 걸립니다.
- **Decode(쓰기):** 출력 토큰을 **하나씩** 만듭니다. 독후감을 한 글자씩 쓰는 것처럼 앞 글자가 나와야 다음 글자를 쓸 수 있어서 병렬화가 안 됩니다. 매 토큰마다 지금까지의 기억(KV 캐시) 전체를 메모리에서 읽어와야 해서, GPU **메모리에서 데이터를 꺼내오는 속도**가 병목입니다(memory-bound). 이 단계가 **TPOT**(토큰당 시간)를 결정합니다.

### 2. KV 캐시와 PagedAttention

**KV 캐시:** 모델은 다음 토큰을 만들 때 앞의 모든 토큰을 참고하는데, 매번 처음부터 다시 계산하면 너무 느립니다. 그래서 앞 토큰들의 계산 결과(Key와 Value라는 중간값)를 저장해두고 재사용합니다. 이 저장소가 KV 캐시입니다. 요청이 많고 대화가 길수록 GPU 메모리의 대부분을 KV 캐시가 차지합니다.

**문제:** 예전 방식은 요청이 들어오면 "이 요청은 최대 8,000토큰까지 갈 수 있으니" 8,000토큰분의 메모리를 **연속된 한 덩어리로 미리** 잡아뒀습니다. 실제로는 500토큰에서 끝나도 나머지 공간은 낭비됩니다. 식당이 2명 손님에게 10인석을 통째로 내주는 것과 같습니다.

**PagedAttention**(vLLM의 핵심 아이디어)은 운영체제가 메모리를 관리하는 방식(가상 메모리 페이징)을 빌려, KV 캐시를 **작은 블록으로 나눠 필요한 만큼만** 할당합니다. 손님이 늘어날 때마다 2인석을 하나씩 붙여주는 식입니다. 낭비가 크게 줄어서 같은 GPU에서 **훨씬 많은 요청을 동시에** 처리할 수 있습니다.

덤으로, 같은 앞부분(시스템 프롬프트 등)을 가진 요청끼리 블록을 **공유**하는 **prefix caching**도 가능합니다. 상용 API의 프롬프트 캐싱(3주차)과 같은 원리입니다.

### 3. Continuous batching

GPU는 요청을 여러 개 묶어서(배치) 한꺼번에 처리할 때 효율이 좋습니다.

- **정적 배치:** 요청 8개를 묶어 시작하면, 8개가 **모두** 끝날 때까지 새 요청을 못 넣습니다. 7개는 짧게 끝났는데 1개가 길면, GPU 자리 7개가 놀면서 기다립니다. 승객 8명이 모두 내려야 다음 승객을 태우는 버스와 같습니다.
- **Continuous(in-flight) batching:** **토큰 하나 만들 때마다** 끝난 요청을 빼고 대기 중인 새 요청을 넣습니다. 정류장마다 내린 만큼 바로 태우는 버스입니다. GPU가 쉬지 않아 처리량이 크게 늘어납니다.

### 4. 양자화와 그 밖의 기법

- **양자화:** 모델의 숫자(가중치)를 FP16(숫자 하나에 2바이트)에서 FP8/INT8(1바이트), INT4(0.5바이트)로 줄입니다. 고화질 사진을 압축하는 것과 비슷해서, 메모리가 줄고 속도가 빨라지지만 품질이 조금 떨어질 수 있습니다. 얼마나 떨어지는지는 작업마다 다르므로 **반드시 내 평가 세트로 확인**합니다(AWQ, GPTQ, FP8 등 방식).
- **텐서 병렬:** 모델 하나가 GPU 한 장에 안 들어가면 여러 GPU에 나눠 올립니다(`--tensor-parallel-size`).
- **추측 디코딩(speculative decoding):** 작고 빠른 초안 모델이 다음 토큰 몇 개를 먼저 제안하고, 큰 모델이 한 번에 검증해서 맞으면 그대로 채택합니다. 하나씩 쓰는 decode 단계를 빠르게 합니다.
- **구조화 출력:** vLLM은 JSON Schema 등으로 "이 형식에 맞는 글자만 고르게" 제약하는 guided decoding을 지원합니다(4주차 네이티브 Structured Outputs와 같은 원리). 오픈 모델의 도구 호출 안정성을 크게 높입니다.

### 5. vLLM 서버 띄우기

```bash
# GPU 머신에서 (Docker로 vLLM의 OpenAI 호환 서버를 띄운다)
docker run --gpus all -p 8000:8000 --ipc=host \
  -v ~/.cache/huggingface:/root/.cache/huggingface \  # 내려받은 모델을 재사용하도록 캐시 폴더 연결
  vllm/vllm-openai:latest \
  --model Qwen/Qwen3-8B \                  # Hugging Face에서 받아올 모델
  --max-model-len 32768 \                  # 한 요청의 최대 길이 (작게 할수록 KV 캐시 여유가 생긴다)
  --gpu-memory-utilization 0.9 \           # GPU 메모리의 90%까지 사용
  --enable-prefix-caching \                # 같은 앞부분을 가진 요청끼리 KV 캐시 공유
  --enable-auto-tool-choice --tool-call-parser hermes   # 도구 호출 지원 (파서는 모델 계열에 맞춰야 함)
```

```python
from openai import OpenAI
# 상용 OpenAI SDK를 그대로 쓰되, 주소만 내 서버로 바꾼다 (OpenAI 호환 API이기 때문)
c = OpenAI(base_url="http://gpu-host:8000/v1", api_key="local")
r = c.chat.completions.create(model="Qwen/Qwen3-8B", messages=[{"role": "user", "content": "안녕"}])
```

OpenAI 호환이므로 19주차 LiteLLM에 `local` 모델로 추가하면 에이전트 코드를 한 줄도 바꾸지 않고 라우팅할 수 있습니다. 도구 호출 파서(`--tool-call-parser`)는 모델 계열에 맞춰야 하니, 모델 이름과 옵션은 vLLM 문서의 지원 모델 목록에서 확인하세요.

<Aside type="tip" title="GPU가 없다면">
클라우드 GPU를 시간 단위로 빌리거나(RunPod, Lambda, Modal 등) 무료 노트북의 GPU로 작은 모델을 실험하세요. 개념 실습만이라면 CPU에서 Ollama로 OpenAI 호환 서버를 띄워 같은 코드를 시험할 수 있습니다.
</Aside>

### 6. 측정해야 할 서빙 지표

- **TTFT, TPOT, 엔드투엔드 지연**의 p50/p95
- **처리량:** 초당 출력 토큰 수, 초당 처리 요청 수
- **동시 요청 수에 따른 변화:** 동시성 1, 8, 32, 64에서 지연·처리량 곡선을 그리면 서버의 한계가 보입니다. 동시성을 올리면 처리량은 늘다가 어느 순간 평평해지고, 그때부터 지연만 급격히 늘어납니다. 그 꺾이는 지점이 이 서버의 적정 동시성입니다.
- **GPU 메모리·사용률**, KV 캐시 사용률, 대기열 길이

## 애플리케이션 배포

### 배포 대상 선택

에이전트 서버(FastAPI)를 인터넷에 올리는 방법은 여러 가지입니다.

| 선택지 | 적합 |
| --- | --- |
| 컨테이너 PaaS (Cloud Run, Fly.io, Render, Railway) | 포트폴리오, 소규모 서비스. Docker 이미지만 주면 알아서 띄워줘서 가장 빠름 |
| 쿠버네티스 | 사내 표준이 k8s인 회사, 대규모 |
| 서버리스 함수 | 짧은 요청만. 실행 시간 제한이 있어 긴 스트리밍·장기 작업에는 맞지 않음 |
| 관리형 에이전트 런타임 (AWS Bedrock AgentCore, Vertex AI Agent Engine 등) | 해당 클라우드를 쓰는 조직. 세션·메모리·관측을 클라우드가 관리 |

포트폴리오는 컨테이너 PaaS 하나에 배포하고, 면접에서 "쿠버네티스 환경이라면 이렇게 바꾸겠다"를 설명할 수 있으면 충분합니다.

### 운영 체크리스트

- [ ] 시크릿(API 키)은 플랫폼의 시크릿 관리 기능에 넣는다 (이미지·저장소에 넣지 않음, 2주차)
- [ ] `/healthz`(프로세스가 살아 있음)와 `/readyz`(DB·LLM 게이트웨이에 연결되어 요청을 받을 준비가 됨)를 분리한다. 살아 있어도 준비가 안 됐으면 트래픽을 보내면 안 된다
- [ ] 인증(API 키, OAuth/OIDC), 사용자별 레이트 리밋(Redis 토큰 버킷: 사용자마다 "토큰 통"을 두고 요청마다 하나씩 빼서, 통이 비면 잠시 거절)
- [ ] 요청 타임아웃과 스트리밍용 프록시 설정 (버퍼링 해제, 오래 조용한 연결을 끊지 않게 idle timeout 늘리기, 2주차)
- [ ] 구조화 로그 + 트레이스 ID 전파 (15주차)
- [ ] 비용 예산 알림
- [ ] 롤백 방법 (문제가 생기면 이전 이미지 태그로 즉시 되돌리기)
- [ ] CORS, HTTPS, 보안 헤더

## 심화

### 오픈 모델을 에이전트에 쓸 때의 현실

오픈 모델은 한 번 묻고 답하는 일은 잘해도, **여러 단계에 걸쳐 도구를 쓰는 긴 작업**에서는 상용 최상위 모델과 격차가 남아 있는 경우가 많습니다. 그래서 실무에서는 섞어 씁니다.

- **하이브리드:** 민감 데이터를 다루는 단계(문서 요약, 개인정보가 든 추출)는 내부 모델로, 데이터가 밖으로 나가도 되는 어려운 계획 단계는 상용 모델로.
- **폐쇄망이라 상용 모델을 못 쓴다면:** 작업을 더 작고 명확한 단계로 쪼개서 워크플로우 비중을 높이고(5주차), 구조화 디코딩과 단계별 검증을 강화합니다. 모델이 스스로 판단할 부분을 줄여주는 것입니다.

### 용량 산정 감각

"이 모델을 돌리려면 GPU가 얼마나 필요한가?"를 대략 계산할 수 있어야 합니다.

```
필요 메모리 ≈ 파라미터 수 × 숫자 하나당 바이트 + KV 캐시 + 여유분
```

예: 8B(80억) 파라미터 모델을 FP16(2바이트)으로 올리면 가중치만 8B × 2 = 약 16GB입니다. 24GB GPU에 올리면 KV 캐시에 쓸 수 있는 공간이 8GB도 안 남아서, 동시 요청 수와 컨텍스트 길이가 제한됩니다. 해결책은 양자화(INT4로 하면 가중치가 약 4~5GB), 더 큰 GPU, `max-model-len` 줄이기입니다. 면접에서 이 계산을 즉석으로 해 보이면 좋습니다.

## 실습 과제

`infra/` + `weeks/w20_serving/`

**A. 서빙**

1. vLLM(GPU) 또는 Ollama(CPU)로 오픈 모델 하나를 OpenAI 호환으로 띄운다.
2. 부하 테스트 스크립트(asyncio + httpx)로 동시성 1/8/32에서 TTFT·TPOT·처리량을 측정해 그래프로 그린다.
3. LiteLLM에 `local`로 추가하고, 6주차 RAG의 "청크 문맥 생성" 단계를 로컬 모델로 돌려 상용 모델 대비 품질·비용을 비교한다.

**B. 배포**

1. 포트폴리오 프로젝트 1 또는 2를 컨테이너 PaaS에 배포한다(백엔드 FastAPI + 간단한 웹 프론트).
2. 위 운영 체크리스트를 모두 적용한다.
3. 공개 URL에서 SSE 스트리밍이 끊김 없이 동작하는지 확인한다.

**채점 기준**

- [ ] 동시성별 지연·처리량 그래프가 있다
- [ ] 공개 URL이 있고, 인증 없이는 API를 호출할 수 없다
- [ ] 배포 환경에서 스트리밍이 토큰 단위로 나온다

<details>
<summary>vLLM이 빠른 이유는 무엇인가요?</summary>

핵심은 PagedAttention과 continuous batching입니다. PagedAttention은 KV 캐시를 고정 크기 블록으로 나눠 필요한 만큼만 할당하고 접두사가 같은 요청끼리 공유해 메모리 낭비를 크게 줄이므로, 같은 GPU에서 더 많은 요청을 동시에 처리합니다. Continuous batching은 토큰 단위로 끝난 요청을 빼고 새 요청을 넣어 GPU를 쉬지 않게 합니다. 여기에 최적화된 커널, 양자화, 텐서 병렬, 추측 디코딩, prefix caching 지원이 더해집니다.
</details>

<details>
<summary>TTFT와 TPOT은 무엇이고, 각각 무엇이 영향을 주나요?</summary>

TTFT는 요청 후 첫 토큰이 나오기까지의 시간으로, 입력 길이(prefill 연산량), 대기열, 캐시 적중 여부가 영향을 줍니다. TPOT는 이후 토큰 하나당 생성 시간으로, 모델 크기, 메모리 대역폭, 동시 배치 크기, 양자화가 영향을 줍니다. 채팅 UX는 TTFT가, 긴 출력 작업은 TPOT가 중요하고, 에이전트는 턴이 많아 TTFT가 누적되므로 캐싱과 입력 길이 관리가 특히 중요합니다.
</details>

<details>
<summary>폐쇄망 환경에서 에이전트를 만들어야 한다면?</summary>

vLLM 같은 서버로 오픈 모델을 내부에 서빙하고 OpenAI 호환 게이트웨이 뒤에 둡니다. 오픈 모델은 긴 다단계 도구 사용이 상대적으로 약하므로, 작업을 명확한 단계로 쪼개 워크플로우 비중을 높이고, 구조화 디코딩·스키마 검증·재시도를 강화하며, 도구 수를 줄이고 설명을 정교하게 씁니다. 임베딩·리랭커·관측 도구도 내부에 배포해야 하고, 모델·패키지의 공급망 검증과 오프라인 업데이트 절차가 필요합니다. 평가 세트로 상용 모델 대비 격차를 측정해 기대치를 관리합니다.
</details>
