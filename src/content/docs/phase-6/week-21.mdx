## 학습 목표

- 분~시간 단위 에이전트 작업을 요청-응답이 아닌 작업(job) 모델로 설계한다
- durable execution의 개념을 설명하고 LangGraph 체크포인트·Temporal과 비교한다
- 재시도, 타임아웃, 멱등성, 보상(compensation)으로 부분 실패를 다룬다
- 부하 테스트로 동시 처리 한계를 측정하고 병목을 찾는다

## 왜 별도 주차인가

데모 에이전트와 프로덕션 에이전트의 가장 큰 차이는 **실패했을 때 무슨 일이 일어나는가**입니다. 데모에서는 잘 돌아가는 모습만 보여주면 되지만, 실제 서비스에서는 이런 일이 매일 일어납니다.

- LLM API가 수시로 429(너무 많은 요청), 529(과부하), 타임아웃을 냅니다.
- 도구로 쓰는 외부 API가 갑자기 느려집니다.
- 새 버전을 배포하느라 서버 프로세스가 재시작됩니다.
- 사람 승인은 며칠 걸립니다.

30분짜리 보고서 작업이 25분째에 죽었는데 처음부터 다시 해야 한다면, 비용도 두 배가 들고 사용자 신뢰도 잃습니다. 이번 주는 "**어디서 죽어도 이어서 끝내는**" 에이전트를 만듭니다.

## 핵심 개념

### 1. 작업(job) 아키텍처

2주차에 살짝 본 작업 패턴을 본격적으로 만듭니다. 식당의 주문 시스템과 같습니다. 카운터(API)는 주문을 받고 번호표를 준 뒤 바로 다음 손님을 받고, 주방(워커)이 주문표 꽂이(큐)에서 주문을 꺼내 요리하고, 손님은 전광판(이벤트 스트림)으로 진행 상황을 봅니다.

```
Client ──POST /jobs──▶ API ──enqueue──▶ Queue (Redis/SQS/Postgres) ──▶ Worker N개
  │                     │                                              │
  │◀── 202 {job_id} ────┘                                              ├─ 에이전트 실행
  │                                                                    ├─ 체크포인트 저장 (Postgres)
  └── GET /jobs/{id}/events (SSE, Last-Event-ID) ◀── 이벤트 스트림 ◀────┘   진행 이벤트 발행 (Redis Stream)
```

- **API는 작업을 접수하고 즉시 반환**합니다(`202 Accepted` + 작업 번호). 무거운 일은 워커가 합니다. 그래서 API 서버가 재배포돼도 진행 중인 작업에 영향이 없습니다.
- **진행 이벤트는 저장소에 쌓아둡니다.** 이벤트마다 번호를 붙여두면, 클라이언트가 끊겼다가 다시 붙을 때 "마지막으로 받은 번호(`Last-Event-ID`)"를 알려주고 그 다음부터 받을 수 있습니다.
- **워커 수를 늘려 수평 확장**합니다. 단, 동시 실행 수는 LLM 레이트 리밋에 맞춰 제한합니다(아래 심화).
- **작업 상태:** `queued(대기) → running(실행 중) → (waiting_approval: 승인 대기) → succeeded(성공) / failed(실패) / canceled(취소)`. 사용자가 "그만"할 수 있도록 **취소 API가 꼭 필요합니다.**

### 2. 실패의 분류

모든 실패를 똑같이 "재시도"로 처리하면 안 됩니다. 종류에 따라 대처가 다릅니다.

| 실패 | 예 | 처리 |
| --- | --- | --- |
| 일시적 | 429, 529, 네트워크 끊김 | 지터 섞은 백오프로 재시도 (1주차) |
| 영구적 | 400 잘못된 요청, 권한 없음 | 재시도하지 않고 실패 처리, 모델에게 오류 전달 |
| 논리적 | 에이전트가 목표 달성 실패 | 바깥 루프에서 다른 전략으로 재시도하거나 사람에게 (12주차) |
| 인프라 | 워커 크래시, 배포 재시작 | 체크포인트에서 재개 |
| 지연 | 도구가 끝없이 안 끝남 | 단계별 타임아웃, 전체 데드라인 |

### 3. 멱등성

재시도와 재개를 안전하게 하려면, **같은 단계를 두 번 실행해도 결과가 한 번 실행한 것과 같아야** 합니다(멱등성, 2주차). 엘리베이터 버튼을 여러 번 눌러도 엘리베이터는 한 번만 오는 것과 같습니다.

특히 위험한 경우: 워커가 "환불 API 호출 성공" 직후, "완료 기록" 직전에 죽었다고 해봅시다. 재시작된 워커는 기록이 없으니 환불을 또 합니다. 이걸 막는 코드입니다.

```python
async def execute_refund(order_id: str, amount: int, *, idem_key: str):
    # idem_key = f"{job_id}:{step_id}" 처럼 "같은 작업의 같은 단계면 항상 같은 값"이 되게 만든다
    # 1) 이 키로 이미 실행한 적이 있는지 먼저 확인
    existing = await db.fetchrow("SELECT result FROM side_effects WHERE key=$1", idem_key)
    if existing:
        return existing["result"]       # 이미 했으면 다시 하지 않고 그때 결과만 돌려준다
    # 2) 처음이면 실행. 외부 결제 API가 멱등 키를 지원하면 같이 넘긴다
    #    → 우리 기록 전에 죽어도, 결제사가 "이 키는 이미 처리됨"이라며 중복을 막아준다 (이중 방어)
    result = await payments.refund(order_id, amount, idempotency_key=idem_key)
    # 3) 실행 결과를 기록
    await db.execute("INSERT INTO side_effects(key, result) VALUES($1, $2)", idem_key, result)
    return result
```

그런데 LLM 호출은 어떨까요? LLM은 같은 입력에도 다른 답을 하므로(3주차), 다시 부르면 다른 결과가 나와서 이후 흐름이 완전히 달라질 수 있습니다. 그래서 아래 durable execution 엔진은 **이미 끝난 단계(LLM 호출 포함)의 결과를 기록해두고, 재개할 때 다시 부르지 않고 기록된 결과를 재사용(replay)**합니다.

### 4. Durable execution

**Durable execution**은 "프로그램이 어디서 죽든, 마지막으로 완료된 단계부터 자동으로 이어서 실행된다"는 보장입니다. 게임의 체크포인트 저장과 같습니다. 보스전에서 죽어도 처음부터가 아니라 보스방 앞에서 다시 시작합니다.

| | LangGraph 체크포인트 | Temporal (및 유사 엔진) |
| --- | --- | --- |
| 저장 단위 | 그래프의 super-step (7주차) | 워크플로우의 activity(작업 단위) |
| 재개 방법 | 같은 thread로 다시 invoke | 엔진이 자동으로 재시도·재개 |
| 타이머·대기 | interrupt 후 외부에서 resume | 내장 타이머, 신호(signal), 며칠짜리 대기 |
| 재시도 정책 | 노드별 RetryPolicy | activity별 재시도·타임아웃·하트비트 |
| 운영 부담 | 저장소(Postgres)만 있으면 됨 | 별도 서버 클러스터(또는 관리형 서비스) |
| 적합 | 에이전트 내부 흐름, 사람 승인 | 여러 시스템에 걸친 긴 비즈니스 프로세스 |

**Temporal**은 durable execution 전용 엔진입니다. 코드를 "워크플로우(전체 흐름)"와 "activity(실제로 바깥 세상과 상호작용하는 단계)"로 나눠 쓰면, 엔진이 activity마다 결과를 기록합니다.

```python
# Temporal 스케치: LLM 호출과 도구 호출을 activity로 분리한다
@activity.defn
async def llm_step(messages: list[dict]) -> dict: ...      # 비결정적인 일(LLM 호출)은 activity로

@activity.defn
async def tool_step(name: str, args: dict, idem_key: str) -> str: ...   # 부수효과 있는 일도 activity로

@workflow.defn
class ResearchWorkflow:
    @workflow.run
    async def run(self, task: str) -> str:
        messages = [{"role": "user", "content": task}]
        for turn in range(30):
            # activity 실행: 엔진이 결과를 기록해두므로, 재개 시 이미 끝난 호출은 다시 하지 않는다
            resp = await workflow.execute_activity(llm_step, messages,
                         start_to_close_timeout=timedelta(minutes=2),       # 한 번 호출은 최대 2분
                         retry_policy=RetryPolicy(maximum_attempts=5))      # 실패하면 최대 5번 재시도
            ...   # 도구 호출도 activity로, 결과는 엔진이 기록
```

규칙이 하나 있습니다. **워크플로우 코드는 결정적이어야 합니다.** 현재 시각 읽기, 난수, 직접 네트워크 호출을 워크플로우 안에서 하면 안 되고, 비결정적인 일은 모두 activity로 뺍니다. 왜냐하면 재개할 때 엔진은 워크플로우 코드를 처음부터 다시 "재생"하면서, activity 자리에 오면 기록된 결과를 끼워 넣기 때문입니다. 워크플로우 코드가 매번 다르게 동작하면 기록과 맞지 않게 됩니다. 이 규칙만 지키면, 워커가 죽어도 다른 워커가 기록을 재생해 **정확히 같은 지점에서** 이어갑니다.

### 5. 타임아웃 계층

타임아웃은 여러 층으로 두고, **안쪽이 바깥쪽보다 항상 짧아야** 합니다. 그래야 안쪽 단계가 멈췄을 때 바깥쪽 단계가 정리할 시간을 가질 수 있습니다.

- LLM 호출 하나: 60~120초
- 도구 호출 하나: 도구별 (검색 15초, 코드 실행 30초)
- 에이전트 턴 수: 최대 N턴
- 작업 전체: 데드라인 (예: 30분). 넘으면 지금까지의 결과로 "부분 완료" 처리
- 사람 승인 대기: 만료 시간 (예: 72시간) 후 자동 취소 + 알림

## 심화

### 보상(compensation)과 사가(saga)

여러 외부 시스템에 걸친 작업은 DB 트랜잭션 하나로 묶을 수 없습니다. 여행 예약 에이전트가 "항공권 예약 → 호텔 예약 → 렌터카 예약"을 하다가 렌터카에서 실패하면, 이미 예약한 항공권과 호텔은 자동으로 취소되지 않습니다.

그래서 각 단계마다 **되돌리는 동작(보상 작업)**을 미리 정의해두고, 중간에 실패하면 이미 한 단계의 보상 작업을 **역순으로** 실행합니다(호텔 취소 → 항공권 취소). 이 패턴을 **사가(saga)**라고 합니다. 에이전트가 부수효과 있는 도구를 여러 개 쓴다면, 도구마다 "되돌리기" 도구를 짝지어 두면 실패 처리가 명확해집니다.

### 부하와 레이트 리밋

워커를 아무리 늘려도, **LLM 공급자의 분당 요청 수(RPM)·분당 토큰 수(TPM) 한도**가 실제 상한입니다. 고속도로 차선을 늘려도 톨게이트 수가 그대로면 소용없는 것과 같습니다.

- **전역 토큰 버킷(Redis):** 워커마다 따로 제한하면 합쳐서 한도를 넘으니, 모든 워커가 공유하는 하나의 "토큰 통"을 Redis에 두고 요청 전에 하나씩 꺼내게 합니다.
- **우선순위 큐:** 사람이 기다리는 실시간 요청(채팅)을 배치 작업보다 먼저 처리합니다.
- **기능 강등:** 한도에 가까워지면 작은 모델로 바꾸거나, 급하지 않은 작업은 배치 API로 돌립니다(19주차).

### 장애 시나리오 연습 (game day)

**Game day**는 일부러 장애를 일으켜보고 시스템이 설계대로 견디는지 확인하는 훈련입니다. 소방 훈련과 같습니다. 진짜 불이 났을 때 처음 확인하면 늦습니다.

- LLM 공급자 하나가 10분간 529를 낸다 → Fallback이 동작하는가
- 워커 절반을 강제 종료한다 → 작업이 재개되는가, 중복 부수효과가 없는가
- 도구 API가 30초씩 지연된다 → 타임아웃과 부분 완료가 동작하는가
- 큐에 작업 1,000개가 몰린다 → 대기 시간과 비용 예산이 통제되는가

### 백그라운드·비동기 에이전트의 UX

사용자가 화면 앞에서 기다리지 않는 에이전트(코드 리뷰 봇, 야간 리서치, 이메일 분류)가 늘고 있습니다. 이런 에이전트는 화면 설계가 다릅니다. 시작 알림, 진행 상황 페이지, 완료 알림(메일·슬랙), 결과 검토 화면, 그리고 실패 시 사람이 이어받는 경로가 필요합니다.

여러 에이전트를 동시에 돌리면 이번엔 **사람의 검토가 병목**이 됩니다. 에이전트 10개가 보고서 10개를 내놓으면 사람이 다 읽을 시간이 없습니다. 그래서 검토를 결과물 단계가 아니라 **계획 단계로 앞당기는** 방식도 씁니다. "이렇게 조사하겠습니다"를 먼저 승인받고 나면, 결과물 검토는 훨씬 가벼워집니다.

## 실습 과제: 죽지 않는 리서치 서비스 (Phase 6 완료 과제)

포트폴리오 프로젝트 1에 적용합니다.

**요구사항**

1. `POST /jobs`, `GET /jobs/{id}`, `GET /jobs/{id}/events`(SSE, Last-Event-ID), `POST /jobs/{id}/cancel`.
2. 워커는 별도 프로세스(컨테이너)로, LangGraph 체크포인트(Postgres) 또는 Temporal로 내구성을 확보한다.
3. 모든 부수효과 도구(파일 저장, 알림 발송)는 멱등 키를 쓴다.
4. 타임아웃 계층(호출·도구·턴·전체 데드라인)을 모두 적용한다.
5. Game day: 작업 실행 중 워커를 `kill -9`하고 재시작 → 작업이 이어서 완료되고 알림이 한 번만 간다.
6. 부하 테스트: 작업 20개를 동시에 넣어 완료 시간 분포, 실패율, 총비용을 측정하고 전역 레이트 리밋이 동작함을 확인한다.

**채점 기준**

- [ ] 워커 강제 종료 후 재개 성공 + 중복 부수효과 없음
- [ ] 클라이언트 재접속 시 놓친 이벤트부터 받는다
- [ ] 취소 API가 진행 중인 LLM 호출을 멈춘다
- [ ] 부하 테스트 결과표가 있다

<summary>오래 걸리는 에이전트 작업의 신뢰성을 어떻게 보장하나요?</summary>

요청-응답 대신 작업 큐와 워커 구조로 바꾸고, 상태를 체크포인트로 외부화해 워커가 죽어도 마지막 완료 단계부터 재개하게 합니다. 일시적 오류는 지터 백오프로 재시도하고, 부수효과가 있는 단계는 멱등 키로 중복 실행을 막으며, LLM 호출·도구·턴·전체 작업에 계층적 타임아웃을 둡니다. 진행 이벤트를 저장해 클라이언트가 재접속해도 이어받게 하고, 취소와 부분 완료 처리를 지원합니다. 필요하면 Temporal 같은 durable execution 엔진을 쓰고, 장애 시나리오 연습으로 검증합니다.
</details>

<details>
<summary>Durable execution이란 무엇이고 에이전트에 왜 필요한가요?</summary>

프로세스가 어디서 중단되든 완료된 단계의 결과를 기록해두고, 재시작 시 기록을 재생해 정확히 중단 지점부터 이어 실행하는 실행 모델입니다. 에이전트는 실행 시간이 길고, LLM 호출이 비결정적이라 다시 하면 결과가 달라지며, 외부 부수효과가 있고, 사람 승인처럼 긴 대기가 있기 때문에 필요합니다. 완료된 LLM 호출 결과를 재사용하므로 비용과 일관성을 모두 지킵니다.
</details>

<details>
<summary>에이전트 도구에서 멱등성이 왜 중요한가요?</summary>

재시도, 체크포인트 재개, 네트워크 중복 요청으로 같은 도구 호출이 여러 번 실행될 수 있기 때문입니다. 결제, 메일 발송, 티켓 생성 같은 부수효과가 두 번 일어나면 실제 피해가 생깁니다. 작업·단계 ID로 결정적인 멱등 키를 만들고, 실행 기록을 저장해 같은 키는 이전 결과를 돌려주며, 외부 API가 멱등 키를 지원하면 함께 전달합니다.
</details>
